# Short PRD

把产品需求写成可直接粘贴到讨论或需求文档中的短说明。默认使用中文，以用户认可的“流程＋具体规则”格式输出。

## 写法

1. 先提取用户已确认的决定，必要时核对当前有效 PRD。建议、待定项和已确认规则分开，不把建议写成定论。
2. **先写流程**：用一行“入口 → 用户动作 → 系统反馈 → 结果”串起主流程，通常 3–6 步，只保留实际存在的步骤。
3. **再写具体规则**：通常 4–7 条，每条以简短的加粗标签开头，用一至两句说明行为、条件或边界。不为凑条数增加规则。
4. 使用用户能理解的词，例如“点击展开”“再次收起”“当天重开”“跨日处理”。优先写用户做什么、界面如何反馈。
5. 删除背景铺垫、反复解释、论证过程、客套开场和结尾总结；默认不用表格、嵌套列表或长段落。
6. 简短不等于省略关键条件：保留适用时间、重复操作、奖励去重、已有数据与进度例外等会改变行为的规则，只写本题相关内容。
7. 不加入用户未确认的入口、文案、玩法或数值；不把产品目标写成已实现能力。遇到影响流程的关键缺口，简短标为“待确认”，必要时只问关键问题。
8. 用户提供截图时，参考其排版、短标签和信息密度；除非用户明确要求，不把截图中其他功能的业务规则搬入当前需求。
9. 默认直接在对话中输出。只有用户要求更新文档时才修改对应文件，遵守仓库的目标文件及提交规则。

## 输出模板

**流程：** 进入入口 → 执行操作 → 显示反馈 → 得到结果。

**具体规则：**

- **默认状态：** 说明进入时看到什么。
- **点击操作：** 说明点击后如何变化。
- **重复操作：** 说明再次点击或重新进入时如何处理。
- **边界处理：** 说明与本需求有关的时间、状态或资格限制。
- **保留与例外：** 说明哪些结果、数据或已有进度继续保留。

标签和条数按实际需求调整，不必机械套用。用户仅要求段落时，仍保持先流程后规则的顺序，将规则改写为简短段落。

## 输出前检查

- 流程是否在规则之前？
- 每条是否只表达一组紧密相关的规则？
- 是否只写已确认内容，并显式标出必要的待定项？
- 是否保留会改变用户行为或结果的条件与例外？
- 能否删去一句而不丢失规则？能则删去。
