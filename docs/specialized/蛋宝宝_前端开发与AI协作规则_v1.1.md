# 蛋宝宝 前端开发与 AI 协作规则 v1.1

> 状态：正式生效（2026-09-21）
> 适用范围：蛋宝宝微信小程序 C 端仓库内所有前端开发、文档整理与 AI 协作任务
> 历史版本：《蛋宝宝_前端开发与AI协作规则_v1.0》保留为历史文档，不再作为执行依据；v1.1 中未重述的 v1.0 规则一律视为作废。

本文件与 `AGENTS.md` 的长期硬规则保持一致。冲突时以 `AGENTS.md` 为准，并同步修订本文件。

经验来源：[前端静态项目经验迁移（来自“标看看”Project Lessons Learned）](../development/蛋宝宝_前端静态项目经验迁移_20260919.md)。其中与本规则重叠的条目以本文件表述为准。

## 1. 产品只维护两种状态

- 产品只有两种状态：**开发状态** 与 **正式状态**，不存在第三套产品逻辑。
- 微信技术环境按以下方式映射：

| 微信 `envVersion` | 产品状态 |
| --- | --- |
| `develop` | 开发状态 |
| `trial` | 正式状态（沿用 release 逻辑） |
| `release` | 正式状态 |

- `trial` 是正式状态的预览，不允许为它单独维护功能开关、文案或路由。
- 正式用户功能在 `develop`、`trial`、`release` 三个环境中必须可用且行为一致。
- 只有以下能力限 `develop`：fixture 切换、测试按钮、场景与状态切换器、开发说明、独立开发验收入口、调试日志与测试参数。
- 正式用户功能开关与开发调试开关必须分开维护，不得用同一个布尔值（例如 `localDemoEnabled`）同时控制两类能力。

## 2. 从用户真实入口开发和验收

- 任何用户功能都从用户真实到达的入口开始实现和验收，不以开发验收页、编译参数或直达路由作为功能存在的证明。
- 破壳后房间左上角现有“今日心情”是今日陪伴的唯一入口；信件以 overlay 形式出现在当前房间之上，不跳转第二张场景图。
- 开发验收入口只用于快速比较开发状态界面，正式用户命中旧路由时必须回到正式入口或欢迎页。

## 3. 用户确认的可见内容是封闭清单

- 经用户（COO）人工验收确认的界面内容是封闭清单：只允许出现清单中的元素。
- AI 不得擅自增加文案、小标题、落款、解释说明、装饰（心形、勾选、徽章、横线）、图标、新入口、新卡片、新页面或新的文字层级。
- 用户没有提出的可见元素默认不加入；用户已经确认的视觉、文案、leading、间距和层级不得重新设计。
- 一次只改用户指出的问题，不顺手补充“替代元素”。

## 4. 人工视觉验收不可替代

- 自动测试只证明结构、状态和环境策略没有回归，不代表视觉已经获得确认。
- 视觉好坏由 COO 在微信开发者工具中人工确认；自动截图不能代替人工验收。
- 用户没有明确要求时，不使用 computer-use，也不用自动化操作替代人工点击验收。

## 5. 前端边界

- 前端只做三件事：静态 UI、本地内容、接口适配层。
- 本地状态不等于服务端能力：页面内防重复点击、运行内存中的星星累计只是前端保护，不是正式服务端幂等或持久化。
- 未经用户在当前任务中明确扩大范围，不得新增云函数、数据库、远程 AI、正式账号系统、服务端写入、跨设备同步、服务端幂等、正式内容下发、数据仓库或真实留存计算。
- COO 已确认的本地静态内容可以进入正式版，但文档和界面不得声称 CTO 服务已经接入。
- adapter 保持 `iaa-mvp-v1` 合同形状，正式接入时由 CTO 替换 adapter，页面不直接读取服务端专属字段。

## 6. 仓库、分支与合入

- 正式代码只在 `/Users/octopusgump/dev/eggbabe-main` 维护；其他目录、iCloud 副本或临时目录只作为参考，不得成为提交来源。
- 长期分支只保留 `main`；任务分支遵守 `AGENTS.md` 的 `<type>/<scope>-<summary>-<YYYYMMDD>` 命名规范。
- 任务分支经 COO 人工验收后合入 `main`，随后归档并清理；未经验收不得合入，也不得由 AI 自行合并或删除分支。
- 提交只按明确路径暂存，禁止 `git add .` 与 `git add -A`；一个任务分支只承载一个交付主题。

## 7. 文档纪律

- 文档必须区分“完整概念范围”和“本次实际发布范围”，不得把暂停项写成已上线。
- 状态描述统一使用“开发状态 / 正式状态”，不再使用“develop-only”“正式版不开放”等与本规则冲突的表述来描述正式用户功能。
- 历史文档保留并标注为历史，不覆盖、不删除。

## 8. 结论与交付诚实

- 报告中的结论必须区分“实跑确认”和“读码推断”；推断只能作为排查线索，不能写成产品事实。用户看到的真实现象与推断冲突时，以真实现象为准并撤回旧结论。
- 未验证项单独列出，不与已验证结果混写；测试失败如属基线已有问题，要说明并给出证据，不得静默跳过或顺手扩大范围修复。
- 每个任务的分支、提交和推送去向必须明确，不留下只存在于本地的孤本。
