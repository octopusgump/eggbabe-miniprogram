## 产品意图

用户从百宝箱进入“明信片”，同一次东京旅行只显示一个“东京之旅”入口。点击进入明信片详情后，点击明信片大图，进入像破壳后生活空间一样的全屏沉浸式场景，观看玉兔经历的东京之旅。东京可包含咖啡巷与城市露台两个子场景，用户可横向浏览同一 `journey_id` 下的多个旅途时刻。

这是历史回放，不是玉兔此刻的实时状态。任何浏览、点击或返回都不得改变玉兔当前所在场景、动作、时段、旅行状态或服务端业务数据。

## 当前基础

- 明信片仍在既有功能中，没有东京专属按钮。
- 开发版三态预览的第三态只有一个“东京之旅”入口。
- 东京预览旅程包含 12 张 1600×900 候选合成图：咖啡巷 8 张、城市露台 4 张。
- 明信片大图已绑定 `onOpenJourneyScene`，已新增并注册 `pages/journey-scene/journey-scene`。
- 回放页已具备全屏图片、横向 `swiper`、返回、场景标题、动作标题和第一人称正文。
- 容易被误认为按钮的“左右滑动看这次旅程”胶囊已删除。
- 候选图只用于微信开发版验收，正式 `POST_HATCH.postcards` 仍为空。
- 工作区已有用户修改与删除记录，必须全部保留。

## 素材能力边界

当前 12 张 WebP 已把环境、玉兔、动作、道具、遮挡和阴影烘焙在同一张图中，没有无角色底图、透明角色动作、遮挡层、动画帧或可靠热点坐标。因此：

- 不得伪造玉兔自由走动、拖动或独立动画；
- 不得创建与画面不一致的道具热点；
- 不得用 CSS 位移或透明点击区伪装已完成真实交互；
- 首版保持“全屏静态旅途回放＋横向切换＋原生文案”的诚实降级；
- 真正的独立走动、动画和热点需要新的分层美术资产与状态验收，不在本轮伪实现。

## 数据与发布边界

- 一个 `journey_id` 对应列表中的一个旅程入口；咖啡巷和城市露台是同一次东京旅程的子场景。
- 不同日期的两次东京旅行才使用不同 `journey_id`。
- 候选图不得写入 `miniprogram/config/post-hatch-assets.js`，不得重命名成正式资产，不得移动、覆盖、删除或生成新图片。
- 不接入正式后端，不虚构接口成功。
- 检查开发预览资源是否可能被 trial / release 打包。如果现有机制不能在保留开发验收的同时仅排除 trial / release，必须如实记录并要求发布前检查上传文件清单，不能只凭 `localDemoEnabled` 声称候选文件一定不进包。

## 验收路径

1. 在微信开发者工具中进入已破壳玉兔。
2. 打开百宝箱 → 明信片，将开发版三态预览切到第三态。
3. 列表中只有一个“东京之旅”入口。
4. 进入详情，点击当前明信片大图，进入独立全屏旅途回放。
5. 回放从刚才点击的图片开始；横向滑动可查看咖啡巷和城市露台。
6. 图片完整、清楚，不压缩、不拉伸、不裁掉主体。
7. 场景名、动作名和第一人称正文随图片更新。
8. 页面没有胶囊滑动按钮、数量、锁定、进度或新增东京入口按钮。
9. 返回后回到原明信片详情和原图片位置。
10. 进入前后玉兔的当前状态完全一致。
11. 无旅程数据、数据不匹配、图片失败时都有可返回的安全状态。
12. trial / release 不显示开发预览控件，正式素材配置不引用 `_candidates`。
