## 1 · 背景与现状

当前项目已经具备聊天入口、完整聊天页面、输入框、消息气泡、等待动画和正式接口适配层，但还不具备可上线的正式聊天闭环。

当前主要问题：

1. `backendEnabled=false` 且 `apiBase` 为空，trial / release 无法访问正式聊天服务。
2. develop 环境只返回本地审核过的固定回复，不是真实模型对话。
3. 聊天页每次进入都重新生成开场白，没有读取和展示历史消息。
4. 模型异常或超时时，正式链路返回失败，没有按主 PRD 返回审核过的兜底回复。
5. 失败消息留在页面，同时输入框恢复原文；再次发送会出现重复气泡和重复请求风险。
6. 现有测试以静态门禁、demo 和模拟接口为主，尚未完成真实后端、真机和异常链路测试。

## 2 · 产品目标

破壳后，当蛋宝宝处于任一居家状态时，用户可以进入完整聊天页，与同一只蛋宝宝进行安全、连续、稳定的文字对话。

上线版本必须做到：

- 正式用户发送的消息能够到达正式服务，并得到蛋宝宝回复。
- 回复保持蛋宝宝的固定人设、今日语气和当前场景，不因重新进入页面而无故失忆。
- 模型不可用时仍有审核过的安全回复；网络不可用时不伪装成发送成功。
- 重试不会造成重复气泡、重复模型调用或重复落库。
- 输入和输出在展示、落库前均经过服务端内容安全检查。
- 聊天正文不进入广告、用户画像、关系等级、成长值、权益或解锁系统。

## 3 · 非目标

本期不包含：

- 语音输入、语音回复或实时语音通话；
- 群聊、用户之间聊天或公开社区；
- 好感度、关系等级、连续聊天奖励或隐藏剧情解锁；
- 用户自定义模型、人设或系统提示词；
- 外出状态下的聊天、写信、留言或回信；
- 医疗诊断、用药方案、法律结论、投资建议、成人内容或违法指导。

## 4 · 用户与使用条件

### 4.1 前置条件

- 用户已经登录并持有服务端签发或验证的正式会话。
- 用户已经绑定一枚属于自己的实体蛋。
- 服务端生命周期为 `HATCHED`。
- `getPostHatchHome.chat_access.status` 为服务端返回的 `available`。

任一条件不满足时，不进入可输入的聊天状态，并向用户展示明确原因。

### 4.2 入口规则

- 左下角始终显示同一个“陪伴状态图标”，不因外出而消失。
- 服务端返回 `chat_access.status=available` 时，图标为正常态；点击后直接进入完整聊天页，不弹出场景内输入框。
- 服务端返回 `chat_access.status=away` 或 `unavailable` 时，图标为低饱和禁用视觉，并显示“外出中”或“暂不可聊”标识；轻触只展示服务端返回的状态说明，不进入聊天、写信、留言或回信。
- App 不得根据本地 `atHome`、`major_scene_id`、小场景或时间自行决定图标是否可聊天；这些字段仅用于场景视觉。
- 旧版“外出时左下角留空”规则废止；本次保留的是**状态提示**，不是沟通入口。

### 4.3 目标对话架构：服务端唯一规则来源

破壳后正式聊天采用“**App 无规则、服务端全决策**”架构。App 不是内容审核器、上下文拼装器或回复生成器，不能以本地关键词、长度、场景或历史记录得出任何聊天结论。

```text
用户输入
  ↓
App：创建 pending 临时气泡 + 发送最小请求
  ↓ HTTPS
chatReply 服务端
  ├─ ① 会话 / 蛋归属 / 破壳 / 当前可聊天状态校验
  ├─ ② 幂等查询（同一 client_message_id 直接返回已有最终结果）
  ├─ ③ 输入规则与内容安全（空白、长度、隐私、一般违规、危机）
  ├─ ④ 从服务端读取人设、权威场景、必要历史与记忆边界
  ├─ ⑤ 模型生成或服务端审核兜底
  ├─ ⑥ 输出安全审核
  └─ ⑦ 原子落库 / 审计 / 返回标准结果
  ↓
App：仅按结果类型更新气泡、恢复草稿或展示服务端文本
```

**职责边界**

| 能力 | App | 服务端 |
| --- | --- | --- |
| 输入内容规则、最大长度、敏感信息、一般违规、危机判断 | 不判断 | 唯一判断来源 |
| 当前是否可聊天、场景、蛋归属、破壳状态 | 仅展示 | 权威判断来源 |
| 模型上下文、历史裁剪、人设、记忆 | 不上传、不拼装 | 从权威数据读取并组装 |
| 回复、危机安全结果、模型故障兜底 | 不生成、不改写 | 生成、审核、落库 |
| 幂等、限流、审计、数据保留和删除 | 不处理业务规则 | 唯一处理来源 |
| 气泡、等待、失败重试、草稿恢复 | 展示与交互 | 返回明确结果类型 |

**App 可处理的结果状态（不基于正文判断）**

| 服务端结果 | App 动作 |
| --- | --- |
| `REPLY`（`safety_result=passed`） | 将同一临时气泡确认为 `sent`，展示服务端回复 |
| `CRISIS_REPLY`（`safety_result=crisis`） | 将同一临时气泡确认为 `sent`，原样展示服务端安全结果 |
| `INPUT_REJECTED` | 移除临时气泡，恢复草稿，展示服务端提示，不提供原地重试 |
| `RETRYABLE_ERROR` | 临时气泡改为 `failed`，允许复用同一幂等键重试 |
| `FATAL_ERROR` | 停止当前聊天或刷新状态；不伪造回复 |

## 5 · 核心用户流程

### 5.1 正常流程

1. 用户在居家生活空间点击聊天按钮。
2. App 打开聊天页，同时请求最近一页聊天记录。
3. 页面显示头像、昵称、当前状态和历史消息，并滚动到最后一条。
4. 用户输入文字并点击发送。
5. App 立即生成一条状态为“发送中”的本地用户消息，并锁定重复发送。
6. 服务端完成身份、蛋归属、生命周期、场景权限、输入安全和幂等校验。
7. 服务端读取蛋宝宝基础人设、今日心情、当前状态和必要历史，生成回复。
8. 服务端完成输出安全检查，将用户消息和安全回复原子落库。
9. App 用服务端返回的消息 ID 更新用户消息状态，并展示蛋宝宝回复。

### 5.2 重新进入

1. App 请求服务端最近一页历史消息。
2. 页面不得只显示新的开场白而丢失已有对话。
3. 如果历史为空，可以显示当前场景开场白；开场白默认不作为用户真实聊天记录重复落库。

### 5.3 加载更多历史

- 首屏读取最近 20 条消息。
- 用户向上滚动到顶部时，使用服务端游标读取更早消息。
- 服务端按稳定顺序返回，App 去重后插入顶部，不改变用户当前阅读位置。
- App 只向页面展示历史，**不向 `chatReply` 上传历史或场景上下文**；服务端从权威聊天记录中选择必要的最近上下文，默认最多 12 条。页面展示数量和模型上下文数量互不绑定。

## 6 · 页面和交互要求

### 6.1 顶部区域

必须显示：

- 蛋宝宝头像；
- 蛋宝宝昵称，未命名时显示“蛋宝宝”；
- 当前场景状态，例如“在家 · 看书”或“旅行 · 大理”。

### 6.1.1 不可聊天状态页

- 用户通过旧链接、分享链接或状态切换期间进入聊天页，而服务端返回 `chat_access.status!=available` 时，页面显示“蛋宝宝现在不在家”和服务端 `chat_access.message`。
- 不展示聊天历史、输入框、发送按钮、写信、留言或回信入口；提供“返回生活空间”。
- 用户正在发送时若服务端返回 `TALK_NOT_AVAILABLE`，App 移除未确认临时气泡，保留草稿，切换为不可聊天状态页；不将该消息标记为发送失败，也不允许重试。

### 6.2 消息状态

用户消息至少支持以下状态：

| 状态 | 页面表现 | 可执行操作 |
| --- | --- | --- |
| `pending` | 正常气泡 + 轻量发送中状态 | 不允许重复点击 |
| `sent` | 正常气泡 | 无 |
| `failed` | 气泡旁显示“发送失败” | 点击重试 |

重试必须复用同一条本地消息、`client_message_id` 和幂等键，不得新增第二个相同气泡。

### 6.3 回复等待

- 等待回复时自动滚动到三点气泡。
- 成功、被安全拒绝或失败后立即移除等待气泡。
- 单条请求处理中可以继续编辑下一条草稿，但本期默认不允许并行发送。
- 页面离开或请求超时后，应取消仍可取消的网络请求，并忽略已经失效的页面回调。

### 6.4 输入校验

- 空白、长度、敏感信息、一般违规和危机表达均由服务端统一判断。
- App 原样发送用户输入；收到服务端拒绝后，移除临时气泡、恢复草稿并展示服务端提示。
- 最大长度暂定 120 个 Unicode 字符，但该限制只在服务端执行和维护。

## 7 · 异常与兜底规则

### 7.1 模型不可用

模型超时、模型供应商故障或模型输出未通过安全检查时：

- 服务端返回审核过的固定回复并正常落库；
- 响应标记 `fallback_used=true` 和内部原因码；
- App 按普通蛋宝宝回复展示，不向用户暴露模型、供应商、安全评分或内部规则；
- 同一条用户消息不得重复调用模型。

建议兜底文案按法务审核版本配置，例如：“我在听。慢慢说就好。”

### 7.2 网络失败

- App 将用户消息标记为 `failed`，保留在原位置并提供重试。
- 不得把尚未获得服务端确认的用户消息标记为已发送。
- 不得用本地角色回复伪装成服务端已经收到消息。
- 重试复用原 `client_message_id`；若服务端已处理过，应直接返回同一结果。

### 7.3 请求超时

- App 请求超时时间与服务端响应目标必须统一，默认 10 秒，最终数值由联调确认。
- 超时后进入可重试状态，不新增重复消息。
- 服务端依靠幂等键解决“已经处理成功但响应丢失”的情况。

### 7.4 内容安全拒绝

- 一般违规输入：服务端不调用模型、不落聊天正文，并返回审核后的提示。
- 手机号、身份证号、邮箱等敏感信息：服务端拒绝处理并返回隐私保护提示。
- 严重危机表达：由服务端暂停日常角色扮演，并返回法务审核的安全结果；App 只展示服务端已审核的结果。
- 危机判断、回复文案和审计标记均由服务端负责；App 不得根据本地关键词改写服务端回复；危机事件不进入人设、偏好或商业画像。

## 8 · CTO / 服务端需求

### 8.1 P0 服务能力

CTO 负责提供：

1. 正式登录与会话签发、刷新和失效机制。
2. `getPostHatchHome` 正式接口，返回权威当前状态、服务端时间及必填 `chat_access`。
3. `getChatHistory` 接口，支持按蛋、游标和页大小读取历史。
4. `chatReply` 接口，完成校验、安全、生成、幂等和落库。
5. 模型服务、基础人设读取、今日心情和当前场景上下文组装。
6. 输入、输出双向内容安全和危机兜底。
7. 消息保存、查询、删除、保留期限和账号注销联动。
8. 限流、成本护栏、错误日志、调用链路追踪和告警。
9. staging 与 production 两套 HTTPS 环境、测试账号和已破壳测试蛋。
10. 所有聊天规则的版本配置、灰度发布与回滚；不得把规则下发给 App 后由 App 自行执行。

### 8.1.1 `chat_access` 权威合同（CTO P0）

`getPostHatchHome` 的成功响应必须包含以下字段；App 只读取和展示，不根据场景表推导聊天权限：

```json
{
  "chat_access": {
    "status": "available",
    "reason": "AT_HOME",
    "message": "",
    "next_available_at": null
  }
}
```

| 字段 | 规则 |
| --- | --- |
| `status` | 必填枚举：`available`、`away`、`unavailable`。只有 `available` 可打开可输入聊天页。 |
| `reason` | 必填服务端原因码，例如 `AT_HOME`、`AWAY`、`LIFECYCLE`、`SYSTEM`；供分析和排障，不展示内部实现。 |
| `message` | `away` / `unavailable` 时必填，已审核、可直接展示的用户文案；不得包含模型、审核或内部服务信息。 |
| `next_available_at` | 可选 ISO 8601 时间；只有服务端能确定时返回，App 不猜测回家时间。 |

缺失或非法 `chat_access` 视为 `unavailable`：App 显示“聊天权限正在同步，请稍后再试”，不得本地放行。demo 仅可用同结构 fixture 模拟，不得成为正式运行兜底。

### 8.2 `chatReply` 服务端处理顺序

服务端必须按以下顺序处理每一条请求；任一步失败都不得进入后续模型生成：

1. 校验会话、用户、蛋归属、环境和 `HATCHED` 状态。
2. 校验当前权威聊天权限 `chat_access.status=available`，不得信任 App 传来的场景、`atHome` 或任何可聊天标记；不满足时返回 `TALK_NOT_AVAILABLE` 和已审核用户文案。
3. 以 `egg_id + client_message_id` 查询幂等记录；已有最终结果直接返回，禁止再次审核、调用模型或落库。
4. 以服务端规则版本校验输入：空白、120 个 Unicode 字符上限、个人敏感信息、一般违规与危机表达。
5. 输入拒绝时返回标准 `INPUT_REJECTED` 错误结果，不调用模型、不保存聊天正文；只保留最小化的审计信息。
6. 危机表达时停止日常角色扮演，由服务端返回法务审核的 `CRISIS_REPLY` 安全结果，并按合规要求记录最小审计信息。
7. 正常输入时，从服务端读取固定人设、权威当前场景、已确认历史和允许使用的记忆，组装模型上下文。
8. 审核模型输出；失败时生成审核过的服务端兜底回复。
9. 将已确认的用户消息、服务端回复、规则版本、幂等记录和必要审计以同一事务或可恢复流程落库，再返回结果。

### 8.3 服务端强制校验

`chatReply` 不得信任 App 单独传入的结果，必须自行校验：

- 会话有效；
- `egg_id` 属于当前用户；
- 蛋处于 `HATCHED`；
- 当前权威状态允许聊天；
- `mode=live` 且环境一致；
- `client_message_id` 和 `request_id` 的幂等性；
- 输入长度与内容安全；
- 输出内容安全；
- 返回和落库的数据一致。
- App 请求中的正文以外字段只可作为非权威诊断信息，不能改变安全结论、人设、场景权限或模型上下文。
- `history`、`scene_context`、客户端内容标签和客户端安全结论一律不作为 `chatReply` 的入参契约。

服务端返回 `safety_result="crisis"` 时，必须同时返回已审核的安全文本；App 仅展示该文本和状态，不生成或替换危机文案。

### 8.4 数据最小集

每条消息至少包含：

```json
{
  "message_id": "server-message-id",
  "client_message_id": "stable-client-message-id",
  "egg_id": "egg-id",
  "session_id": "server-chat-session-id",
  "role": "user",
  "text": "消息正文",
  "safety_result": "passed",
  "rule_version": "chat-policy-2026-08-10",
  "fallback_used": false,
  "created_at": "2026-08-10T12:00:00+08:00",
  "mode": "live"
}
```

- `fallback_used` 对用户消息固定为 `false`。
- `rule_version`、`safety_result`、`fallback_used` 和消息可见性均以服务端落库结果为准，App 不得自行补写。
- 安全内部评分、模型提示词、模型密钥和供应商原始响应不得返回 App。
- 对话保存期限须与隐私政策一致；未完成法务确认前不得发布正式聊天。

## 9 · App / 前端需求

### 9.1 P0 App 改造

App 团队负责：

1. 为 trial 和 release 配置不同的 `apiBase`，并在正式环境打开后端能力。
2. 将 staging / production 域名加入微信小程序 request 合法域名。
3. 新增聊天历史读取适配，进入页面时展示真实历史。
4. 用稳定 `client_message_id` 管理每条用户消息。
5. 实现 `pending / sent / failed` 状态和原地重试。
6. 修复失败重试新增重复气泡的问题。
7. 统一请求超时，并在可能时取消失效请求。
8. 对服务端模型兜底回复进行正常展示。
9. 补齐头像、昵称和当前状态。

11. 页面卸载、切后台和重复进入时不更新失效页面、不丢失已经确认的消息。
12. `chatReply` 仅发送 `egg_id`、`message`、`client_message_id`、`request_id` 与运行环境必需字段；不上传 `history`、`scene_context`、内容分类或安全判断。

### 9.5 App 端逐项解决方案

#### 第 1 项 · 修复失败重试重复消息

**当前原因**

发送时先把用户消息加入 `messages`；失败后这条消息仍保留，同时草稿又恢复。再次发送会创建第二条相同用户消息，并把上一条失败消息再次作为历史传给服务端。

**明确方案**

1. 为用户消息建立稳定的 `clientMessageId`，首次发送时生成，重试时复用。
2. 页面消息增加 `status`：`pending`、`sent`、`failed`。
3. 发送失败时不恢复成一条可以再次“新发送”的草稿；原消息就地变为 `failed`。
4. 用户点击失败消息的“重试”后，将同一消息改回 `pending`，不向数组追加新气泡。
5. 请求成功后，用同一 `clientMessageId` 找到原消息，更新为 `sent`，再追加一条服务端回复。
6. App 按 `clientMessageId` 和服务端 `messageId` 双重去重。
7. `pending` 和 `failed` 消息只用于页面展示，不得作为任何服务端模型上下文的一部分；模型历史由服务端从已确认记录读取。

**预计影响文件**

- `miniprogram/pages/chat/chat.js`
- `miniprogram/pages/chat/chat.wxml`
- `miniprogram/pages/chat/chat.wxss`
- 新增或扩展聊天页面行为测试

**验收标准**

- 连续失败并重试 3 次，页面始终只有一个用户气泡。
- 3 次重试使用相同 `clientMessageId`。
- 失败消息不进入下一次模型历史。
- 成功后原气泡变为已发送，只增加一条蛋宝宝回复。

**行动门槛**

#### 第 2 项 · 统一超时、取消和失效回调

**当前原因**

聊天适配层 8 秒后返回超时，但底层网络请求允许继续到 15 秒；计时器和旧请求没有形成统一取消关系。用户离开页面或重试后，旧请求仍可能继续运行。

**明确方案**

1. 只保留一套聊天请求超时配置，建议默认 10 秒，联调后可调整。
2. 每次发送保存请求对象和页面请求令牌。
3. 超时、页面卸载或同一消息重试前，调用可用的 `abort()`。
4. 回调返回时同时核对页面仍活跃、请求令牌仍有效、消息仍为 `pending`。
5. 清理已结束请求的超时计时器，避免成功后计时器继续存在。
6. 旧请求晚到时不得新增回复或改变当前消息状态。

**预计影响文件**

- `miniprogram/services/chat-service.js`
- `miniprogram/services/cloud-api.js`
- `miniprogram/pages/chat/chat.js`
- 聊天超时与页面卸载测试

**验收标准**

- 成功响应后不再触发超时逻辑。
- 页面退出后，旧响应不更新页面。
- 同一消息重试后，旧响应不产生第二条回复。
- 等待气泡在成功、失败、超时和退出时都正确消失。

#### 第 3 项 · 服务端规则校验与最小请求

**当前原因**

输入规则和模型上下文曾分散在页面与服务适配层，用户可绕过 App，也可能将过期场景或不完整历史传给服务端；代码中另有破壳前的 50 字历史文本互动逻辑，不能视为破壳后完整文字聊天或任何语音聊天入口，容易造成口径混淆。

**明确方案**

1. 服务端 `chatReply` 统一校验空白、120 字长度、敏感个人信息、一般违规和危机表达。
2. App 不设置输入长度或关键词拦截，且请求只发送 `egg_id`、原始 `message`、`client_message_id` 和 `request_id`。
   - App 可以将发送按钮在空白/纯空格草稿时设为不可点击，防止用户误触；这只是页面交互，不是内容规则。服务端仍必须拒绝任何绕过页面或直接到达接口的空白输入。
3. 服务端自行读取当前状态、蛋宝宝人设和已确认聊天历史；App 不上传 `history` 或 `scene_context`。
4. 服务端拒绝时返回标准错误码和审核后的用户提示；不得调用模型或落聊天正文。
5. App 收到输入拒绝后移除临时气泡、恢复草稿，展示服务端提示；不提供“重试”按钮。
6. 危机表达由服务端直接返回已审核的安全结果，App 只展示。

**预计影响文件**

- `miniprogram/pages/chat/chat.js`
- `miniprogram/pages/chat/chat.wxml`
- `miniprogram/services/chat-service.js`
- `miniprogram/services/post-hatch-companion.js`
- `miniprogram/services/tests/chat-input-validation.test.js`

**验收标准**

- 空白、120/121 字、手机号/身份证号/邮箱和一般违规均到达服务端。
- 服务端拒绝后，临时消息气泡被移除，原草稿恢复，页面展示服务端提示。
- App 不保存或自行判断上述输入的安全结果。
- `chatReply` 请求中没有 `history`、`scene_context` 或任何本地安全标签；服务端仍能按权威数据生成连续回复。
- 危机表达完整交给服务端；服务端应停止日常角色扮演并返回已审核的安全结果。

## 10 · 前后端接口契约

### 10.1 获取历史 `getChatHistory`

请求示例：

```json
{
  "egg_id": "egg-id",
  "cursor": "",
  "limit": 20,
  "mode": "live",
  "session_id": "auth-session-id",
  "request_id": "request-id",
  "client_version": "3.7.0-ordinary"
}
```

成功响应：

```json
{
  "success": true,
  "request_id": "request-id",
  "server_time": "2026-08-10T12:00:00+08:00",
  "data": {
    "mode": "live",
    "messages": [],
    "next_cursor": "",
    "has_more": false
  },
  "error": null
}
```

`messages` 内每条已确认记录必须提供 `message_id`、`role`、`text`、`created_at`；用户消息还必须提供对应的 `client_message_id`，用于 App 在回到前台后确认未送达消息的真实状态。首次请求返回最近 20 条，列表固定按时间由旧到新排序；后续请求只返回更早记录。`next_cursor` 必须是不透明且稳定的服务端游标，不能因新消息写入而造成漏读或重复。

### 10.2 发送消息 `chatReply`

请求示例：

```json
{
  "egg_id": "egg-id",
  "client_message_id": "client-message-id",
  "message": "今天过得怎么样？",
  "mode": "live",
  "session_id": "auth-session-id",
  "request_id": "stable-idempotency-key",
  "client_version": "3.7.0-ordinary"
}
```

成功响应：

```json
{
  "success": true,
  "request_id": "stable-idempotency-key",
  "server_time": "2026-08-10T12:00:01+08:00",
  "data": {
    "mode": "live",
    "result_type": "REPLY",
    "session_id": "chat-session-id",
    "user_message": {
      "message_id": "message-user-id",
      "client_message_id": "client-message-id",
      "role": "user",
      "text": "今天过得怎么样？",
      "created_at": "2026-08-10T12:00:00+08:00"
    },
    "reply": {
      "message_id": "message-reply-id",
      "role": "assistant",
      "text": "这一页刚好讲到月亮，我看得有点慢。",
      "safety_result": "passed",
      "fallback_used": false,
      "created_at": "2026-08-10T12:00:01+08:00"
    }
  },
  "error": null
}
```

危机安全结果也是成功响应，但服务端必须明确标识结果类型：

```json
{
  "success": true,
  "request_id": "stable-idempotency-key",
  "data": {
    "mode": "live",
    "result_type": "CRISIS_REPLY",
    "user_message": { "message_id": "message-user-id", "role": "user", "text": "用户原始消息" },
    "reply": {
      "message_id": "message-reply-id",
      "role": "assistant",
      "text": "法务审核后的安全结果",
      "safety_result": "crisis",
      "fallback_used": false
    }
  },
  "error": null
}
```

输入拒绝必须使用失败响应，不返回或落库用户消息与蛋宝宝回复：

```json
{
  "success": false,
  "request_id": "stable-idempotency-key",
  "data": { "result_type": "INPUT_REJECTED" },
  "error": {
    "code": "INPUT_TOO_LONG",
    "message": "服务端审核后的用户提示"
  }
}
```

接口约束：`history`、`scene_context`、`safety_result`、内容标签和任何客户端安全结论均不得由 App 传入。服务端使用当前会话、`egg_id` 与已确认记录取得全部上下文。

### 10.3 结果类型

| `result_type` | 是否成功响应 | App 动作 |
| --- | --- | --- |
| `REPLY` | 是 | 确认用户临时气泡并展示服务端回复 |
| `CRISIS_REPLY` | 是 | 确认用户临时气泡并原样展示服务端安全文本 |
| `INPUT_REJECTED` | 否 | 移除临时气泡、恢复草稿并展示服务端提示 |

### 10.4 错误码

| 错误码 | 含义 | App 行为 |
| --- | --- | --- |
| `AUTH_REQUIRED` | 未登录或会话失效 | 引导重新登录，不继续重试聊天 |
| `EGG_FORBIDDEN` | 蛋不属于当前用户 | 退出聊天并提示数据异常 |
| `NOT_HATCHED` | 尚未破壳 | 返回首页并提示破壳后开放 |
| `TALK_NOT_AVAILABLE` | 当前不允许聊天 | 切换为不可聊天状态页，移除未确认临时气泡、保留草稿，并提供返回生活空间 |
| `INPUT_EMPTY` | 输入为空或纯空白 | 移除临时消息、恢复草稿并展示服务端提示 |
| `INPUT_TOO_LONG` | 输入超长 | 移除临时消息、恢复草稿并展示服务端提示 |
| `CONTENT_REJECTED` | 一般内容安全拒绝 | 移除临时消息、恢复草稿并展示服务端提示 |
| `SENSITIVE_INFO` | 包含敏感个人信息 | 移除临时消息、恢复草稿并展示服务端提示 |
| `RATE_LIMITED` | 触发服务护栏 | 轻量提示稍后再试，不展示次数资源 |
| `SERVICE_UNAVAILABLE` | 服务异常 | 标记发送失败，允许原地重试 |
| `REQUEST_TIMEOUT` | 请求超时 | 标记发送失败，复用原 ID 重试 |

模型供应商异常不直接返回给 App，应由服务端转换为审核过的兜底成功响应。

## 11 · 内容安全与隐私

- 用户输入和模型输出必须先审核、后展示、后落库；用户消息与回复应在同一业务事务或可恢复流程中保持一致。
- 破壳后聊天的输入校验、内容安全、危机判断、回复和审计必须完全以服务端为准；App 仅负责转发和展示服务端结果。
- App 不得在日志、埋点、缓存或请求字段中保存、推导或上报内容风险标签、危机标签、模型上下文、人设提示词或规则版本。
- 不主动索取住址、学校、联系方式或证件信息。
- 对话正文不得写入 analytics、广告系统、用户画像、蛋宝宝性格生成或内容推荐标签。
- 埋点只记录消息长度、结果类型、耗时、错误码和场景 ID，不记录正文。
- 用户注销时，聊天记录按账户删除流程处理并保留必要审计证明。
- 服务端使用的危机安全结果、保留期限、未成年人策略和具体官方求助资源必须在发布前经法务确认。

## 12 · 埋点要求

按技术接口规格统一使用：

| 事件 | 触发时机 | 禁止字段 |
| --- | --- | --- |
| `chat_open` | 聊天页成功加载 | 消息正文 |
| `chat_message_sent` | 服务端确认用户消息成功 | 消息正文、个人信息 |
| `chat_reply` | 安全回复成功展示 | 回复正文、模型提示词 |
| `chat_session_end` | 用户离开聊天页 | 消息正文 |

允许属性包括：`scene_id`、`msg_len`、`latency_ms`、`fallback_used`、`result`、`error_code`。当前代码中的 `chat_reply_result` 应在联调时与技术规格统一，避免同一指标使用两个事件名。
