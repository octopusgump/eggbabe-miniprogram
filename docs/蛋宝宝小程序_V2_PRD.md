## 1 · 产品定位与合规边界

### 1.1 一句话定位

> 一只需要你亲手孵化的蛋宝宝——它从一枚实体蛋破壳，成为你独一无二的收藏，此后每天都有自己的状态，愿意和你说话。

### 1.2 产品形态

蛋宝宝是**实体潮玩 + 微信小程序陪伴**的组合：用户在小程序外购买实体蛋（机械装置），用激活码在小程序内绑定，孵化到预设破壳日后，物理装置打开、小程序承接生成数字破壳收藏卡，进入长期陪伴与对话。

### 1.3 合规定位（给王敏 / 张棣对齐）

首发只做微信小程序，合规打法锁定如下，开发按此守边界：

| 维度 | 锁定结论 |
|------|---------|
| 平台 | 仅微信小程序，不做 H5 |
| 变现 | **小程序内无任何虚拟支付 / 内购 / 氪金**；购买发生在站外，小程序只负责“输入激活码 → 绑定实体蛋”。普通版不提供虚拟货币、道具商店、付费或免费虚拟商品经济。 |
| 备案主体 | **必须为中国大陆企业主体**；软著、著作权自我声明、ICP 备案均挂此主体 |
| 类目与备案 | 当前按“IP 陪伴 / 对话 / 实体设备服务”普通小程序准备材料，但**平台按实际功能而非自称判断类目**。若微信或主管部门认定为网络游戏，应立即停止普通版上线该功能，转入独立游戏立项、平台游戏类目和出版审批流程；“不付费即可免版号”不作为本项目结论。 |
| 时间源 | **服务器时间，北京时间 UTC+8 单一时区**（见 §11） |

> **合规红线（三条，不可破）：**
> 1. 小程序内不出现任何付费点（卡片、加速、款式、外观一律不售卖）；
> 2. 破壳收藏卡的"限定"属性只表达来源/批次，**不承诺价格、收益或升值**；
> 3. 备案主体、游戏名称在提审各阶段保持一致，改名/换主体会重置备案时效。

### 1.8 从普通小程序到游戏小程序的阶段路线

| 阶段 | 产品状态 | 准入条件 | 交付物 |
|---|---|---|---|
| P0 合规收敛（现在） | 冻结所有 🟥 功能 | 生产包与 demo 隔离；完成路由、接口、埋点和文案扫描 | 普通版白名单、构建开关、提审检查表 |
| P1 普通陪伴版 | 互动 + 对话 + 情绪价值 + 实体蛋服务 | 微信服务类目预审通过；隐私、内容安全、APP 备案等就绪 | 可提审普通小程序 |
| P2 陪伴价值验证 | 不增加游戏系统，观察真实使用 | 用对话回访、有效互动、设备绑定与满意度验证价值 | 8–12 周验证报告与游戏立项决策 |
| G0 独立游戏立项 | 建立单独游戏产品线 | 企业主体、名称 / 著作权、出版单位、运营资质、平台游戏账号 / 类目及防沉迷方案完成核验 | 独立游戏 PRD、合规矩阵、预算和排期 |
| G1 出版与平台审批 | 仅内测申报版本，不公开运营 | 按主管部门与出版单位要求申报，取得出版审批及平台要求的全部资质 | 获批版本、出版物号 / 批文、平台审核记录 |
| G2 游戏版上线 | 只发布获批范围内玩法 | 版本、名称、运营主体与获批材料一致；实名、防沉迷、内容与支付持续合规 | 独立游戏小程序上线与变更控制 |

**迁移原则**：普通小程序走到游戏小程序不是“在原账号里打开功能开关”。在微信给出可留档结论前，本项目按“独立账号 / 类目、独立发布包、独立后端域与数据边界”规划；普通版用户数据是否能迁移，由隐私授权、平台规则和获批范围另行评估。

## 2 · 陪伴体验原则：四大支柱

> 🟨 **普通版改写**：本节只指导陪伴体验，不再以“内部按游戏设计、对外按工具呈现”为原则。产品定位、页面文案、后台逻辑与实际上线功能必须一致。

V2 所有陪伴体验决策服务于这四根支柱。新增任何能力先问“它是否增强自由互动、对话或情绪价值”，答不上来就砍。四支柱与 MVP 既有体验关键词一一对应：

| 支柱 | 含义 | 对应 MVP 关键词 | 落地机制 |
|------|------|--------------|---------|
| **零操作压力** | 不惩罚、不逼签到；用户想来再来 | 参与 | 不推每日动作、不设完成态、不做强制登录 |
| **自然变化的回应** | 新鲜感来自内容变化，不来自奖励概率 | 惊喜 | 动画与对话可轮换；不掉落资源、不设概率奖励 |
| **情感投射** | 养的是"我的蛋"，不是数值 | 稀缺 · 活人感 | 激活码稀缺；专属命名；每日一句活人感状态 |
| **纪念与身份** | 独一无二、可留存、可分享 | 纪念 | 实体蛋身份档案；初始主人 + 破壳日记录，不设卡池、稀有度或集齐 |

## 3 · 产品主线与 MVP 范围

### 3.1 产品主线

**扫码进入 → 微信授权 → 输入激活码绑定实体蛋宝宝 → 自由触摸 / 装点 / 说话 → 到达服务端预设破壳日 → 物理装置打开 → 小程序生成一份纪念收藏卡 → 查看定性状态与开启对话**

本阶段验证三个核心问题：用户能否顺利绑定和使用实体蛋；自由互动与一对一对话是否能提供情绪价值；破壳纪念与后续陪伴是否让用户自愿回访。

### 3.2 本阶段要做

| 模块 | 目标 |
|---|---|
| 二维码进入 | 扫码快速打开小程序 |
| 微信授权 | 基础用户注册与身份识别 |
| 激活码 | 控制新增节奏；支持企业 / 个人 / 购买激活码 |
| 添加蛋宝宝 | 输入激活码获得蛋宝宝 |
| 自由陪伴互动 | 触摸、说话、看窗外、画记号；无任务、无完成态、无数值增长 |
| 蛋的交互 | 触摸蛋获得即时反馈 |
| ~~露珠货币~~ | 🟥 普通版停用；点击只提供即时情绪反馈 |
| ~~商店与背包~~ | 🟥 普通版停用；颜色、贴纸、手绘作为免费创作能力 |
| 收藏卡 | 🟨 用户侧统一称“收藏卡”，定位为一蛋一份的纪念档案；无卡池、稀有度、掉落、集齐或交易 |
| 每日状态 | 每天最多一句活人感状态文案 |
| 文字对话入口 | 破壳后保留对话入口（语音后续版本） |

### 3.3 本阶段暂不做

## 4 · 用户完整流程

### 4.1 主流程

1. 扫描小程序二维码 → 打开小程序
2. 完成微信授权登录
3. 输入激活码
4. 系统校验：账号是否未绑定蛋宝宝 + 激活码是否有效
5. 校验通过 → 绑定 1 只蛋宝宝 → 进入主界面
6. 用户按意愿触摸、装点蛋壳或说话，蛋宝宝给出即时、非数值化回应
7. 到达机械装置预设时间 → 物理装置打开，用户先看到实体本体
8. 进入小程序承接破壳结果 → 生成一蛋一份的纪念收藏卡
9. 保存 / 分享纪念收藏卡
10. 进入破壳后档案与对话体验
11. 系统按需生成定性状态与对话内容，用户自愿回访

### 4.2 单蛋版本基础规则

当前版本一个账号**最多绑定 1 只蛋宝宝**。

> 🟦 **多蛋为未来游戏版方向**：普通版维持单蛋，暂不为集卡、复购或养成开放多蛋入口；后续是否开放须按 §1.8 重新评估。

- 未绑定账号首页展示"领取 / 添加蛋宝宝"空状态
- 输入激活码成功后绑定 1 只
- 已绑定账号再次使用激活码：不新增第二只，且**不消耗**新输入的激活码
- 当前版本不提供列表、切换、多只同时孵化
- 每只蛋拥有独立的服务端生命周期阶段、定性状态、纪念收藏卡和对话记录，不拥有互动成长进度

**前端测试必须覆盖两态**：未添加蛋（空状态 + 添加入口）、已添加 1 个蛋（孵化 / 破壳后主界面）。

### 4.3 核心体验关键词

专属（实体蛋与账号绑定）· 参与（自由触摸与创作）· 惊喜（实体破壳承接）· 纪念（一蛋一份收藏卡）· 活人感（有状态、愿意回应和对话）。

## 5 · 激活码系统

### 5.1 设计目的

控制新增节奏，承接站外购买、运营发放与用户邀请；控制早期 token / 宠物生成 / AI 对话成本；过滤低意愿用户；追踪来源与传播链路；通过个人激活码形成轻量裂变。

### 5.2 激活码类型

| 类型 | 创建方式 | 使用次数 | 数量规则 | 主要用途 |
|---|---|---:|---|---|
| 企业激活码 | 后台创建 | 多次 | 后台设上限 | 活动、品牌合作、内测、定向投放 |
| 用户个人激活码 | 添加第一只蛋后系统生成 | 1 次 | 每账号 5 个 | 邀请朋友、私域传播 |
| 购买激活码 | 用户购买后生成 | 1 次 | 每次购买生成对应码 | 绑定指定原型的蛋宝宝 |

### 5.3 添加页设计规则（唯一入口 = 手动输入）

- 不展示第二种添加方式 tab、不展示二维码扫描框、不展示相机入口
- 页面只保留一个输入框 + 提交按钮
- 占位文案统一"请输入激活码"；页面文案只用"激活码"，不用其他码类命名

### 5.4 激活码关键配置

可添加原型（锦鲤 / 玉兔等）· 预设破壳日 / 打开时间 · 来源类型（企业 / 个人邀请 / 购买）· 可用次数或是否已使用 · 是否限定批次 / 活动来源。

### 5.5 购买添加规则

- MVP 不做小程序内购买 / 支付；购买发生在站外
- 小程序只负责"输入激活码 → 添加蛋宝宝"
- 已绑定账号再用任何激活码：不新增、不消耗
- 用户购买 / 添加时**已知原型**（锦鲤 / 玉兔），**破壳前不知具体款式**；款式随破壳收藏卡揭晓
- MVP 页面不展示款式概率、不承诺具体款式结果

### 5.6 企业激活码规则

后台支持：创建 / 设上限 / 查已用次数 / 改上限 / 暂停启用 / 查带来的注册用户数。

- 一码多用户使用；每成功添加 1 只消耗 1 次额度
- 仅未绑定账号成功绑定后才消耗额度
- 达上限后不可用；不绑定具体邀请人，只记来源渠道
- 可配置默认原型与预设破壳日

### 5.7 用户个人激活码规则

添加第一只蛋后系统自动生成 5 个。

- 每账号仅 5 个，每个仅用 1 次，用后置"已使用"，不可重复、不可自增
- 被邀请账号成功绑定后计一次有效邀请，个人码才置"已使用"
- 原型与预设破壳日由后台默认规则决定
- MVP 只做“邀请朋友进入”和实体蛋受邀关系追溯，不做积分 / 排行 / 兑换；~~邀请奖励为露珠~~ **🟥 v2.27 普通版不发放任何虚拟资源、道具、成长值或抽奖机会**

### 5.8 用户使用流程

扫码 → 授权 → 选"添加蛋宝宝" → 输入激活码 → 校验账号是否已绑定 → 已绑定则提示只能绑 1 只且不消耗 → 未绑定则校验激活码 → 通过则绑定 1 只 → 同步激活码状态 → 蛋进入"待激活" → 展示原型（不展示款式）→ 播放**添加成功惊喜反馈** → 自动进入孵化首页。

**添加成功惊喜反馈要求**：精致、有期待感，非普通 toast；约 1 秒、不阻塞；只围绕"原型 + 蛋形状态"表达（如"你获得了一只锦鲤蛋宝宝"）；**不展示款式 / 纹理 / 编号等任何暗示款式的信息**——这是"获得蛋"的期待时刻，不是"开奖"时刻。

### 5.9 异常情况

| 场景 | 页面提示 |
|---|---|
| 激活码不存在 | 激活码无效，请检查后重试 |
| 个人激活码已被使用 | 该激活码已被使用 |
| 企业激活码达上限 | 该激活码名额已满 |
| 购买激活码已被使用 | 该蛋宝宝已添加 |
| 用户已用过同一码 | 该激活码已添加过蛋宝宝 |
| 激活码被后台停用 | 该激活码暂不可用 |
| 账号已绑定蛋宝宝 | 当前版本一个账号只能绑定 1 只蛋宝宝 |

### 5.10 数据记录

激活码 ID · 类型 · 使用用户 ID · 邀请人 ID（仅个人码）· 来源渠道（仅企业码）· 外部订单号（仅购买码，可空）· 原型 · 款式（破壳后生成，破壳前空）· 使用时间 · 是否成功添加。

## 6 · 孵化机制

> 🟥 **普通版冲突标记（v2.27）**：本节的“孵化进度、动作贡献、每日有效次数、完成度阈值、性格 / 卡面随行为成长”均不得进入普通版生产逻辑。实体装置的破壳日与售后状态可以保留；自由互动、蛋壳绘图和身体回应按 🟩 保留，但不得影响数值、权益、内容解锁或破壳结果。以下数值仅作为历史方案存档，未来只能在独立游戏版重新审批后采用。

### 6.1 设计目的与闭环

让用户在破壳前先与蛋建立关系。MVP 只做轻量闭环：

**普通版新闭环：添加蛋宝宝 → 自由互动或说话 → 获得即时身体 / 文字回应 → 等待实体装置按服务端日期破壳**

目标：让用户不"领完即走"；收集初始偏好；建立专属感；提供愿意反复打开的蛋形观察空间；为破壳后性格 / 外观 / 对话提供基础数据。

### 6.2 双轨孵化机制

避免小程序进度与物理装置打开时间冲突：

| 机制 | 受用户互动影响 | 作用 |
|---|---|---|
| 破壳日 | 否 | 决定物理装置何时打开 |
| 孵化进度 | 是 | 决定反馈、性格倾向、收藏卡内容丰富度 |
| 破壳收藏卡 | 部分 | 款式不提前暴露；性格 / 文案 / 标签可受孵化行为影响 |

规则：进度 100% 也不提前改变物理打开时间；进度 100% 未到破壳日 → 首页"准备好了，等待破壳日"；进度低不惩罚、不阻止按时打开；高进度让收藏卡更完整、更有"被养出来"感；破壳日范围 3–10 天，**MVP 默认 7 天**；用户不可手改破壳日 / 倒计时。

**孵化完成度归一化（已定）**：完成度标签（完整 / 轻量，写入收藏卡 §8.3）按该蛋周期的**理论最大进度**计算——完成度 = 实际进度 ÷ 该周期可获得上限，**≥90% 记「完整孵化」**。理由：短周期蛋数学上到不了 100%（例：每日动作上限 15% 时，3 天蛋上限 = 40% + 45% = 85%；具体数值随动作增减变化——§6.4 新增"跟我说说话"后每日上限为 20%——归一化规则本身不变），做满所有动作的用户不应永久标"轻量孵化"。

### 6.3 孵化动作设计原则

像照顾蛋而非填表 · 每个动作有即时反馈 · 每个动作收集一点有效信息 · 不制造每日必做感 · 视觉增强陪伴但不增加前台数值压力。首页常驻自由陪伴入口，用户想来时自行选择，不要求每天完成，也不显示连续签到、任务编号、完成打勾或奖励比例。

### 6.4 孵化互动机制（后台规则）

> 下表的进度贡献只供内部游戏机制与服务端迭代使用。**用户界面不得展示单次动作的 `+5% / +20%`、每日上限或“完成任务”提示**；前端只呈现蛋宝宝的身体反应和第一人称反馈。

| 孵化动作 | 进度贡献 | 类型 | 用户动作 | 产品定义 |
|---|---:|---|---|---|
| 给蛋宝宝起昵称 | +20% | 输入型 | 输入 ≤10 字昵称 | 建立专属感 |
| 贴贴蛋宝宝 | +5% / 日 | 长按型 | 长按蛋壳 1.5 秒 | 最简动作制造亲密 |
| 告诉我一个愿望 | +5% / 日 | 选项型 | 选 1 个愿望 | 收集期待与情绪偏好 |
| 教我一件小事 | +5% / 日 | 选项型 | 选择想教的一件事 | 收集期望的性格方向 |
| 蛋壳绘图 | +20% | 创作型 | 选色、图样 / 贴纸、手绘蛋壳 | 提升仪式感与专属感 |
| 跟我说说话 | +5% / 日 | 输入型 | 给蛋说一句话（≤50 字） | WAIC 新增：满足"多讲讲话"的参与感；话语沉淀为语料与偏好 |

**动作要点**（详规见 MVP 原文，此处保留规则骨架）：
- 起昵称·入口（v2.21）：**进入小程序时弹命名弹窗**（bottom-sheet，§12.4）——绑定成功后首次进入必弹；提供「暂不命名」可跳过（守支柱 1，不强迫）；未命名期间每日首次进入轻弹一次提醒，命名后不再弹
- 起昵称·规则：≤10 字，中英数，禁空、敏感词拦截（内容安全检测，§10.6）；可改名，**每天最多改 1 次**（服务端按北京时间日界判定，§11.1）；仅首次命名提升进度（+20%）；改名同步更新收藏卡标题（§8.9.6）
- 贴贴：每日有效 1 次，中途松手不算，重复只给动画反馈
- 今日许愿 / 蛋前教育：每日更新 1 题，每日提交 1 次首次提升进度；选择记为性格偏好
- 蛋壳绘图：首版支持柔和蛋壳色、少量预设图样 / 贴纸和单笔刷手绘；用 Canvas 合成并保存，完整规则见 §6.4.1。首次保存的内部进度贡献由后台判定，前端不显示比例。
- 跟我说说话：**输入框常驻首页**，随时可说；每日首次提交的内部贡献由后台判定，后续输入仍有反馈与落库；前端不公开贡献比例；内容过内容安全检测（§10.6）；只影响内部孵化进度与偏好沉淀，**不改变破壳日**。
- 跟我说说话·反馈形态（v2.20）：**孵化期不做每次文字回答**——蛋还没破壳，不该像聊天机器人。输入后蛋用"身体反应"回应，从反馈池随机一种：轻轻晃动 / 开心大晃 / 壳身发光 / 颜色微微变一下 / 壳内咚咚两声，可配合手机短震动（`wx.vibrateShort`）；**低概率（约 1/5）**附一句第一人称气泡短文案（素材取自原孵化期文案池，§9.6）。破壳前**不接大模型、不生成对话回复**（省成本 + 保神秘感）；用户说的话全部落库为语料与偏好，破壳后可被引用（如"你以前跟我说过…"，增强惊喜）

> 许愿 / 教育的题库与选项文案沿用 MVP v0.1 原文案池，V2 不改（人称须按 §9.6 硬规则改写为第一人称）。蛋壳绘图改按 §6.4.1 的首版范围执行，不再沿用旧“颜色 / 纹理预设”限制。

#### 6.4.1 蛋壳绘图（首版）

**产品目标**：让用户装点自己的蛋宝宝，同时保持现有蛋体的光滑材质、高光和立体感。绘制结果是蛋壳表面装饰，不改变蛋宝宝原型、破壳款式、孵化数值或破壳时间。

**三层 Canvas 架构**：

| 层级 | 内容 | 渲染规则 |
|---|---|---|
| 底层 · 真实视觉母版蛋 | 蛋形、柔和高光、青绿色体积渐变、底部暖阴影 | 直接使用 `miniprogram/assets/scenes/incubation/webp/egg_base_day.webp` 的原始 RGB + Alpha；不得用人工中性渐变覆盖成扁平色块 |
| 中层 · 用户颜色 | 6–8 种柔和蛋壳颜色 | 以半透明混色覆盖母版主体；保留母版高光、边缘明暗和半透明质感 |
| 上层 · 装饰画布 | 预设图样、贴纸、用户手绘轨迹 | 全部裁切在蛋形透明轮廓内；不得绘制到背景、孵化窝或靠枕 |

**场景阴影独立**：首页窝垫接触阴影不属于上述三层，也不得合成进母版蛋。阴影继续由前端独立渲染，并随呼吸、轻触、长按和说话动作实时变化；换色、绘图或擦除均不影响阴影。

**真实视觉母版蛋要求（v2.26）**：`egg_base_day.webp` 是最终视觉母版，不再只作为 Alpha 轮廓。Canvas 必须原样保留它的蛋体轮廓、左上柔和椭圆高光、青绿色体积渐变、侧面与底部暖阴影、透明背景及当前底部锚点；不得用中性白渐变重绘其 RGB，也不得额外画一个覆盖原高光的人工高光。母版不带花纹、文字或地面投影，窝垫接触阴影仍由场景层独立负责。

**首版功能范围**：

| 功能 | 首版规则 |
|---|---|
| 蛋壳颜色 | 提供 6–8 种低饱和柔和颜色；候选可含奶油白、薄荷绿、雾蓝、淡粉、杏黄、浅紫和暖灰 |
| 预设图样 / 贴纸 | 首批只包含星星、爱心、叶子等少量图形；同一素材可作为重复图样或单个贴纸使用 |
| 圆形画笔 | 只有 1 支圆润 / 圆形画笔；仅 1 种固定笔触粗细，不提供硬边、纹理笔刷或粗细调节 |
| 橡皮擦 | 按手指轨迹擦除上层装饰内容，可持续擦到上层完全为空；不得擦除真实视觉母版、高光或颜色层 |
| 撤销 | 撤销最近一次上层编辑操作，包括手绘、擦除、添加 / 移动 / 删除图样或贴纸 |
| 清空 | 一次清空全部上层装饰内容，回到当前所选蛋壳颜色；不删除真实视觉母版和颜色层 |
| 保存 | 保存当前颜色、图样 / 贴纸与手绘轨迹；返回首页后立即显示同一结果 |
| 图片上传 | 首版不开放相册上传、拍照导入或外部图片粘贴，减少内容安全与画面失控问题 |

**Canvas 合成顺序（v2.26）**：先直接绘制 `egg_base_day.webp` 的原始 RGB + Alpha；用户换色时再以母版 Alpha 为范围叠加不高于 32% 的半透明颜色；最后绘制图样、贴纸和手绘轨迹。颜色层不得替换母版 RGB，高光与体积阴影必须始终可见。

**绘图交互**：手指落下开始路径，移动时用圆角线段连续补点，抬手形成一次可撤销操作。画笔与橡皮擦共用固定粗细；橡皮擦只对上层装饰画布使用 `destination-out`，不得破坏母版与颜色层。

**坐标规则**：图样、贴纸和笔迹使用相对蛋体画布的归一化坐标保存，不使用页面绝对像素。不同手机尺寸、首页蛋体缩放和导出预览必须得到一致位置。

**保存与内容边界**：绘图只用于当前蛋宝宝的孵化期外观，首版不提供公共作品广场、公开分享或用户图片上传。正式数据持久化与跨设备同步由 CTO 后端按 §18.2 实现；demo 数据不得进入 live 记录。

**最新交互结论（2026-07-20）**：孵化修炼手册及“今天陪我做的事”的任务表达全部取消。首页改为「一起待一会儿」自由陪伴区，常驻 8 个入口：摸摸我、跟我说句话、安静陪我一会儿、一起看看窗外、告诉我一个愿望、教我一件小事、画一个小记号、说一句秘密暗号。入口无序号、无完成态、无奖励数字，用户不必每天参与。

## 7 · 蛋的交互（孵化期主界面）

> 🟩 **普通版保留边界（v2.27）**：保留真实蛋体、呼吸、触摸回弹、光泽、窝垫阴影、轻震动、自由陪伴入口和对话；移除孵化百分比、露珠余额、点击奖励、每日上限提示及任何“完成 / 获得 / 再点”的引导。

### 7.1 主界面闭环

**看到蛋 → 自由选择一种陪伴 → 蛋或房间回应 → 想停就停、想来再来**

让用户在破壳前感到“这颗蛋是活的”，同时避免签到、打卡和每日任务压力。普通版后台也不记录由互动累积的成长进度；点击只产生即时动画、触觉和情绪回应。

| 已添加 1 个蛋 | 账号已绑定 | 四季昼夜房间 + 蛋宝宝主体 + 定性状态文案 + 内容轮换反馈 + 8 个自由陪伴入口；不显示孵化百分比或货币余额 |

**孵化场景（NEW，v2.20）**：孵化首页增加一个固定背景场景——**家中的小房间**（温暖安静，蛋被放在房间里照顾的氛围）。规则：

- 全体用户统一同一个孵化房间，**不可选择、不可更换**；与破壳后六场景体系（§10.2）无关；房间本身不设置收集热点、不掉收藏卡，8 个陪伴入口属于首页表现层

- **季节**：按节气划分四季（立春 / 立夏 / 立秋 / 立冬为界，接 §11.3 节令配置表），切换季节底图（窗外景色 + 室内小物随季节变化）

首页的 U 形窝垫接触阴影继续作为独立场景层实时渲染，随呼吸和互动变化，不参与蛋壳合成，也不受换色、清空或橡皮擦影响。不得把房间背景、窝垫或其阴影烘焙进用户蛋壳图片。

保存配置未取得、解析失败或旧数据不兼容时，首页直接回退到 `egg_base_day.webp` 真实视觉母版，不随机生成颜色或图样。昼夜与天气只调整场景光线和整体色温，不覆盖用户已保存的蛋壳装饰。

**孵化首页不展示"今日状态 / 今日心情"模块**（变更，见 §9.1）：心情标签、状态一句话等每日状态相关信息全部不出现在孵化期首页。此处"状态文案"仅指蛋的引导 / 气泡文案（第一人称，如"我还在睡觉，叫醒我吧"），与每日状态系统（§9）无关。

### 7.3 孵化展示动画（独立设计项）

进入孵化首页可先播一段短动画，再进入稳定蛋形展示。动画可表现呼吸、轻微晃动、发光、壳内动静、能量聚合，在孵化场景（小房间，§7.2）内进行；**不能引导选场景、不能暗示破壳后六场景、不能提前暴露破壳款式**。保留"左侧一段动画 → 右侧蛋形孵化页"流程，后续由设计师补特效。

### 7.4 蛋的状态展示

| 状态 | 触发 | 表现 |
|---|---|---|
| 待激活 | 刚绑定、尚未进入稳定服务状态 | 蛋安静，提示“我在这里”；不要求完成动作 |
| 孵化中 | 服务端生命周期处于孵化阶段 | 蛋形 + 第一人称定性文案 + 轻微动态；无进度数值 |
| 准备见面 | 服务端判断已接近破壳日 | 蛋形 + “我准备好啦，就快见面了”；无进度条或完成条件 |

### 7.5 交互 1 · 轻触蛋宝宝

轻点（~0.1s）→ 蛋左右晃动 1 次 + **点击处迸出小撒花 / 小星星粒子特效**（每次点击都触发、可连点，约 0.5s 消散）+ 轮换气泡文案。基础互动动画可无限触发；文案 2 秒内最多 1 条；粒子每次必出但同屏上限 3 组（防性能）；**轻点不触发手机震动**（震动属于长按，§7.6）；`prefers-reduced-motion` 时粒子降级为单颗星星淡出；**轻点和长按均不产生孵化进度、奖励或权益**。

> 🟥 **普通版停用（v2.27）**：以下“点击获得露珠”整段为历史 / 未来游戏版规格。普通版生产构建不得创建余额、阈值、每日计数、飞行动效、`+1` 文案或点击货币请求；轻触永远只执行上一段的即时情绪反馈。

**点击获得露珠（v2.25 历史规格 · 🟦 仅未来游戏版重新审批后评估）**：

1. 服务端以北京时间 UTC+8 计算每日点击获取额度；每位 live 用户每日通过点击蛋宝宝最多获得 **10 个露珠**，跨日由服务端重置，不能依赖手机设备时间。
2. 当日第 1–10 个露珠**全部采用受控惊喜机制**：每获得一个露珠后，服务端为下一个露珠生成一个隐藏的“所需有效点击次数”；达到该次数时固定获得 1 个露珠，不做每次点击相互独立的纯概率判定。
3. 隐藏阈值按露珠序号分段：前段奖励更密集，让用户快速建立获得感；中后段逐渐拉开，制造轻微期待。每个露珠均有明确最大点击次数，**不会无限点不到**。
4. 隐藏阈值由服务端生成并持久化；退出重进、网络重试或更换设备不重新抽取。前端不得写死、推算或展示阈值 / 权重，也不得通过设备时间或本地计数自行发币。
5. 第 10 个露珠到账时，立即显示一次柔和提示：**“今天的 10 个露珠已经收好啦”**。当日后续点击仍保留蛋的晃动、粒子和情绪反馈，但不再发放露珠；同一页面会话内不重复弹出上限提示，避免形成任务压力。
6. “有效点击”由服务端做节流、防重和幂等判定。长按贴贴按 §7.6 处理，不与同一次手势重复发放点击露珠。

**受控惊喜阈值（当前基准）**：

| 露珠序号 | 距上一个露珠所需的有效点击数 | 抽取权重 | 体验目标 |
|---|---|---|---|
| 第 1–3 个 | 1 / 2 次 | 70% / 30% | 开场密集反馈，尽快建立“摸它会有回应”的感受 |
| 第 4–7 个 | 2 / 3 次 | 55% / 45% | 保持稳定节奏，但不形成每次必得的机械预期 |
| 第 8–9 个 | 3 / 4 次 | 40% / 60% | 产生短暂期待，仍保证最多 4 次必得 |
| 第 10 个 | 4 / 5 / 6 次 | 20% / 50% / 30% | 作为当日收尾，最多 6 次必得并触发上限提示 |

- 获得当天全部 10 个点击露珠约需 **21–32 次有效点击**，按上述权重的期望值约为 **26 次**。
- 服务端应按“露珠序号”抽取目标次数，而不是为每次点击重新掷概率；目标次数一旦生成，在该露珠到账前保持不变。
- 运营可以灰度调整各段权重，但不得突破表中最大点击次数；如需改变点击次数区间或每日上限，须重新评审任务压力与经济平衡。

**到账视觉反馈（每次获得都必须出现）**：

- 点击位置生成一颗小露珠，短暂放大后沿柔和弧线飞向右上角露珠余额；同时在蛋旁显示轻量 `+1 露珠`，余额数字完成一次小幅弹跳并更新。
- 蛋的基础晃动与粒子在触摸后立即响应；露珠飞行动效和余额增加只在服务端确认 `awarded = true` 后发生，禁止网络失败时先加余额造成“假到账”。
- 尚未达到隐藏阈值时只播放原有蛋互动，不出现“未获得”“再点一次”“还差几次”等催促文案；弱动效模式下将飞行动效降级为露珠淡入 + 余额数字更新。
- 前端请求须带唯一点击请求 ID；接口至少返回 `awarded`、`amount`、`daily_click_earned`、`daily_click_cap`、`balance`、`stage`（`early / middle / late / final / capped`）与 `server_time`。正式数值以服务端响应为准；demo 数值只能进入 demo 命名空间，不得写入 live 余额、流水或统计。

### 7.6 交互 2 · 贴贴蛋宝宝

长按触发一次自由安抚：长按 → **按住满 1 秒触发一次手机短震动（`wx.vibrateShort`），此后每满 1 秒再震一次（3 秒内最多 3 次），指尖有“它在回应”的体感** → 满 3 秒时蛋壳发光 + “我暖起来了”（第一人称，§9.6）。🟩 普通版不记录每日有效次数、不增加进度、不显示完成态；中途松手也可自然结束，系统关闭震动 / 设备不支持时静默跳过。

### 7.7 随机反馈文案

蛋在触摸 / 长按 / 完成动作后自动给一句短反馈，以气泡 / 小字轻量出现，**不用弹窗**，从当前状态文案池随机抽 1 条，展示后自动消失或被下次反馈替换。文案本身不产生进度；短时间内尽量不重复。（文案池沿用 MVP：普通状态 / 点击后 / 贴贴后 / 完成动作后四类，人称按 §9.6 硬规则改写为第一人称。）

**轻量主动招呼**：首次进入首页时，蛋可以用第一人称轻轻表示“我在这里”，但不催促用户完成当日动作。当前文案为“我在窝里。想来时，就陪我待一会儿吧。”点击只收起气泡，不跳转、不计完成。招呼只在页面内出现，不弹窗、不推送，不使用“今天必须”“还没完成”等任务式语言。

### 7.8 主界面按钮逻辑

> “开始孵化 / 孵化修炼手册 / 查看孵化进度”三态主按钮取消。孵化中由「一起待一会儿」自由陪伴区提供入口；主按钮只保留破壳相关状态：

| 用户状态 | 按钮文案 |
|---|---|
| 孵化中（默认） | 无主按钮，展示 8 个自由陪伴入口与常驻说话输入框 |
| 服务端生命周期进入“准备见面” | 等待破壳日 |
| 即将破壳 | 等待破壳 |
| 到达预设破壳时间（服务端判定，界面无倒计时展示） | 查看破壳结果 |

**破壳触发规则**：MVP 不做小程序与机械装置实时硬件联动（无蓝牙 / 联网状态 / 打开信号同步）；以“预设打开时间”作为可承接依据，并设**承接容差**：服务器时间进入预设打开时间前 2 小时即允许承接（容差值按装置时钟精度调整），避免装置时钟偏快导致“实体已开、小程序仍显示即将破壳”的穿帮；物理装置按预设时间打开、用户先看实体；小程序不在物理打开前提前展示款式 / 收藏卡；用户下次进入 → “待破壳 / 待承接” → 点“查看破壳结果” → 承接并生成一蛋一份的收藏卡；长时间未打开则收藏卡在下次进入时生成，生日仍按预设破壳日记录。

## 8 · 收藏卡系统

> 🟨 **普通版改写（v2.27）**：普通版只保留一蛋一份的“纪念收藏卡 / 数字档案”，用于记录实体蛋身份与破壳记忆；不得出现卡池、稀有度、随机获取、系列进度、空卡位、集齐、交换、购买权解锁或价值暗示。§8.8 整节为 🟥 普通版停用。现有用户界面若保留卡片，统一称“收藏卡”，但页面定位是纪念档案而非收集玩法。

> **命名统一（重要）：界面 / 用户侧一律称「收藏卡」，不出现"破壳卡 / 场景卡 / 套卡"等字样。** 卡册标题为「我的收藏卡」，用户看到的每一张都叫收藏卡。
>
> 本章为区分**两种生成方式**（供开发实现，用户不感知），在文档内部沿用两个代号：
> - **收藏卡·破壳生成**（§8.1–8.7）：破壳时一蛋一张的身份卡，带名字 / MBTI / 星座 / 生日等。
> - **收藏卡·场景收集**（§8.8）：破壳后逛场景收集的多张卡，按系列凑齐，是六场景成为长期玩法、并沉淀用户偏好数据的核心机制。
>
> 下文出现"破壳卡 / 场景卡"仅为工程内部区分生成逻辑，**均不作为界面文案**。

### 8.1 收藏卡（破壳生成）· 设计目的

物理装置打开后小程序发放的核心数字纪念物，承担惊喜（承接实体"哇塞"时刻）、收藏（唯一身份档案）、传播（保存 / 分享，后续可赠送 / 交换）。

**一句话**：每只蛋宝宝物理装置打开后，小程序生成一张唯一收藏卡，记录出生信息、原型、款式、性格与收藏编号。

### 8.2 破壳惊喜承接节奏（四步）

1. **机械破壳**：物理装置按预设时间打开，先看实体本体
2. **小程序承接**：到点后进入小程序，蛋进入"待承接破壳结果"
3. **数字确认**：展示一句出生文案（如"它终于见到你了"）
4. **纪念档案生成**：卡片从光里淡入，展示完整档案，提示“这是我的破壳纪念”

**生成规则**：仅到达预设打开时间后生成；一蛋一卡；重复进入展示已生成卡不重随机；款式 / 性别 / MBTI / 血型 / 编号一经生成固定；生日按预设破壳日记录；生成失败可重试但必须复用同一固定结果。

**命名规则（升级）**：名字优先取用户在孵化期设置的昵称（≤10 字，§6.4）。**未命名时不再显示原型名，而是从该角色专属名字池随机取一个合适的名字**（锦鲤池：阿金 / 流年 / 自在 / 知足 / 小润 / 澄澈…；玉兔池：望舒 / 皎皎 / 阿晚 / 素素…，见 destiny-seal 名字池），并固定写入卡片；用户后续仍可在档案里改名（每天最多 1 次，§6.4），改名同步更新卡面显示的名字（编号 / 生日 / 款式等其余字段不变）。

### 8.3 收藏卡内容

宠物头像 / 形象 · 原型（锦鲤 / 玉兔）· 款式（破壳揭晓）· 昵称 · 生日 · 星座（按生日）· 性别（随机，符号显示）· MBTI（趣味标签，按孵化选择生成）· 性格简介（≤20 字）· 血型（随机）· 收藏属性（普通 / 限定）· 收藏编号 · 孵化完成度标签（完整 / 轻量孵化）· 初始主人。

> MBTI 为趣味人格标签，非严肃测评；由孵化选择 + 原型 + 随机因子生成，卡面展示但不解释完整逻辑。

### 8.4 稀缺感设计

**唯一编号**：如 `EGG-KOI-20260318-000128`（EGG 体系 / KOI 锦鲤原型 / 破壳日期 / 当天第 128 张），同编号不重复。

**原始孵化记录**：卡片永久记录"初始主人 + 破壳日期"，即使未来流转也保留——让第一任主人、早期用户、特殊日期卡更有纪念价值。

**收藏属性（仅 2 类，不做多层稀有度）**：

| 属性 | 含义 | 生成方式 |
|---|---|---|
| 普通 | 常规破壳生成 | 默认 |
| 限定 | 特定活动 / 节日 / 节气 / 企业激活码 / 运营批次产生 | 后台配置来源或批次 |

规则：收藏属性只表达来源 / 批次，不影响功能权益、**不承诺价格 / 收益 / 升值**；不做"稀有 / 闪光 / 传说"多级；长期稀缺感来自唯一编号 + 原始记录 + 破壳日期 + 批次来源 + 具体款式。

> **与节令系统的接口**（见 §11）：节气 / 传统节日期间由后台配置"限定"批次，使当期破壳的收藏卡带节令来源标记——这是"限定卡"的唯一实现路径，无需新增稀有度系统。

### 8.5 收藏与分享（MVP）

MVP 只做收藏与分享，不做转让。破壳卡自动进卡册；可生成分享图（含收藏编号 + 小程序码 + **分享码**）；可分享给微信好友。**赠送 / 持有人查询 / 流转记录**留到 1.1 版本。暂不做：现金交易 · 竞价 · 二级市场 · 卡片定价 · 平台撮合 · 收益承诺。

**分享落地闭环**：分享图上带一个**分享码**（本质为该用户尚未使用的个人激活码，§5.7）。好友扫小程序码进入后处于未绑定空状态，直接输入分享图上的分享码即可完成添加，不存在"进来后无码可用"的死状态。每个账号可用于分享的码数量上限在代码 / 配置中可调（默认沿用 §5.7 的 5 个）。

**卡册结构（已定）：所有收藏卡（无论破壳生成还是场景收集）合为一个统一卡册「我的收藏卡」，不做 tab 区分。**

- 取消"破壳卡 / 收藏套卡"分 tab 的做法；所有收藏卡在**同一个「我的收藏卡」**里展示。
- 卡册内可用**分区/分组**（如按收集系列分节，见 §8.8）自然组织，但**不是可切换的 tab**——所有收藏卡同屏、连续浏览。
- 未获得的系列卡位显示占位（如"尚未遇见"+ 编号 `007/010`），已获得卡显示卡面 + 名称 + 编号 + 获得日期 + 分享。
- 界面文案一律「收藏卡」，不出现"破壳卡 / 场景卡 / 套卡"。

### 8.6 页面按钮

查看我的卡册 · 保存图片 · 分享给好友。破壳卡生成后自动进"我的卡册"（无需手动收藏）；"赠送卡片"作为 1.1 版本，不进 MVP 主流程。

### 8.8 场景卡系统（NEW）

> 🟥 **普通版整节停用（v2.27）**：包括低概率掉落、卡池、稀有度、限定、每日上限、系列卡位、集齐、电商权益解锁、掉卡动效及相关数据 / 埋点。仅把本节作为未来独立游戏版的历史需求留档。**禁止仅替换“掉落 / 抽卡”为“遇见 / 收集”后继续运行同一机制。**

破壳后逛场景可收集的多张卡。它让六个生活场景从"一次性展示"升级为"长期收集玩法"，并把用户的探索行为沉淀为可复用的偏好数据。

**逻辑闭环**：逛场景 → 触发互动点 → 低概率掉落场景卡 → 收集成套 → 解锁实体电商购买权 + 沉淀偏好数据 → 反哺个性化与选品。

#### 8.8.1 产出规则（守住零操作 + 惊喜）

- 破壳后逛场景、触发互动点时**低概率掉落场景卡**，不做"必得"、不做进度条式确定奖励
- 每个场景有**独立卡池**（草地卡池、海边卡池……）；每个角色有自己的一组场景卡池（见 §10.5 方案 B）
- 掉落判定在**服务器侧**（防刷，见 §11.1 / §18.6）
- 每日掉落有上限（防肝防刷屏，见下方数值基准）

**掉落数值基准（已定初始值，服务端参数可调）**：

- 目标节奏：活跃用户约 **4 周集齐一个 10 张系列**
- 反推：日均 2 次有效互动机会 × 单次掉率 **≈18%** × 28 天 ≈ 10 张
- 已获得的卡**不重复掉出**（无重复获取，接 §8.8.2 用词规则的前提）
- 每日掉落上限 **2 张**
- 上线后按真实互动频次校准掉率，守住"4 周左右集齐"的节奏（过快无稀缺、过慢会放弃）

#### 8.8.2 稀有度与限定（沿用两级，不新增稀有度系统）

| 属性 | 含义 | 生成方式 |
|---|---|---|
| 普通 | 常规逛场景掉落 | 默认 |
| 限定 | 节气 / 节日期间该场景掉的限定款 | 后台配置节令批次（接 §11.3） |

例：中秋期间在"天台"场景可掉"中秋·天台·赏月"限定场景卡；限定卡过期下架、次年回归（制造 FOMO 与回访）。**限定只表达来源，不承诺价格 / 收益 / 升值**（守 §1.3 合规红线）。

#### 8.8.3 收集系列结构与收集 → 电商闭环

**收集系列（Set）结构**：场景收集的收藏卡以"系列"组织，每系列固定张数（如玉兔第 1 系列 = 10 张，系列代号 `YT-S01`；`YT` 原型 + `S01` 系列序）。系列是**卡册内的分组单位**，非用户须记忆的卡类名——用户看到的仍是"收藏卡"。

- 卡册中每系列显示全部卡位；未获得位显示占位（"尚未遇见" + 系列内编号如 `007/010`），已获得位显示卡面 + 名称（如"月夜泡泡浴"）+ 编号 + 获得日期 + 分享。
- 单卡编码沿用全局编号体系（如 `EGG-YT-20260714-000001`，§8.4）；系列内编号（`007/010`）是系列内序位，二者并存。

**收集 → 电商闭环**：集齐某系列 / 跨场景系列 / 某角色全部 → **解锁站外实体潮玩购买权 / 优惠**（承接 §8.4 同一条导流机制）。解锁只给权限，购买发生在站外，小程序内无支付。

- 解锁购买权指向**实体蛋（新角色）**；V2 不做配件 / 周边购买（避免复杂化）。多蛋绑定入口在展会后版本开放（§4.2）。
- 站外购买承接方式（已定）：**跳转对应的淘宝 / 小红书店铺**。实现约束：微信小程序内**无法直接拉起**淘宝 / 小红书 App 或其网页，落地形式 = 解锁页展示店铺指引 + **一键复制店铺链接 / 淘口令**（用户到对应 App 粘贴打开），可辅以店铺二维码长按识别（以微信审核放行为准）。`ecommerce_cta_click` 的 `entry` 属性记录承接形式（复制链接 / 二维码 / 淘宝 / 小红书）。

> 卡册为统一视图：所有收藏卡（破壳生成 + 场景收集）同在「我的收藏卡」，以系列分区组织但**不分 tab**（§8.5）。

#### 8.8.4 场景卡数据字段

场景卡 ID · 所属角色 · 所属场景 · 卡池 ID · 稀有度（普通 / 限定）· 限定批次（节令来源，可空）· 卡面图 · 获得时间 · 获得场景互动点 · 是否保存 · 是否分享 · 持有用户 ID · `mode`（live / demo，见 §17.3）。

> 场景卡产生的"偏好数据点"是本系统的长期价值所在，独立记录，详见 §18.2 数据表与 §19.4 成长系统。

#### 8.8.5 掉卡瞬间体验（遇见时刻）

参照破壳四步（§8.2）的迷你版——这是支柱 2"不可预测的回馈"的高频情绪节拍，不做成普通 toast：

1. **触发**：互动点特效正常播完（不提前打断）
2. **预示**：一枚光点从互动点飘出、聚拢（约 0.5s）
3. **揭晓**：卡片从光里翻出，展示卡面 + 名称 + 系列内编号（约 1.5–2s，可点击跳过）
4. **收束**：文案"你遇见了一张新的收藏卡"，卡片自动收入卡册；提供「查看」/「分享」轻量入口，不强制跳转，关闭浮层即回场景继续逛

规则：揭晓层为浮层，不打断逛场景主流程；`prefers-reduced-motion` 时降级为淡入；文案守 §8.8.2 用词硬规则（只说"遇见"，不出现"掉落 / 抽"）；限定卡揭晓时展示节令来源标记；埋点沿用 `scene_card_drop`（§18.9.5）。

### 8.9 破壳卡视觉与 H5 实现规格（交付 Codex 5.6 Sol）

> 本节是破壳卡（§8.1–8.7）的实现级、自包含规格，供 Codex 直接落地——Codex 不必通读整份 PRD 即可依本节开工。目标：把破壳卡做成**水彩水墨风、三段式（名字标题 / 插画 / 数据）的可分享收藏卡**（对标下述最终方向图）。角色档案页复用同一数据模型与视觉系统。

#### 8.9.1 视觉基线与最终方向（参考图）

- **基线 A（旧实现）**：奶油色卡面，数据字段较多。仅作数据模型参考。
- **最终方向（本版采用）**：**水彩水墨风卡片**——顶部名字标题（带装饰星点）+ 中部随机插画 + 底部三行数据栏（MBTI / 星座 / 生日）。参考 Lovart 迭代稿（图三过程稿 → 最终采用图一右上角卡式）。柔和、可爱、手绘感，非宇宙科技风。
- **WAIC 宇宙海报属独立营销物料**，不是本卡的卡面风格，勿套用到破壳卡。

**卡面展示 8 项（头像数据保留，不再单独显示）**：

1. IP 形象头像（角色形象图，用作头像）
2. 原型（锦鲤 / 玉兔）
3. 名字（用户昵称；未命名走名字池，§8.9.6）
4. 生日（破壳日，**年月日**）
5. 星座（按生日自动计算）
6. 性别（随机，仅显示符号 ♀ / ♂）
7. MBTI（性格算法得出最接近的类型）
8. 性情独白（性格算法生成的一句性格简介，≤20 字）
9. 血型（随机）

仍不上卡面、留在**角色档案页**：款式 / 编号 / 收藏属性 / 孵化完成度 / 初始主人（编号可作分享图脚注）。

> **卡面模板统一**：以上为所有收藏卡共用的卡面模板。场景收集的收藏卡（§8.8）在同一模板上**额外**带：系列名（如"玉兔初见·水彩日常"）、卡名（如"月夜泡泡浴"）、系列内编号（如 `010/010`），插画区为该场景卡卡面图。

#### 8.9.2 实现方式：H5（webview）

- 破壳卡与角色档案页**用 H5 实现**，小程序 webview 承载，不用原生渲染。原因：① 需要自由视觉合成（卡模板 + 随机插画 + 数据层）；② 需要 canvas 导出可分享长图；③ 视觉迭代频繁，H5 解耦后不必重构原生。
- **数据注入**：小程序侧拿到 `card_id` → H5 通过 URL 参数 / JSBridge 取卡片数据 JSON 渲染。
- **H5 只渲染，不生成任何随机值**：插画选择 / 款式 / 性别 / MBTI / 血型 / 编号 / 名字回退等一切随机与固定结果，**均由服务端在破壳时一次生成并落库**（§8.2）；H5 收到的是已定稿 JSON。重复进入渲染同一结果，永不重随机。
- **时间**：一律服务器时间（北京时间 UTC+8，§11.1），不用设备时间。
- **mode**：每张卡带 `mode`（`live` / `demo`，§17.3）；`demo` 卡不进正式卡册与统计。
- **前置条件 ①（业务域名，本节全部交付的前置依赖）**：web-view 仅能加载**已 ICP 备案域名 + HTTPS**——使用 `eggbabe.com`（备案主体：上海爱予慧科技有限责任公司，§1.4）；开发前须在小程序后台配置业务域名并完成域名校验文件放置。
- **前置条件 ②（保存图片）**：web-view 内 H5 的 canvas 图**不能直接写入用户相册**。规避方案：H5 将图片数据经 `postMessage` 回传小程序侧，由 `wx.saveImageToPhotosAlbum` 保存（首选）；或服务端合成图片 URL 后下载（备选）。§8.9.9 的"建议先 canvas"须按此路径实现。

#### 8.9.3 卡片视觉结构（三段式）

卡片为固定模板（圆角边框 + 浅底），H5 在模板内合成三段：

| 段 | 位置 | 占比 | 内容 | 说明 |
|---|---|---|---|---|
| **头衔区** | 顶 | ~15% | 左：**IP 形象头像**（egg-avatar 圆形 / 蛋形框，§12.4）· 中：名字标题（站酷快乐体，§8.9.6）+ 装饰星点 · 名字下方小字：**原型名**（玉兔 / 锦鲤） | 名字随用户改名实时更新 |
| **插画区** | 中 | ~45–50% | 随机插画（节令 / 性格加权，§8.9.5）；场景收集卡为该卡卡面图 | 一卡一图，生成时定，重进不变 |
| **数据区** | 底 | ~35–40% | 五行：生日（**年月日**）/ 星座（带符号）/ 性别（符号 ♀ / ♂）/ MBTI / 血型；底部一行**性情独白**（居中引句，≤20 字） | 圆角描边容器 + 每行彩色图标 |

**信息密度硬原则（8 项不等于拥挤）**：卡面必须**简单、清晰、有留白**——信息多靠排布消化，不靠堆叠塞满。

- **视觉主次**：插画 > 名字 > 数据。插画区和留白是卡片的呼吸感来源，不许被数据区挤压。
- **数据区收紧**：两列排布（生日+星座 / 性别+血型 一行两列，MBTI 单独一行或并入），小字号、图标弱化、去多余分隔线；数据区整体不超过卡面 1/3。
- **头衔区轻量**：头像小尺寸置左，原型名是名字下的一行小字，不做独立模块。
- **性情独白**：数据区之外单独一句居中引句，四周留白，是卡片唯一的"气口"，不带图标不带容器。
- 每个字段**只出现一次**，无标签冗余（如性别只显符号，不写"性别：♀"）。

其他：数据区行样式对标最终方向图（浅底、圆角描边、左图标 + 标签 + 右值）；竖版比例建议 3:4 或 9:16；插画是**卡片模板内的一块居中插画**（非全出血背景），头衔区与数据栏是模板 UI，叠在插画上下。

#### 8.9.4 卡面字段 + 完整数据模型 + JSON

**卡面展示（8 项 + 系列内编号）**：

| 卡面字段 | 来源 | 格式 / 规则 |
|---|---|---|

#### 8.9.5 插画选择：随机 + 节令 / 性格上下文

卡片中部插画从**该原型的插画池**中选取（如兔子插画池：招手、泡澡、看报、骑车、打坐、纸箱探头、花丛、滑板、跳舞、科学实验……，即 Lovart 产出的多姿态水彩插画）。

**选择 = 加权随机（服务端破壳时定，一卡一图固定）**：

- **保底随机**：默认从池中随机，保证惊喜感（支柱 2）。
- **节令加权**：命中当前节气 / 节日时（§11.3），提升对应主题插画权重（如中秋 → 赏月 / 月亮插画；春节 → 喜庆姿态）。
- **性格加权**：按 MBTI / 孵化偏好提升匹配插画权重（内向 / INFJ → 打坐、看报、独处；外向 / E → 滑板、骑车、跳舞）。
- 三者加权后抽一张，`illustration_id` 落库固定；重进渲染同一张。

**插画池要求**：每张插画角色居中、留白一致、水彩底柔和，供卡模板直接嵌入；新增插画 = 往池里加图 + 打标签（节令标签 / 性格标签），不改代码。

#### 8.9.6 名字与性情独白：字体 / 动态子集 / 未命名回退

**名字是卡片顶部主标题**（对标最终方向图），随用户改名实时更新标题文字（编号 / 生日 / 插画等其余不变）。**性情独白与名字使用同一 ZCOOL KuaiLe 字体**，但保持独立的字号和留白规则。

**字体（已选）：站酷快乐体（ZCOOL KuaiLe）**
- 圆润、可爱、手写感，与水彩兔子插画气质一致。
- **授权（务必用 Google Fonts 版本）**：站酷快乐体有两个版本——① 站酷自发版，EULA 含"禁止转售牟利 / 禁止改字体名"等限制；② **Google Fonts 版**，2018 年以 **SIL OFL 1.1** 发布，web family 名 `ZCOOL KuaiLe`。**本项目一律使用 Google Fonts 的 OFL 版本**——OFL 允许商用、嵌入、打包（仅禁止把字体文件单独当商品出售），与品牌英文字体 Google Sans 的 OFL 体系一致，商用安全。**不要使用站酷自发版**，以免落入其 EULA 限制。
- **托管（⚠️必须自托管）**：Google Fonts CDN（`fonts.googleapis.com`）在中国大陆不可稳定访问，**不可作为线上依赖**。做法：Bohao 已从 Google Fonts 下载 OFL 版字体文件 → **自托管到备案域名 / CDN**（OFL 允许自托管与嵌入）。开发实施前须提示确认字体文件已就位。
- **加载优化（子集化）**：CJK 整包字体体积大。用 **fonttools / fontmin 做服务端动态子集化**，子集必须同时包含当前名字与性情独白的全部字符（等价于 Google Fonts `&text=` 的自托管实现）。用户改名或服务端更新独白时，按新的两段文字重新生成 / 请求子集。原生回退页通过 WXSS 内嵌当前性格算法全部固定句所需的轻量 TTF 子集；保存图片不得依赖旧版 Canvas 不支持的动态字体接口，统一绘制随包交付的 2x ZCOOL 预渲染独白素材。小程序发布包内必须携带 OFL 1.1 许可证。
- **字集**：GB2312 / 6763 字，覆盖常用汉字；生僻名字字符可能缺字 → fallback。
- **fallback 栈**：`"ZCOOL KuaiLe", "PingFang SC", sans-serif`（缺字 / 未加载时回退 PingFang SC）。

**未命名回退**：破壳时若用户未命名，服务端从**该原型专属名字池**随机取一个固定写入（`name_by_user=false`），**不显示原型名**。用户后续可在档案改名（**每天最多 1 次**，§6.4），标题同步。

**名字池样本**（完整池见 destiny-seal）：
- **锦鲤（KOI）**：阿金 · 流年 · 阿悠 · 知足 · 小润 · 自在 · 阿顺 · 澄澈 · 涟涟 · 锦程 · 阿漫 · 泓泓 · 春鱼 · 小池 · 鱼乐 · 阿泓 · 清波 · 丰年

3a. 信息密度过关（§8.9.3 硬原则）：插画与留白为视觉主体，数据区 ≤ 卡面 1/3（两列收紧），性情独白四周留白，无字段重复、无标签冗余。

6. 卡面 / 分享图英文字标只显示全小写 `eggbabe`。

9. 每张卡带 `mode`；`demo` 卡不进正式卡册与统计。
10. 数据栏文字对比度过 WCAG AA。

## 9 · 每日状态

> 🟩 **普通版可保留（v2.27）**：每日状态是非数值、非奖励的一句情绪表达。不得生成心情值、亲密度、连续到访记录、成长加成或专属剧情解锁；用户未访问时不得用负面文案施压。

### 9.1 设计目的与定义

增强"活人感"：用户每天回来会好奇它今天心情 / 在干嘛 / 有没有想我 / 是否因昨天互动而变化。

**MVP 只做一件事**：破壳后的蛋宝宝每天最多生成一句状态文案，展示在角色主页、对话页、档案页（§9.2）。**孵化期不生成、不展示每日状态**（变更：孵化首页信息做减法，陪伴感由轻量主动招呼 §7.7 与气泡反馈承担）。它是蛋宝宝今天主动"冒出来"的一句话，不是选择题、不是弹窗。

### 9.2 展示位置

| 页面 | 展示方式 |
|---|---|
| 破壳后角色主页 | 居中"今日状态"文字（见 §10.2） |
| 对话页顶部 | 显示今日心情标签 + 一句话 |
| 宠物档案页 | 展示"今日心情"模块 |

> 变更：孵化期首页**不展示**每日状态（§9.1 / §7.2），原"蛋宝宝首页展示蛋状态一句话"的做法取消。

> 注：当前构建已删除"我的"页里的独立蛋宝宝状态模块（见 §14.2），每日状态不再在"我的"页展示。

### 9.3 生成规则

每天最多 1 条；当天首次进入相关页面时按需生成；当天生成后不变，次日重新生成；未绑定不生成；**孵化期不生成，仅破壳后生成与展示**。互动内容可作为对话上下文，但不得累积为关系数值或决定奖励 / 解锁。生成失败先用本地文案池兜底再重试；兜底文案不落库、不进统计。

### 9.4 生成依据（MVP 用 5 类输入）

宠物基础人设（非成长属性）· 最近一段对话的语义上下文 · 当前生命周期阶段 · 节令 / 昼夜内容上下文 · 内容去重。

**逻辑**：宠物阶段 + 基础性格 / 孵化偏好 + 用户最近行为 + 随机心情 = 今日状态一句话。

> **V2 增强**：节令与昼夜作为可选上下文输入（见 §11）——节气 / 节日当天，状态文案池可切到对应节令子池（如中秋"它今晚一直看着月亮"）；昼夜相位可轻微影响措辞（深夜偏安静）。此为可选增强，不改变"每天 1 条、随机为主"的基本盘。

### 9.5 今日心情类型（仅 5 类，避免变重）

| 心情 | 适用场景 | 文案方向 |
|---|---|---|
| 开心 | 最近有互动 | 亲近、期待、轻快 |
| 平静 | 正常活跃 | 陪伴、安稳、日常 |
| 想念 | 多日未打开 | 轻微撒娇、等待 |
| 兴奋 | 即将破壳 / 互动频繁 | 期待、活跃、好奇 |
| 低落 | 长期未互动 | 温柔提醒，不做惩罚感 |

不做愤怒 / 焦虑 / 嫉妒等重情绪。

### 9.6 分阶段文案规则与风格

破壳后写"宠物"（心情 / 行为 / 想念 / 今天在做什么）。原孵化期文案池（壳里动静 / 等待 / 被照顾 / 即将破壳）**不再用于每日状态**（孵化期不展示，§9.1），转作 §7.7 气泡反馈与轻量主动招呼的素材池，人称同样改写为第一人称。**风格**：≤20 字（最多 30）；像宠物自己的状态不像系统通知；不鸡汤、不堆热词、不给负担。

**人称硬规则（WAIC 反馈，全局生效）**：所有蛋宝宝相关文案一律**第一人称、一对一对话**——蛋宝宝自称"我"、称用户"你"；**禁止第三人称旁白**（"它今天…"式描述）。适用范围：每日状态 · 气泡反馈（§7.7）· 轻量主动招呼 · 出生文案（§8.2）· 状态卡片（§10.1）· 破壳承接文案 · **AI 对话的全部输出**（§10.4，模型 prompt 中写死人称约束）——凡是"宠物在说话"的地方，一律第一人称。

- ✅ 我今天把想你这件事藏得不太好。 / 我醒得很早，一直在等你。
- ❌ 它今天把想你这件事藏得不太好。（第三人称旁白） / 请尽快完成今日任务以提升活跃度。（系统腔）

> 完整示例文案池（孵化期 × 5 心情、破壳后 × 5 心情）沿用 MVP v0.1 的题材与心情结构，但**须整体改写为第一人称**（显式推翻此前"V2 不改文案池"的约定）；§9.4 节令子池同标准。

### 9.7 数据字段

宠物 ID · 日期 · 今日心情类型 · 状态文案 · 生成时间 · 是否已展示 · 生成依据（性格 / 互动 / 活跃 / 随机 / 节令）· 当日是否点击查看 · 是否因状态进入对话页 · 生成方式（算法 / 兜底）。

| 天台 | 风铃摇动 · 纸飞机飞过 · 云层移动 |

**场景硬性规则（当前实现 + 须保持）**：

- 六场景共约 18 个主要互动点，**全部避开微信右上角胶囊按钮区域，也避免贴近屏幕最底部 / 边缘**
- 每个互动点声明的动效都有对应视觉样式（无"声明了但没样式"的悬空点）
- **页面离开后动效必须停止并清理**，避免返回其他页面后继续运行或重复触发
- 系统开启"减少动态效果"（`prefers-reduced-motion`）时，连续环境动画弱化 / 隐藏，但**保留必要的文字反馈**
- 进入场景加入渐变过渡，减少页面突然切换感

**交互逻辑（当前实现）**：

- 点击角色主图直接进入当前场景，**不再弹"更换场景"选择器**
- 底部两个并排按钮：**"和我说说话"约占 70%、"更换场景"约占 30%**
- 点击"更换场景"才打开六场景选择界面
- 已删除原先位于场景详情页右上角、易被胶囊按钮遮挡的入口
- **普通版互动点只返回动画和第一人称文案**；不掉卡、不发资源、不形成收集进度，也不据此建立兴趣画像

### 10.3 场景系统的维护成本（须在正式版处理）

当前六场景可运行，但场景样式文件较大、每个场景重复编写代码。**新增角色 / 场景前，须把「场景配置 + 互动点 + 动效类型 + 文案反馈 + 环境动画」抽象为统一的场景组件与配置系统**（见 §18.6），否则每加一个角色的六场景都要重写一遍，维护成本线性膨胀。

### 10.4 对话入口

破壳后开放对话，作为建立关系后的自然延续：用户可说话，蛋宝宝按性格 + 每日状态回应，收集真实语料与反馈。

**元素**：顶部宠物信息（头像 / 昵称 / 今日心情）· 消息区 · 输入区（文字）· 今日状态小提示。
**规则**：破壳后开放；对话页展示今日心情标签 + 状态文案；文字输入；回复风格受 MBTI + 性格简介 + 今日心情影响；**回复一律第一人称**（§9.6 硬规则，写入模型 system prompt）；后台记录对话次数 / 时长 / 留存。语音能力后续版本。

### 10.5 场景与角色差异化（已定：方案 B — 共用引擎 + 每角色场景组单配）

**技术上共用一套场景引擎（建一次），内容上每个角色配自己贴合世界观的场景组。** 普通版的价值来自不同角色的视觉、文案与对话个性，不以场景卡收集或购买驱动衡量。

**共用 vs 单配的明确分工：**

| 层 | 共用（建一次，所有角色复用） | 单配（每角色一份配置） |
|---|---|---|
| 场景框架 | 六格结构、导航、"更换场景"选择器 | 各场景的**美术背景图** |
| 角色形象 | 主页布局、70/30 按钮结构 | 角色在每个场景里的**立绘 / 形象** |
| 互动 | 互动点位置逻辑、避胶囊规则、点击→特效机制 | 每个互动点的**专属文案** |
| 动效 | 动效引擎 / 类型（飘雪、蝴蝶、发光…） | 是否启用、参数微调、专属特效 |
| 系统 | 定性状态、对话安全、内容轮换与服务端生命周期 | 角色基础人设、专属场景文案与视觉素材；无成长、掉落或卡池 |

**场景组配置（方案 B）**：建一个更大的场景库，每个角色从中挑最贴合的六个，而非全角色共用同一套六场景。示例映射（待美术确认）：

| 角色 | 世界观 | 场景组倾向 |
|---|---|---|
| 玉兔 | 月 / 静 | 月下天台 · 房间 · 桂树林 · 云海 …（偏静） |
| 锦鲤 | 水 / 流 | 海边 · 溪river · 雨 · 荷塘 …（偏水） |
| 企鹅（墩气） | 雪 / 冷 | 雪地 · 冰面 · 极地 …（偏冷） |

**落地要求**：新增角色 = 填一份场景组配置（美术 + 立绘 + 文案），**不重写代码**。若不做配置系统、把六场景写死成玉兔专用，则每加一个角色都要重写六场景，成本线性爆炸——这是 §10.3 / §18.7 强制要求场景配置系统的根本原因。

### 10.6 对话安全与兜底（NEW）

> 对话是情感陪伴产品的核心，也是内容安全责任最重的模块。本节为上线前必做项。

**模型与合规基线**

- 对话能力接入**阿里通义千问**（已完成生成式 AI / 深度合成备案的大模型服务，API 接入）；生成侧算法备案由模型方覆盖，**产品侧仍自担内容审核责任**。
- 所有**用户输入**（对话消息、昵称、改名等用户生成文本）与**AI 输出**在展示 / 落库前过内容安全检测：微信 `security.msgSecCheck`（或云开发内容安全接口）+ 模型侧内容过滤，双层。检测不过：输入侧温和提示"换个说法试试"；输出侧丢弃并从兜底文案池回复。
- 对话频次 / 成本护栏由 CTO 侧模型方案统一负责，不在本节设定（备忘：若未来加上限，拒绝话术须拟人化，如"它今天说累了，想安静一会儿"）。

**情感陪伴危机应对（必做）**

- **检测**：关键词库 + 模型判断双通道，识别自伤 / 自杀 / 严重情绪危机表达。
- **响应**：命中后**跳出日常人设**，使用固定安全回复模板——温和、不评判、明确建议向身边真实的人求助，并给出**全国统一心理援助热线 12356**；不以角色扮演方式展开危机话题、不提供任何方法性信息。
- **不加重**：低落 / 想念等日常心情（§9.5）不得使用制造愧疚或加深负面情绪的表达（守支柱 1）。
- **记录**：危机命中会话仅打安全审计标记，**不进入偏好画像**（§18.2）。

**未成年人保护**

- 产品面向全年龄、不做强制年龄验证，因此**全部对话内容按未成年人可见标准执行（最严标准）**：无成人 / 恐怖 / 赌博暗示 / 诱导消费内容。
- 不向用户索取敏感个人信息；用户在对话中主动透露的个人信息不落库、不进画像。
- 深夜时段（§11.2 夜相位）连续长时间对话时给一次温和的休息提示（拟人化，如"它有点困了，你也早点休息吧"），不强制中断、不重复打扰。

**AI 输出边界（人设护栏）**

- 不输出：医疗诊断 / 用药建议、投资建议、成人内容、对真实人物的评价、诱导站外消费。
- 不做"主动发起联系"式表达（守品牌原则：它在自己的世界里生活、向你分享发现，而非主动纠缠）。
- 模型不可用 / 超时：从兜底文案池按今日心情取一条回复，不报错、不空白。

## 11 · 时间与节令系统

> 🟨 **普通版改写（v2.27）**：服务器北京时间、昼夜视觉、节气背景与问候可保留；“限定掉落、节令发币、限定道具、连续回访奖励”全部停用。节令只换内容，不发资源。

> 本节为 V2 新增，统一 MVP 中散落的时间依赖（破壳日、每日状态刷新、限定批次），并把"共勉/一起经历"的节令层做成轻量、不与极简原则冲突的机制。

### 11.1 权威时间

- **权威时间 = 服务器时间，北京时间 UTC+8，单一时区。**
- 破壳日判定、每日状态刷新、节令事件、收藏卡生成时间戳，全部以服务器时间为准。
- **禁止使用设备本地时间**驱动任何判定（防改时钟：加速孵化、刷每日状态、蹭限定批次）。
- 客户端只做展示，破壳结果 / 收藏卡 / 每日状态在服务器侧生成。

### 11.2 昼夜（仅轻表现层，不切内容池）

昼夜**只影响蛋 / 宠物的待机呈现与每日状态措辞**，不切分任何卡池、不增加玩法：

- 白天：蛋形 / 宠物待机偏活跃，光线明亮
- 夜晚：待机偏安静，光线柔和；深夜每日状态措辞可偏安静

时段采用**固定区间 + 按节气整体平移**（春分昼夜均分、夏至昼最长、冬至夜最长、秋分昼夜均分为锚点，相邻线性过渡），不做逐日天文计算。

### 11.3 节气 / 节日（接入既有"限定"收藏属性）

节令层**不新增系统**，只通过后台配置驱动两件既有能力：① 让当期破壳的收藏卡带"限定"来源标记（§8.4）；② 让每日状态切到节令子池（§9.4）。全员同一时刻进入同一节令相位，形成"一起经历"的社交与晒卡动机。

**v1 节气（6 个，以二分二至为骨架，与昼夜咬合）**

| 节气 | 昼夜意义 | 角色主场 / 主题 |
|---|---|---|
| 立春 | 开年 | 锦鲤"解冻之跃" |
| 春分 | 昼夜均分 | 平衡意象（通用） |
| 谷雨 | 生长 | 万物生长（通用） |
| 夏至 | 昼最长 | 户外 / 锦鲤 |
| 秋分 | 昼夜均分（入秋） | 玉兔氛围渐起 |
| 冬至 | 夜最长 | 玉兔"至阴极阳"主场 |

**v1 传统节日（6 个）**

| 节日 | 历法 | 同框强度 | 角色主场 / 主题 |
|---|---|---|---|
| 春节 | 农历 | ★★★ | 三角色齐上 · 团圆 |
| 元宵 | 农历 | ★★ | 灯 / 圆 |
| 端午 | 农历 | ★★ | 龙舟 / 粽（通用） |
| 七夕 | 农历 | ★★ | 义维度里程碑话术 |
| 中秋 | 农历 | ★★★ | 玉兔绝对主场 · 寻月 |
| 跨年 | 公历 | ★★ | 全员倒计时 |

春节、中秋为两个绝对主场，资源优先。

### 11.4 实现方式

- 服务器侧挂一张**节令配置表**：预置未来若干年的公历触发日期（农历节日预先换算写死），到日触发对应"限定批次 + 每日状态子池"。
- **不需要实时农历运算**，王敏侧加一张配置表即可。
- 节气按太阳历判定，可用预置对照表；跨年按公历。

### 11.5 订阅消息触达（NEW）

用户等破壳最长 10 天，无触达则全靠自觉回访。使用微信**订阅消息**（一次性订阅）做最小触达集，全部由服务端按北京时间发送（§11.1）：

| 消息 | 触发 | 授权请求时机 |
|---|---|---|
| 破壳日提醒 | 预设破壳日当天 | 绑定成功后请求（体验最顺的授权点，一次请求可含多条模板） |
| 即将破壳提醒 | 破壳前 <24h | 同上 |
| 节令限定上新 | 节气 / 节日限定批次开启（§11.3） | 破壳后在场景 / 卡册内的自然时机请求 |

规则：一次性订阅按微信规则"授权一次发一条"；请求时机须自然（绑定成功、破壳承接后），**不弹窗轰炸**；用户拒绝后不重复索取（守支柱 1）。埋点：`push_authorized` / `push_sent` / `push_open`（并入 §18.9，带通用属性与 `mode`）。

## 12 · 设计系统（eggbabe DESIGN）

> 提炼自 eggbabe-DESIGN.md（alpha）。完整 token 以设计源文件为准，本节供开发与 Claude Design 落地对齐。

### 12.1 品牌语言

温暖、有机的情感陪伴品牌，围绕**三蛋色叙事**：青禾绿（扎根 / 滋养）· 晨露黄（觉醒 / 互动）· 桃粉霜（羁绊 / 亲密）。字标为深墨绿圆润几何小写体，字母上带三蛋色小圆点。整体偏柔和椭圆形态、留白充分、神话但可触的调性（破壳 / 灵魂底色 / 命运）——须读作高端潮玩，而非通用 SaaS。

### 12.2 色彩（核心 token）

| 类别 | token | 值 | 用途 |
|---|---|---|---|
| 品牌 | brand-green 青禾绿 | `#ACC861` | 主色 · 品牌"土壤" |
| 品牌 | brand-yellow 晨露黄 | `#F1EC9A` | 觉醒强调（仅点缀，勿作正文底） |
| 品牌 | brand-pink 桃粉霜 | `#FFC5BA` | 羁绊强调（仅点缀，勿作正文底） |
| 墨绿 | ink-green | `#3F5A47` | 主 CTA / 交互主色 · 字标（⚠️待与 logo 源文件核对） |
| 墨绿 | ink-green-pressed | `#324839` | 按压态 |
| 中性 | canvas / ink / hairline | `#FFFFFF` / `#1A1A1A` / `#E5E3DF` | 底 / 正文 / 分隔 |
| 语义 | error-text / warning-text | `#C33F36` / `#976A28` | **文本用 -text 变体**（-base 作文本不过 WCAG AA） |

三色 tint 卡背（green/yellow/pink surface）按灵魂层归类内容：**绿=灵魂底色、黄=今日心境、粉=性格轨迹 / 羁绊**。

### 12.3 字体（两套，严格分离）

- **英文全部 Google Sans**（SIL OFL，2025-12 起可商用）；**中文全部 PingFang SC**。
- ⚠️ **Google Sans 无 CJK 字形**——绝不能作中文 token 的 fontFamily；两套字体不可互为 fallback。
- ⚠️ **PingFang SC 无真 Bold**——最重 Semibold(600)，请求 700 会触发合成粗体、显示异常；标题靠字号 + 字距而非加粗出效果。
- ⚠️ **PingFang SC 无内建 fallback**——Android 微信不渲染，必须配 fallback 栈：`PingFang SC, "Helvetica Neue", "Microsoft YaHei", sans-serif`。

### 12.4 关键组件（小程序骨架）

- **按钮**：primary（ink-green 实心 / 全圆角）· secondary（描边）· ghost；disabled 用 `disabled-text` 而非 ink-faint（后者近乎不可见）。
- **卡片**：card-base + 三色 tint 变体；tint 卡正文须用对应 `-on-tint` 文本色。
- **蛋形专用 `rounded.egg`**（`50% 50% 50% 50% / 58% 58% 42% 42%`）：仅用于头像框、破壳时刻视觉，不作通用圆角。
- **底部 Tab**：MVP 仅两 tab（蛋宝宝 / 我的），icon 在标签上方。
- **列表行 list-row**（52px 起）· 分隔 divider（左缩进对齐文字）· 分组头 section-header：构成"我的"骨架。
- **进度条**：羁绊 / 孵化进度，圆润柔和，fill = brand-green。
- **底部 sheet / modal / toast**：授权提示、确认、picker 用 bottom-sheet；toast-error 用 `error-text` 底色（白字 13px 在 -base 上不过对比度）。
- **egg-avatar**：玉兔 / 锦鲤头像的蛋形 / 圆形框。

### 12.5 动效

- 默认过渡 `180ms ease-out`（hover / press / 变色），柔而不弹。
- 表现性动效（spring / scale / reveal）**只留给情绪节点**：破壳、SEAL 揭晓、里程碑解锁，可慢至 400–600ms、更戏剧化。
- 卡片 hover 抬升 `translateY(-2px)`；按钮按压 `scale(0.98)`。
- 尊重 `prefers-reduced-motion`：破壳 / scale 动画降级为淡入。

### 12.6 布局与触控

- 小程序页：整宽分组列表（list-row 齐边、divider 缩进）；浮动卡片留 16px 边距；每屏一个清晰焦点，品牌语气克制不拥挤。
- 触控：按钮 44–48px、输入 48px、列表行 ≥52px。

### 12.7 已知缺口（须在正式锁定前补）

ink-green 需与 logo 源文件核对 · type scale 为推算值待用实际 CSS 校验 · logo 最小尺寸 / 留白规则未定义 · 无 icon 规范（建议选一套圆润线性图标库并登记）· 深色模式 token 不完整（勿让生成工具即兴）· 应用内 IP 形象渲染风格（玉兔 / 锦鲤在 App 内如何画）未在设计系统中定义，另立文档。

### 17.3 展会数据与正式数据隔离（已定，必做）

**核心机制**：所有数据加一个 `mode` 字段，取值 `live`（正式）/ `demo`（展会）。

| 环节 | 展会模式（demo）的行为 |
|---|---|
| 身份 | 匿名 / 设备级临时身份，**不走真实微信授权绑定、不写入正式 user 表**（或写入独立 `demo_` 命名空间） |

| 破壳卡 / 场景卡 | 不生成正式卡；如生成也带 `demo` 标记，**不进正式卡册与统计** |
| 指标 | 所有留存 / 转化 / DAU / 偏好数据查询**强制 `mode = 'live'`** |
| 生命周期 | demo 数据设 TTL 或支持一键批量清除，展会结束即清 |
| 入口 | 展会体验入口与正式领取入口物理分离；"退出体验"清空当前 demo 会话 |

**三条不可破**：① demo 数据永不进正式指标；② demo 不消耗真实激活码；③ demo 会话可批量清除。

## 18 · 正式版技术方案与数据架构

> 当前 MVP 主要为**前端本地数据**实现，适合演示但不能上线。本节明确正式版必须补齐的后端与数据能力。
>
> **分工（已定）**：本章为需求规格，**全部由王敏（CTO）侧实现**。Bohao 侧 AI 构建只产出前端静态页面 + services 层 mock（§15.1），**不得生成云函数 / 后端代码**——AI 生成的云函数对王敏侧无用且浪费 token。
>
> 🟥 **v2.27 数据门禁**：普通版 live 环境不建、不写、不回放货币、流水、隐藏阈值、掉落、卡池、库存、装配、成长进度、关系值或任务完成数据。历史 schema 可保留在文档 / 非生产分支，但不能成为“隐藏运行”的游戏系统。

### 18.1 后端选型（须决策）

明确二选一或组合：**微信云开发** vs **独立后端**。决策影响下述所有数据表、同步、鉴权与激活码安全的实现方式。建议 MVP→正式过渡期优先评估微信云开发（接入成本低、与小程序鉴权天然打通）。

### 18.2 数据表结构（须定义）

**普通版 live 核心表**（至少覆盖）：用户 · 蛋宝宝（实体蛋 / 绑定关系 / 服务端生命周期阶段）· 角色基础人设 · 收藏卡（数据模型可内部命名 `digital_record`）· 激活码 · 互动日志（触摸 / 对话 / 定性状态，仅为服务质量与上下文）· **蛋壳绘图记录**。每表须定义主键、唯一约束、外键关系与索引，且每表带 `mode`（live / demo）字段。**场景卡、货币余额 / 流水、商品目录、背包、每日获取计数和成长值均不属于普通版 live schema。**

**蛋壳绘图记录（正式数据）**：建议至少保存 `egg_id`、`user_id`、`mode`、`base_asset_id`、`base_version`、`color_token`、`color_alpha`、`pattern_instances`、`stroke_operations`、`canvas_version`、`preview_asset_url`（可选缓存）和 `updated_at`。

`pattern_instances` 使用图样 ID、归一化坐标、缩放、旋转和重复方式；`stroke_operations` 使用归一化点列、工具类型（brush / eraser）、固定笔宽与颜色。结构化编辑数据是事实来源，预览图只作缓存，不以整张截图代替可编辑记录。

正式版保存、跨设备同步和版本冲突处理由 CTO 后端实现；所有正式记录必须为 `mode='live'`，demo 记录独立存放且不得进入正式统计。`updated_at` 使用服务端北京时间 UTC+8，不依赖设备时间；首版 schema 不设置用户图片上传字段。

**🟨 普通版最小化行为分析**：只在隐私政策明确披露、用户可合理预期且确有产品改进需要时，记录必要的页面访问、互动类型与对话安全结果。原“逛场景 / 集卡偏好画像”方案冻结，不以收藏行为建立用户画像或解锁商业权益。

> 🟥 **以下“长期偏好数据点”表为历史方案，普通版 live 不采集、不分析：**

| 数据点 | 记录什么 | 长期用途 |
|---|---|---|
| 场景停留 | 各场景访问次数 / 停留时长 | 用户偏静（草地 / 房间）还是偏动（海边 / 天台） |
| 互动点点击 | 点了哪些点 / 频次 | 细粒度兴趣（蝴蝶 vs 萤火虫） |
| 得卡 / 存卡 / 分享 | 主动保存 / 分享了哪些场景卡 | 收藏偏好、传播偏好 |
| 时段 × 场景 | 什么时间来哪个场景 | 作息 × 场景关联（喂 §11 昼夜 / §9 每日状态） |
| 角色 × 场景 | （多角色后）偏爱谁的场景 | 角色偏好 → **电商选品依据** |

> 🟦 未来游戏版若重新论证并采集上述偏好画像，须在隐私政策中明确披露采集与用途，并在账号注销时依法处理；这不是普通版 live 当前授权。

### 18.3 用户 ID 唯一性

- 当前为前端生成的可读形式：`EB-20260710-XXXXXX-XXXX`（注册日期 + 随机字符），比纯时间戳易识别、降低撞号概率——**仅适合 MVP 演示**。
- 正式版须由**服务器 / 云数据库生成 ID 并设唯一约束**，保证：跨设备不重复 · 同一用户登录后 ID 一致 · 清缓存 / 重装后不生成新 ID · 大量并发注册仍唯一。

### 18.4 头像持久化

`chooseAvatar` 返回的可能只是**临时文件路径**，清缓存后失效。正式版须在选择后**上传至云存储 / 服务器**并落库持久化 URL。无头像时保持空白 / 默认占位，不伪造资料。

### 18.5 写入失败处理

当前部分本地数据写入失败时仍可能提示"操作成功"。正式版须建立**统一的数据错误处理与用户提示**：写入失败明确告知、可重试，禁止"假成功"。

### 18.6 激活码后端安全

激活码目前偏前端演示逻辑。正式上线须由后端完成：生成 · 绑定 · 核销 · 防重复使用 · 防伪造 · 使用记录 · 风控限制（频率 / 来源 / 批次）。

## 20 · 货币与商品（道具）体系

> 🟥 **普通版整章停用（v2.27，覆盖 v2.24 / v2.25）**：露珠、余额、点击获取、运营发放、商店、背包、购买、库存、装配、摆放、投喂与激励广告均不进入普通小程序生产包，也不开发 live 后端。以下内容仅作为历史设计与未来独立游戏版的需求输入；未来使用时必须结合获批版本重新设计，不能默认沿用。
>
> **重要修正**：不可充值、不可真钱购买、纯装饰，并不能单独证明该系统属于普通小程序；本项目不再使用“earn-only 所以不构成游戏 / 不触发版号”的判断。

**前端实现状态（2026-07-20）**：首页余额 / 今日进度、服务确认后的露珠飞行动效与 `+1 露珠`、第 10 个提示、商店、背包、购买确认、余额不足、已拥有、装配 / 卸下 / 摆放 / 投喂反馈和 live/demo service 适配层已完成。demo 仅以独立命名空间内的固定 26 次序列用于验收，不代表正式随机；live 正式余额、隐藏阈值、流水、购买事务、商品目录和库存仍等待 CTO 接口。

### 20.1 历史设计边界（🟥 普通版不适用）

- **单一"软货币"，仅可通过互动 / 时间 / 运营发放获得（未来可加看激励广告）——绝不可用真钱购买（无充值、无氪金、无付费加速）。**
- **道具仅用软货币购买，且纯装饰 / 情感向，不是战力 / 数值 / 付费加速。**
- 小程序内**无任何真钱支付**（守 §1.3）。
- 可充值货币、付费道具或数值加速会显著提高合规复杂度，本项目一律不做；但**是否属于网络游戏、是否需要出版审批，不能由这三项反向推断**，仍以完整机制和主管部门 / 平台结论为准。

### 20.2 货币设计

- **单一软货币，暂名「露珠」**（接品牌晨露黄，收集感、非交易感；如需可改名，避免"币 / 钻石"等强交易 / 博彩联想）。
- 历史方案的获取来源有两类：**互动赚取 / 运营发放**。普通版不启用。
- 明确**不可充值**；余额与流水服务端记账。
- **看激励广告（IAA）换币是未来变现入口，V2 不实现**（见 §20.10）。

### 20.3 获取来源（earn · 服务端判定 · 每日上限防刷）

| 来源 | 频率 | 说明 |
|---|---|---|
| 点击蛋宝宝 | 每日点击所得上限 10 个 | 第 1–10 个均采用“隐藏点击阈值 + 区间内必得”；接 §7.5 |
| 有效邀请 | 每次 | 接 §5.7 个人激活码；奖励额度由运营配置 |
| 节令 / 节日 / 人工补发 | 限时或单次 | 接 §11.3；只作为运营发放，不制造每日任务 |

**点击获取状态机（单用户、单个北京时间自然日）**：

| `daily_click_earned` | 阶段 | 服务端行为 |
|---:|---|---|
| 0–2 | `early` | 按第 1–3 个露珠的 1–2 次隐藏阈值累计有效点击，达到阈值时发放 1 个 |
| 3–6 | `middle` | 按第 4–7 个露珠的 2–3 次隐藏阈值累计有效点击，达到阈值时发放 1 个 |
| 7–8 | `late` | 按第 8–9 个露珠的 3–4 次隐藏阈值累计有效点击，达到阈值时发放 1 个 |
| 9 | `final` | 按第 10 个露珠的 4–6 次隐藏阈值累计有效点击，达到阈值时发放 1 个 |
| 10 | `capped` | `awarded=false, amount=0`，余额不变 |

- 点击所得上限只限制**点击蛋宝宝**这一来源；邀请、节令或人工补发使用独立来源额度，不能挤占当日 10 个点击露珠，也不能绕过各自运营上限。
- 每个露珠的隐藏阈值、分段权重与有效点击节流窗口均由 CTO 后端配置；前端只消费判定结果，不显示阈值，不实现本地随机。
- 所有获取均由服务端判定并记余额 / 流水；北京时间 UTC+8 为唯一日界；请求须幂等，重复请求不得重复发币（接 §11.1 / §18.5）。
- 当前版本不通过每日首次到访、连续到访、查看状态、普通场景点击或完成孵化动作额外发露珠，避免叠加成强任务系统；后续若新增来源，须单独评审经济平衡与任务压力。

### 20.3.1 首页余额与到账反馈

- 首页右上角常驻“露珠图标 + 总余额数字”；点击可查看“今日通过点击已收集 X / 10”。总余额是数量，不显示为百分比；孵化进度百分比使用独立圆环（§7.2）。
- 每次获得露珠都必须出现“点击处露珠 → 飞向右上角余额 → `+1 露珠` → 余额更新”的即时反馈；第 10 个到账后提示“今天的 10 个露珠已经收好啦”。
- 普通触摸反应立即播放，货币到账反馈等待服务端确认；请求失败时余额不变，并提供轻量重试，不出现假成功。
- 达上限后仍可自由点击并获得蛋的情绪反馈，不再发币，也不反复催促或展示“继续点击”的任务文案。

### 20.4 消耗（spend · 商店）

- 蛋宝宝页新增**「商店」入口** + **「背包」**（已拥有道具）。
- 露珠唯一用途：在商店购买蛋宝宝商品道具（§20.5）。
- 购买 = 服务端扣减余额 + 记流水 + 入背包；余额不足给友好提示，不引导充值（无充值入口）。

### 20.5 商品道具（在蛋宝宝页展示）

道具**纯装饰 / 情感向**，分三类（均不影响任何数值 / 战力）：

| 类别 | 示例 | 表现 |
|---|---|---|
| 装扮配件（prop 层） | 帽子 · 围巾 · 花环 · 小道具 | 穿戴在蛋宝宝身上；**限 prop 层，不重定义角色核心叙事**（接玉兔配件哲学：品牌控核心、用户控 prop） |
| 投喂零食 | 胡萝卜 · 小点心 · 饮品 | 投喂触发一段可爱反应 + 可轻微影响当日每日状态倾向（§9），**不做饱食度 / 好感数值** |
| 场景装饰 | 摆件 · 小灯 · 植物 | 摆进六场景（§10.2），装点角色的世界 |

- 展示位置：蛋宝宝页（孵化期蛋首页 / 破壳后角色主页）加商店 + 背包入口；已购装扮可在蛋宝宝身上 / 场景中穿戴 / 摆放。
- **数字道具 ≠ 实体配件**：destiny-seal 的实体配件（犄角 / 翅膀 / 雨靴，实体潮玩 SKU + 解锁成长支线）是另一套系统，勿与本节数字装饰道具混淆。
- 道具走**配置表**（道具 ID / 类别 / 售价 / 图 / 穿戴锚点 / 是否限定），新增道具 = 加配置 + 传图，不改代码。

### 20.6 与电商 / 限定的关系

- 数字道具用露珠购买，**不导流电商付费**，与 §8.8 场景卡的"集齐解锁站外购买权"是两条独立线，不冲突。
- 可选：节令期上架**限定装扮道具**（露珠购买或节令发放，接 §11.3），制造限时收集与回访。

### 20.7 数据模型（并入 §18.2）

货币余额（用户 · 余额）· 货币流水（earn / spend · 来源 · 金额 · 时间）· 商品目录（道具配置）· 用户背包（拥有 · 是否穿戴 · 穿戴位）· 每日获取计数（防刷）。**全部带 `mode`（§17.3）；demo 经济与 live 隔离，不进正式指标。**

点击发放至少补齐以下字段与约束：

- **货币余额**：`user_id`、`balance`、`version`（并发更新）、`mode`、`updated_at`。
- **货币流水**：`transaction_id`、`user_id`、`direction`、`source`、`amount`、`balance_after`、`request_id`、`occurred_at`、`mode`；`request_id + mode` 唯一，保证重复点击请求不重复入账。
- **每日点击计数**：`user_id`、`business_date_bj`、`click_earned`、`clicks_since_last_drop`、`current_target_clicks`、`current_reward_index`、`cap_reached_at`、`mode`；`user_id + business_date_bj + mode` 唯一。`current_target_clicks` 仅服务端可见。
- **发放配置**：`daily_click_cap=10`、各露珠序号对应的 `target_click_options` 与 `target_click_weights`、有效点击节流参数；由服务端配置中心维护并支持灰度，不由前端常量决定。
- 每获得一个露珠后才为下一个露珠抽取并保存 `current_target_clicks`；未到账前不得因刷新、重进或请求失败重新抽取。
- 一次点击判定、余额更新、流水写入与每日计数更新必须在同一服务端事务中完成；任一环节失败则整体失败，前端不得显示到账。

## 22 · 总结

蛋宝宝普通小程序 V2 的核心不是堆玩法，而是跑通一个**实体蛋服务 + 互动 + 对话 + 情绪价值**闭环，并让产品定位、实际功能、数据和提审材料保持一致：

**我绑定自己的实体蛋宝宝 → 想来时摸摸它、装点蛋壳或说句话 → 它用身体和第一人称回应我 → 到约定时间完成破壳 → 留下一份收藏卡作为纪念档案 → 此后我愿意回来和它聊聊、看看它今天想说什么。**
