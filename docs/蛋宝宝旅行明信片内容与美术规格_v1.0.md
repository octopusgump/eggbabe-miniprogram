## 1. 已确认的产品决策

1. **东京保留为正式旅行目的地**，与大理、北京、西双版纳同级。
2. ta 处于旅行状态时，生活空间仍显示**空着的家＋第一人称远方文字**；用户不能对话、写信、留言或回信，主页不显示景区图或旅行中的角色。
3. 旅行景色和 ta 的旅途动作从**独立明信片列表与详情**进入；点击明信片大图后，可进入沉浸式的旅途回放场景。
4. 目的地旅途插画默认在 ta 从旅行状态回到家后送达，使“空房说明离开、明信片证明经历”形成完整叙事。
5. 明信片插画全部是预制审核资产，不在用户端实时生成，不使用用户上传图片，不使用第三方摄影作品作为图生图输入。
6. 明信片是纯内容，不是奖励、卡池或收藏系统；不显示总数、空位、稀有度、进度、连续收信或“还差几张”。

## 2. 用户体验与送达时序

### 2.1 旅行期间

1. 服务端把当前大场景设为 `travel`，并返回正式 `destination_id`。
2. 三屏生活空间显示空着的家，不加载目的地插画。
3. 页面显示一句来自目的地的第一人称短文案。
4. 旅行时左下入口留空，不显示信封；V3.6 / V3.7 不显示主动明信片未读提示或入口。

### 2.2 返回之后

1. 当状态从 `travel` 切回 `home` 时，服务端可随该次旅程送达一张 `travel_memory` 明信片。
2. 新明信片只使用无数字红点提示；用户实际打开后才标记已读。
3. 明信片正面展示预制旅途插画；标题、日期和正文由原生 UI 渲染。
4. 页面与图片作为后续版本储备保留；V3.6 / V3.7 正式用户不可打开明信片列表。

### 2.3 主动旅行明信片

| 类型 | 触发 | 图片 | 内容 |
|---|---|---|---|
| `travel_memory` | ta 完成一次旅行并回到家 | 必须绑定已审核的目的地插画 | 一段具体的旅途观察与感受 |

`travel_memory` 只由服务端主动送达，不得包装为完成任务后“获得”的奖励，也不由用户写信、留言或回信触发。

### 2.4 同一次旅程的明信片与场景回放

- 明信片列表按旅程聚合：同一个 `journey_id` 只显示一个入口，例如“东京之旅”。
- 列表封面可以选用该次旅程中最有代表性的一张插画。
- 点击旅程入口后先进入明信片详情；点击明信片大图，再进入独立的沉浸式“旅途回放”场景。
- 旅途回放复用破壳后生活空间的全屏观看逻辑，按固定顺序横向移动到同次旅程的其他时刻。
- 东京旅程可以同时包含 `alley` 咖啡巷和 `terrace` 城市露台；滑到新场景时只更新场景标题。
- 旅途回放是历史记忆，不是 ta 此刻所在的实时场景；横向浏览不得调用状态、动作或场景切换接口，不改变 ta 当前所在状态。
- 不同日期或不同故事线的两次东京旅行使用两个 `journey_id`，在列表中分别显示。
- 明信片详情不显示胶囊形“左右滑动”假按钮；多张图片不显示“1/12”、空位或收集进度。

### 2.5 旅途回放的能力边界

- 当前 1600×900 候选图已把环境、玉兔、动作、道具和阴影合成在同一张图中，因此首版提供全屏观看、横向场景移动和原生文案层。
- 首版不伪造玉兔可自由行走、独立动画或道具热点；这些交互需要额外的无角色环境底图、透明角色动作、遮挡层与热点配置，通过新的美术和状态验收后再开放。

## 3. 内容数据结构

服务端必须下发明确结果，前端不得随机选择正式明信片。

### 3.1 旅程列表项

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 列表项实例 ID |
| `type` | 是 | 固定为 `travel_memory` |
| `journey_id` | 旅行卡必填 | 同一次旅程的稳定 ID |
| `destination_id` | 旅行卡必填 | `dali`、`beijing`、`xishuangbanna`、`tokyo` |
| `cover_asset_key` | 有插画时必填 | 旅程列表封面 |
| `title` | 是 | 用户可见标题 |
| `source_slot_id` | 旅行卡必填 | 对应旅行状态段，用于幂等，不向用户显示 |
| `sent_at` | 是 | 服务端业务时间 |
| `delivered_at` | 是 | 服务端业务时间 |
| `read_at` | 否 | 用户实际打开后写入 |
| `postcards` | 旅行卡必填 | 按 `sequence` 排列的已送达明信片数组 |

内部可以使用 `source_slot_id` 防止重复送达，但不得据此生成前台次数、连续天数或收集进度。

### 3.2 旅程内明信片

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 单张明信片 ID |
| `scene_id` | 是 | 目的地内固定视觉场景，例如 `alley`、`terrace` |
| `action_id` | 是 | 插画中的唯一主动作 |
| `character_id` | 是 | 例如 `jade_rabbit` |
| `asset_key` | 是 | 指向已批准的正式图片资产 |
| `scene_label` | 是 | 滑动到本张时显示的场景名 |
| `action_label` | 是 | 本张动作标题 |
| `body` | 是 | 本张第一人称正文 |
| `sequence` | 是 | 同一旅程内的固定浏览顺序 |

## 4. 内容写作规格

### 4.1 标题

- 建议 6–12 个汉字。
- 指向一个具体瞬间，不使用营销标题或攻略口吻。
- 不使用“第几站”“限定”“隐藏款”“解锁”等游戏化词语。

### 4.2 正文

- 建议 45–90 个汉字，第一人称。
- 结构优先采用：**一个具体观察＋一个小动作或小失误＋一句自然感受**。
- 可以想起用户，但不得表达等待、责备、被抛弃或催促回来。
- 不编造真实商店、品牌、价格、交通时刻或需要实时核验的事实。
- 不使用用户画像、互动次数或离开时长生成内容。

### 4.3 东京语言气质

- 安静、细小、生活化，避免“打卡攻略”和赛博朋克刻板印象。
- 可写晨光、木巷、落叶、自动贩卖机的机械声、远处东京塔、露台风、城市灯光和晴天远望富士山。
- 不出现真实门店、品牌饮料、商业 Logo 或带地址的招牌。

### 4.4 东京示例

**标题：巷子里的第一罐热饮**

> 我在木头小巷里选了很久，最后抱走了一罐没有名字的热饮。拉环响了一声，远处的塔刚好被晨光照亮。

**标题：风把耳朵吹向富士山**

> 露台的风比我想的轻，只把耳朵吹歪了一点。我捧着杯子看了好久，城市醒来时其实没有什么声音。

## 5. 正式目的地内容边界

| 目的地 ID | 核心视觉母题 | 允许的日常观察 | 禁止方向 |
|---|---|---|---|
| `dali` | 风、山水、白墙灰瓦、开阔天空 | 风吹帽子、看云、安静散步 | 直接复制第三方旅行照片或网红店 |
| `beijing` | 胡同尺度、砖木、城市历史层次 | 院门、树影、冬日热饮 | 真实机构标识、政治性地标误用、商业招牌 |
| `xishuangbanna` | 热带植物、傣锦手作、湿润暖光 | 看织机、摸叶片、雨后气味 | 民族符号拼贴、宗教元素娱乐化 |
| `tokyo` | 暖木咖啡巷、无品牌贩卖机、东京塔、城市露台、富士山远景 | 自拍、热饮、落叶、相机回放、许愿 | 品牌、可读日文招牌、霓虹赛博化、镜头随动作漂移 |

目的地名称可以作为地名使用；任何第三方商业主体的名称、Logo、包装、门店外观和可识别广告均不得出现。

### 6.2 首发门槛

- 东京首发至少需要 **8 张**用户最终确认的正式明信片插画。
- 建议由咖啡巷 4–6 张、清晨露台 1–2 张、暮色露台 1–2 张组成。
- 东京首发在明信片列表中只显示一个“东京之旅”入口，咖啡巷与城市露台在入口内部连续浏览。
- 同一动作只保留一个正式版本；旧版、失败版和未确认版不得进入正式目录。
- 现有候选图片不因“东京成为正式目的地”自动升级为正式资产，仍需逐张终审。

- 清晨露台：捧热饮看富士山、晨间伸展。
- 暮色露台：自拍、面向富士山许愿。

以下动作如进入扩展池，必须从四视图＋锁定底图重新生成 v03，不得复用已删除问题图：

- 抱饮料罐、抱纸袋快步走、探头看咖啡桌、小桌摆两杯饮料；
- 贴近贩卖机挑饮料、踮脚按贩卖机、抱膝发呆、画无字明信片。

## 7. 美术交付规格

### 7.1 文件

| 项目 | 规格 |
|---|---|
| 画布 | 1600 × 900，16:9 横图 |
| 色彩 | RGB |
| 透明度 | 不透明，Alpha=0 |
| 格式 | WebP |
| 压缩 | q82 左右，以主体和材质无明显损失为准 |
| 建议大小 | 单张不超过 500KB |
| 画面文字 | 不允许；标题、日期和正文由原生 UI 渲染 |

严禁通过分别强制宽度和高度的方式把图片压成 1600 × 900。源图必须为 16:9；后处理只允许等比缩放与必要的极小裁切，不得拉伸或压扁角色、圆形物件和建筑。

### 7.2 整体风格

- 温暖治愈、精致清楚的 2.5D 房间式空间。
- 浅木、织物、陶器、植物和石板 / 木地板具有可触摸材质。
- 景深柔和但不能糊成色块；主体边缘、木纹、bouclé、叶片和接触阴影必须清楚。
- 东京塔、富士山和城市只提供目的地识别，不压过角色与动作，也不做海报式夸张。

### 7.3 玉兔身份锁定

唯一身份参考：

`/Users/octopusgump/Library/Mobile Documents/com~apple~CloudDocs/ClaudeCowork/蛋宝宝_eggbabe/01_IP角色设计/01_玉兔 Jade Moon Rabbit/00_View_References/01_Character_Turnaround/JadeRabbit_ReferenceSheet_Standard_02.webp`

必须满足：

- 暖奶油色 bouclé 绒线材质；
- 宽圆、紧凑的一体式蛋形头身，不能拉长、变瘦或压扁；
- 两只长耳、大而有高光的深色眼睛、蓝色小鼻子、蓝色腮边刺绣；
- 背面动作可见小圆尾巴；
- 不穿衣服，不新增第二角色；
- 完整身高锁定画高 32%–36%，低于 30% 或高于 38% 直接淘汰；
- 身体必须保持足够体积，不能只有大头长耳和过小躯干；
- 腿与脚短小、圆润、近乎直立，不出现长腿、弯曲膝关节或普通兔子的后腿结构；
- 动作不能改变头身、耳朵、五官或四肢比例。

### 7.4 场景与镜头锁定

- 每张只使用“玉兔四视图＋本张锁定底图”作为参考输入。
- 提示词必须包含：`preserve base image composition exactly; change only by adding one Jade Moon Rabbit and this action`。
- 不得改变镜头高度、裁切、地平线、消失点、地面位置、建筑、道路、东京塔、富士山、家具、植物、灯光方向或既有道具布局。
- 不得把上一张动作图作为下一张的环境参考。
- 不得为了容纳动作而缩放整张底图、重建巷子或移动露台边缘。

### 7.5 动作与空间逻辑

每张只有一个主动作和必要道具。生成前必须明确：

1. 角色站、坐或支撑在哪个表面；
2. 身体朝向哪个操作面；
3. 双脚、臀部或双爪如何承重；
4. 道具是否能被现有姿势真实操作；
5. 阴影应落在哪里。

硬规则：

- 坐着画画时必须自然面向桌面，凳子方向、桌沿、手、笔和纸构成可操作关系；
- 不得出现屁股朝向操作面、隔着家具操作、手穿过桌面或座位不可达；
- 跳跃只做离地很低的小跳，角色不能因动作被缩小；
- 踮脚时双脚仍有明确接触，不得悬浮；
- 抱膝动作不得生成长腿或弯折膝关节；
- 倒立仅在双爪真实压地、耳朵不承重且身体比例不变时保留。

### 7.6 光影与接地

- 角色、动作道具、环境、遮挡和阴影必须一次同图生成。
- 脚、爪或坐姿支撑面必须完全接触地面 / 凳面。
- 接触阴影短、紧、方向与底图一致。
- 禁止白边、透明扣图后贴、贴纸感或漂浮。

### 7.7 合规禁止项

- 可读文字、品牌、Logo、二维码、UI、水印、边框和标题；
- 第二角色、人物、交通工具或与动作无关的新道具；
- 第三方照片、社交平台图片、品牌包装或门店外观作为生成输入；
- 普通兔子体态、服装、额外肢体、缺耳、五官错位或形变；
- 霓虹赛博朋克化、过度模糊、过度锐化或与 EggBaby 房间风格不一致。

## 8. 生成与验收流程

### 8.1 单张生成

1. 选择已经确认的锁定底图。
2. 输入仅包含玉兔四视图与锁定底图。
3. 明确动作、角色落点、朝向、承重面和目标身高。
4. 一次生成完整环境中的角色、动作、道具、遮挡和阴影。
5. 不合格时重新从四视图＋原底图生成，不从失败动作图迭代。

### 8.2 自动检查

- 文件名符合规则；
- 1600 × 900；
- WebP、RGB、不透明；
- 文件可正常解码；
- 项目候选目录无临时 PNG。

### 8.3 人工视觉检查

| 维度 | 验收问题 |
|---|---|
| 画布 | 是否发生拉伸、压扁或非等比缩放 |
| 构图 | 是否与锁定底图保持相同镜头、透视和物体布局 |
| 比例 | 玉兔完整身高是否在 32%–36%，身体是否仍宽圆饱满 |
| 解剖 | 耳朵、眼睛、鼻子、刺绣、尾巴、短腿和四肢数量是否正确 |
| 动作 | 动作是否一眼可读且符合身体结构 |
| 空间 | 桌椅方向、朝向、承重、遮挡和道具关系是否符合逻辑 |
| 接地 | 是否有真实接触面、短接触阴影和一致光向 |
| 清晰度 | bouclé、木纹、织物、植物、地面和城市细节是否可读 |
| 合规 | 是否无文字、品牌、Logo、二维码、UI 和第二角色 |

### 8.4 状态

| 状态 | 含义 |
|---|---|
| `candidate` | 已生成，尚未由用户终审 |
| `needs_rework` | 已发现明确问题，不能接入 |
| `rejected_deleted` | 用户淘汰并已删除，问题写入清单 |
| `approved_for_promotion` | 用户逐张确认，可准备正式资产 |
| `runtime` | 已复制到正式目录、配置资产键并完成回归测试 |

模型或自动检查不得直接把图片标记为 `approved_for_promotion`；最终视觉批准权属于用户。

## 9. 命名与目录

### 9.1 候选文件

`postcard_travel_<destination>_<scene>_<action>_<character>_vNN.webp`

例如：

`postcard_travel_tokyo_alley_bench_selfie_jade_rabbit_v03.webp`

候选文件保存在 `_candidates/` 下，不进入运行时配置。

### 9.2 正式文件

正式晋级后使用不带生成轮次的稳定文件名：

`postcard_travel_<destination>_<scene>_<action>_<character>.webp`

对应资产键：

`postcard.travel.<destination>.<scene>.<action>.<character>`

例如：

`postcard.travel.tokyo.alley.bench_selfie.jade_rabbit`

- 本规格确认东京的产品身份；当前东京候选图只接入微信开发版验收预览，不代表已进入正式运行时。
