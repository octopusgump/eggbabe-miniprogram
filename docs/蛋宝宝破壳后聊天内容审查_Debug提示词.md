三、已确认的产品与内容原则（不可自行改写）
────────────────

1. 适用范围仅为“破壳后”的**居家文字聊天**。不包含语音输入、语音回复、实时通话、群聊、写信、留言、回信。
2. 破壳前没有语音聊天入口；不要把破壳前的其他文本互动误判为本功能。
3. 正式内容规则统一由服务端执行：空白、最大 120 个 Unicode 字符、敏感个人信息、一般违规、危机表达、输出审核、模型兜底、上下文、人设、记忆、限流、审计、保存与删除。
4. App 可以把纯空格草稿的发送按钮置为不可点，避免误触；这只是交互保护，不能作为服务端规则的替代。服务端仍必须拒绝任何绕过 App 的空白输入。
5. 用户点击发送后，App 可以立即创建本地 `pending` 气泡；只有服务端成功确认后才可显示为 `sent` 和展示回复。
6. App 的 `chatReply` 请求只能包含：`egg_id`、原始 `message`、稳定的 `client_message_id`、`request_id` 和必要运行环境字段。不得上传 `history`、`scene_context`、本地内容标签或安全判断。
7. 危机表达必须以服务端的 `CRISIS_REPLY` / `safety_result=crisis` 为准。App 只原样展示已审核文本，不判断、不改写、不生成模板；危机相关信息不得进入用户画像、广告、成长值或本机长期正文缓存。
8. 一般输入拒绝由服务端返回 `INPUT_REJECTED` 与已审核提示。App 移除临时气泡、恢复草稿、显示服务端提示，不提供原地重试。
9. 网络失败或超时：临时气泡原地变为 `failed`，可重试；重试必须复用同一条消息、同一 `client_message_id` / 幂等键，不得增加重复气泡、重复模型调用或重复落库。
10. 服务端返回 `TALK_NOT_AVAILABLE`：App 移除未确认临时气泡、保留草稿，切换为不可聊天状态；不把它标记为普通失败，也不允许重试。
11. 未送达的 `pending` / `failed` 消息：只在 App 未彻底关闭前保留在页面内存；完全退出 App 后，不得把聊天正文或失败消息持久化到本机。已确认的聊天记录由服务端保存和返回。
12. 历史记录首屏 20 条、向上按游标加载更多、以服务端消息 ID 去重。App 只展示服务端 `created_at`，不使用设备当前时间伪造历史时间。没有历史时可显示不重复落库的场景开场白。
13. 不做关系等级、好感度、连续聊天奖励、成长值、催促聊天、广告定向或“在线状态”。

### A. 破壳状态与聊天入口

- 未破壳、没有蛋、蛋不属于当前用户、生命周期非 `HATCHED` 时，入口和聊天页分别会怎样？是否会被绕过？
- 居家 `available` 时，是否可以稳定进入完整聊天页？是否存在场景内输入框或重复入口？
- `away` / `unavailable` 时，左下角是否仍有同一图标的置灰小按钮？是否有图标缺失、不可见、点击无反馈、文案丢失或仍能进入聊天的情况？
- App 是否错误依赖本地 `atHome` / 场景来决定权限，或服务端 `chat_access` 缺失时错误放行？
- 分享、旧路径、状态切换中直接进入聊天页时，是否得到明确不可聊天页？是否错误展示历史、输入框或重试？

### B. `chat_access` 服务端合同

核验 `getPostHatchHome` / snapshot 对以下字段的读取、转换、异常处理与展示：

```json
{
  "chat_access": {
    "status": "available | away | unavailable",
    "reason": "AT_HOME | AWAY | LIFECYCLE | SYSTEM",
    "message": "服务端审核过、可直接展示的用户文案",
    "next_available_at": "ISO 8601 或 null"
  }
}
```

- 字段缺失、枚举非法、网络失败、旧接口字段命名差异时，App 是否安全地按 `unavailable` 处理？
- `reason` 是否被错误展示给用户？`message` 是否被 App 改写？`next_available_at` 是否被本地猜测？
- CTO 的权威字段与 `chatReply` 二次拦截是否都有契约证据；若 App 只能 mock，必须明确标注“待 CTO 联调”，不能伪称已完成。

### C. 发送、输入与内容安全边界

- 空白输入时，按钮是否禁用且不会生成气泡；同时检查是否仍由服务端兜底拒绝。
- 检查 App 有没有本地 120 字截断/阻断、手机号/身份证/邮箱识别、敏感词识别、危机关键词、固定安全回复或本地人设回复；这些都属于错误架构，必须列出残留证据。
- 检查请求体是否真的只有最小字段；是否泄露 `history`、场景、用户属性、内容标签、安全结论、模型参数或其他不应上传的数据。
- `INPUT_REJECTED` 的错误码是否完整识别（含空白、超长、隐私、一般违规的服务端结果）；临时气泡是否移除、草稿是否原样恢复、服务端提示是否清晰且不会重复显示。
- `CRISIS_REPLY` 是否只展示服务端文字，且没有 App 本地判断或替换；日志/埋点/缓存是否泄露危机标签或正文。
- 输出内容是否仅接受服务端确认的合法 `REPLY` / `CRISIS_REPLY` 结构；字段缺失时是否错误当成功显示。

### D. 发送状态、超时、取消与幂等

- 检查 `pending` / `sent` / `failed` 的完整状态机和 UI 是否一致；用户是否能在 pending 时重复发送。
- 网络错误、10 秒超时、服务器 5xx、字段非法、页面隐藏、页面卸载、重新进入、同一消息重试时，气泡、等待动画、按钮、草稿分别如何变化？
- 请求是否真的可 `abort()`；成功后是否清理超时器；旧请求晚到能否追加第二条回复或覆盖新状态？
- 重试是否复用同一个 `client_message_id` 和 `request_id`；是否会增加第二个气泡、第二次模型调用或重复落库风险？
- 是否把 `TALK_NOT_AVAILABLE` 错当作可重试网络失败？

### E. 聊天记录、连续性与本地存储

- 首屏历史、上拉分页、失败重试、稳定顺序、ID 去重、滚动锚点和“已加载至最早记录”是否按服务端游标实现？
- 重新进入、切后台再回来、账号切换、同一条消息响应丢失后，是否会丢已确认消息、重复显示、错误追加开场白或混入另一只蛋/另一账号的记录？
- 实时 `chatReply` 是否读取并使用服务端 `user_message.message_id`、`reply.message_id`、`created_at`；缺失权威 ID 时是否拒绝显示为“已确认”？
- 确认 App 不把历史正文、pending、failed 或草稿写入 `wx.setStorage` / safe-storage / pet-store。若有任何持久化，列为问题并说明风险。
- 服务端历史读取失败时，App 是否诚实显示加载失败和重试，而非用本地固定回复伪造历史。
- 审查删除、注销、隐私策略与聊天记录之间的承诺是否一致。服务端保存期限、删除执行、危机最小审计留存不应由 App 推断或实现。

### F. 内容呈现与用户体验

- 顶部是否显示已批准的角色头像、昵称和当前状态；未命名时是否正确回退为“蛋宝宝”。
- 已批准头像资源是否在聊天页和生活空间入口正确接入、体积合理、不会因白底/透明背景在浅色界面中消失。
- 发送按钮：非空时是否显示紧凑的 SVG 向上箭头按钮；空白时是否禁用、可理解且不会误导为“已发送”。
- 输入 placeholder 是否垂直居中，键盘弹出、iPhone 安全区、安卓长屏、长消息时是否遮挡最后一条内容。
- pending、failed、等待三点、历史加载失败、不可聊天页的文案、视觉层级、重试入口、触控面积、按压反馈、错误态、弱动效是否符合设计规范。
- 检查是否出现与人设冲突的系统提示、测试文案、模型/审核/供应商术语、奖励化话术或“在线”暗示。

### G. 环境、接口与发布阻断

- develop 是否仅使用明确 demo fixture；trial 是否指向 staging；release 是否指向 production。
- trial/release 未配置 `apiBase`、合法域名、认证或正式接口时，是否明确阻断并报出可理解错误，而不是静默回退 demo / 本地固定回复。
- 正式聊天是否存在未配置却假装 `backendEnabled` 的情况；测试是否可能掩盖 live 缺口。
- `chatReply` 服务端必须完成的鉴权、蛋归属、HATCHED、`chat_access.status=available` 二次校验、幂等、限流、审计、输入/输出安全、模型兜底、原子落库，请按 CTO 交接项逐条核验接口是否具备或仅是 App 假设。
