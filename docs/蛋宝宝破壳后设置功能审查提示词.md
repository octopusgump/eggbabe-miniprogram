二、已经确认的产品边界
────────────────

1. 本次重点是“破壳后”的用户，但账户、隐私、注销入口不应因生命周期变化而不可访问。
2. 破壳完成后，“破壳提醒”已经没有业务意义，不应继续展示、默认开启或请求对应订阅模板。
3. V3.6 / V3.7 正式版不得展示收藏卡、明信片、纪念物、旅途回放、限定上新或其他尚未正式发布内容的通知入口。开发版保留代码不等于正式用户可见。
4. 本产品不做成长、关系、好感度、连续打卡、任务、货币、背包、库存、广告定向、用户画像或自动化推荐设置。不得借“通知设置”增加这些能力。
5. 通知开关不是“用户点一下就算开启”：微信模板授权、模板可用性、用户偏好保存、跨设备同步、实际发送频率和发送审计，都必须由服务端作为最终事实来源。
6. App 只能负责：展示服务端状态、让用户主动发起授权、显示加载/成功/失败/重试、清理本机缓存。App 不得伪造正式授权、正式删除、正式注销完成或正式通知状态。
7. 聊天正文、危机表达标签、安全评分、模型提示词、模型历史和用户敏感输入不得进入设置埋点、通知偏好、用户画像或本地长期缓存。
8. 当前已确认的聊天数据策略：未送达消息只在 App 未彻底退出前保留在页面内存；完全退出后不在本机持久化聊天正文或失败消息。
9. 退出登录只清理本机缓存，不等于注销账号、更不等于删除服务端聊天记录。注销必须由服务端执行，并按隐私协议处理。

四、必须验证的已知风险（逐条给证据）
────────────────

不要假设下面问题一定存在；请逐项用代码证据验证，并给出文件和行号。

A. 破壳后仍出现“破壳提醒”
- 检查此开关的展示条件、默认值、保存方式、触发模板和生命周期判断。
- 判断它在“已破壳”时是否仍可见、是否仍能请求订阅消息、是否会误导用户。

B. “节令上新”开关的可用性与发布范围
- 检查点击开启时调用的函数是否真实导出、是否真实存在、是否有模板 ID。
- 检查“节令上新/限定内容”是否违反 V3.6 / V3.7 正式范围。
- 如果方法不存在、模板未配置或功能未发布，明确说明用户点击后的实际后果。

C. 通知开关的真实状态
- 检查开关默认值是否把“尚未授权”误显示成“已开启”。
- 检查用户拒绝微信订阅授权、网络失败、服务端写入失败、重复快速点击时，页面最终显示什么。
- 检查是否有加载态、禁用态、失败提示、重试路径和状态回滚。
- 检查不同模板是否错误共用同一个“拒绝过”状态。
- 检查 App 写入的是账号隔离的缓存还是全局缓存；账号 A 的偏好是否可能显示给账号 B。

D. live 与 demo 的权威性
- 检查系统设置是否只写本地，是否缺少服务端读取/写入/跨设备同步。
- 检查正式环境在接口或模板未配置时，是否会静默表现为已开启或回退为 demo。
- 检查 `mode`、会话、账号归属和请求合法域名的边界。

E. 个人信息、退出登录与会话
- 头像、昵称的本地校验和服务端校验各自负责什么；服务端是否仍可绕过 App 的本地限制。
- 退出登录时清除了哪些数据：用户、蛋、会话、通知偏好、同步队列、埋点队列、聊天页面内存。
- 是否有未确认写入丢失、账号切换残留、旧会话继续访问或“本地退出被误写成服务端注销”的风险。

F. 注销、隐私与聊天记录
- 审查注销页的承诺、隐私协议的承诺、现有 `manageDeletion` 接口和技术规格是否一致。
- 明确哪些必须由 CTO 执行：冷静期、取消、到期删除、账号/蛋解绑、聊天记录处理、安全审计最小留存、旧会话失效、删除审计。
- 明确哪些必须由法务确认：保存期限、例外留存范围、隐私协议版本/生效日期、第三方处理者和用户权利路径。
- 绝不能建议 App 用“清除本地数据”替代正式注销。

G. 设计与可用性
- 按 eggbabe-DESIGN.md 检查：44–48px 最小触控面积、按钮形态、错误色、加载态、禁用态、按压反馈、弱动效、安全区、小屏和长文案。
- 检查开关行是否能准确表达状态，而不是只给一个无上下文的布尔开关。
