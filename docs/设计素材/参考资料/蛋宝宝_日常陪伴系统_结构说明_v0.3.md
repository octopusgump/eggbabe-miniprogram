## 1 · 总体链路

```
一个 IP
   │  进入小程序
   ▼
宠物今日心情  ← Emotion Engine 驱动
   │
   ├──► 宠物此刻状态  ← Story Engine 驱动（每 5 小时更新）
   │        └──► 场景内交互（对应动作 + 可选说话）
   │                 └──► 纪念物产出（与场景绑定）
   │
   ├──► 纪念物
   │
   ├──► 明信片
   │        └──► 有新消息（主动明信片的无数字提示）
   │
   └──► 收藏卡
```

一句话概括：**一个 IP 在小程序里有「今日心情」这个总入口，往下分出五条支线；其中「此刻状态」是内容量最大的一条，负责让 ta 看起来真的在过自己的日子。**

### 1.1 空间模型：从一张桌子到一个横向展开的世界

这套结构**破壳前就存在**，破壳前后是同一个主循环。差别不在「有没有」，而在**世界的物理边界有多大**。

#### 1.1.1 两个阶段的视野

| 阶段 | 视野 | 横向滑动 | 窗户 |
|---|---|---|---|
| 破壳前（孵化期） | **单屏 · 桌面** | **不可滑动** | 桌面屏内的点击热点 → 张望视图 |
| 破壳后 | **三屏** | 左右可滑 | 仍可点击；右屏另有内容 |

```
破壳前：              ┌───────────┐
                     │  桌面      │   ← 不可滑动
                     │  蛋 + 窗   │      窗为点击热点
                     └───────────┘

破壳后：  ┌────────┬───────────┬────────┐
         │ 起居区  │   桌面     │  扩展区 │   ← 左右可滑
         │ 床/台灯 │  ta + 物件 │ ⚖️ 待定 │
         └────────┴───────────┴────────┘
             ↑                      ↑
         破壳新解锁              破壳新解锁
```

**孵化期不教滑动。** 新用户第一次进来只需要理解一件事：这是我的蛋，它在桌上。多一个手势就多一层认知成本，而孵化期的核心目标是让用户尽快开始养，不是尽快学会导航。**滑动是破壳之后才出现的动词。**

变化感由**窗外的景色**承担：桌面屏背景里的那扇窗，其景色随本机日间 / 日落 / 夜晚、季节与稳定天气变化。**用户不需要移动，世界自己在变。** 环境刷新边界为 00:00 / 06:00 / 17:00 / 19:00，均以淡入淡出过渡；这一条同时解决了孵化期的内容轮换问题——不加任何页面、不加任何手势。

#### 1.1.1.1 孵化期首页入口与一级导航（已实现）

孵化期仍然是单屏空间，入口只是浮在空间上方，不把首页重新变成功能列表：

```
                                  ┌──────────┐
                                  │ 小图标   │
                                  │ 许愿池   │
                                  ├──────────┤
                                  │ 小图标   │
                                  │ 早教班   │
                                  └──────────┘
                                      ○ 画画

                                  ○ 我的（右下）
```

- 许愿池与早教班组成右侧竖向半透明悬浮容器，采用「上方小图标 + 下方短标题」，两项等高并以细分隔线区分；
- 实现尺寸为 `112rpx × 248rpx`、圆角 `56rpx`、右侧间距 `34rpx`，背景约 82% 暖白，使用低对比边框和轻阴影；底部位置叠加安全区；
- 蛋壳创作保持独立小圆按钮，位于组合入口下方，与组合入口间距 `20rpx`。它是场景工具，不是第三个修炼手册栏目；
- 未解锁和当天已回答只改变入口可用状态，不显示完成勾、次数、奖励或催促；重复进入沿用既有页面结果和记录，不重复提交；
- 整块底部 Tab 已移除。首页右下只保留 `88rpx × 88rpx` 白底圆形「我的」图标；「我的」页不显示右下返回按钮，改用左上返回，有页面栈时回上一页、页面栈为空时回到蛋宝宝首页；
- 按压只做轻量视觉反馈；弱动效模式不播放持续呼吸、弹跳或位移。

#### 1.1.2 窗户：贯穿破壳前后的「远方」通道

窗户是**全周期可用**的特殊交互点，也是整个空间模型的情感枢纽。统一为三段式：

| 阶段 | 内容 | 触发 |
|---|---|---|
| **房间中的日常窗户** | 当前季节、昼夜与天气，直接显示在房间窗玻璃中 | 自动变化 |
| **日常窗外详情** | 当前 Window Weather 全屏展开，叠加真实天气、五时段代码动效与第一人称陪伴气泡；本版不显示蛋 / 角色背影 | 点击房间窗户 |
| **魔法窗外** | 大理、北京、西双版纳等远方景区 | 在日常窗外详情中点击远方微光；正式景区图完成后开放 |

这一层解决了一个之前没解决好的问题：**孵化期怎么给「远方」？**

日常窗外先让用户和蛋安静看当下的天气；魔法窗外再承接远方想象。两者不混用：日常窗外使用真实天气，魔法窗外使用预制景区图。

#### 1.1.2.1 日常窗外陪伴文案（已实现）

进入日常窗外详情时，画面保持真实天气和当前时段不变，底部陪伴气泡从固定审核池随机选择一句。**随机的是陪伴表达，不是窗景。**

| ID | 第一人称文案 |
|---|---|
| WINDOW-F01 | 我陪你一起看窗外 |
| WINDOW-F02 | 我在这里，和你看同一片天空 |
| WINDOW-F03 | 我想和你再安静地待一会儿 |
| WINDOW-F04 | 我也在看，云走得好慢呀 |
| WINDOW-F05 | 我听见风了，你听见了吗 |
| WINDOW-F06 | 我把这一刻轻轻记住啦 |
| WINDOW-F07 | 我喜欢这样陪你看远方 |
| WINDOW-F08 | 我想把窗外的光分给你一点 |
| WINDOW-F09 | 我和你一起等天空慢慢变色 |
| WINDOW-F10 | 我会陪着你，看风景慢慢经过 |
| WINDOW-F11 | 我在想，今天的天空也很温柔 |
| WINDOW-F12 | 我想和你一起听窗外安静下来 |

运行规则：

1. 每次进入随机选一句，并排除上一条，避免连续进入看到同一句；
2. 用户点击气泡后，旧句先淡出，再换成一条不同文案并淡入；正常模式淡出和淡入各约 `220ms`；
3. 切换期间锁定重复触发，防止快速连点导致跳字、叠加计时器或连续闪烁；离开窗景时清理计时器；
4. 弱动效模式将单段过渡缩短为 `20ms`，不增加位移、缩放、呼吸或弹跳；
5. 文案是本地临时展示，不落库、不计次数、不参与画像、性格、推荐或业务结果；
6. 气泡沿用 80% 暖白背景、自然绿色文字、圆角与轻阴影，并为点击提供无障碍按钮语义。

#### 1.1.2.2 日常窗外时段动效与清晨鸟影（已实现）

日常窗外详情不是静态放大图。它复用服务端上海天气，并按上海太阳时间选择早晨、正午、午后、日落、夜间五档代码动效：

| 时段 | 主要效果 |
|---|---|
| 早晨 | 柔和斜射光、低密度浮尘、7 只低透明度环境鸟影 |
| 正午 | 窄而稳定的顶部光束、少量浮尘 |
| 午后 | 暖光向窗景另一侧缓慢移动 |
| 日落 | 金橙色斜光、暖色浮尘与低频掠光 |
| 夜间 | 晴夜低频微光；雪后夜间补充冰晶微光 |

天气优先于时段：阴天关闭直射光；雨、雷雨、雾、雪关闭晴天光束并继续使用天气 Canvas；风、雨后、雪后只保留相容的弱光效果。清晨鸟影只在非雨、雷雨、雾、雪、雪后的天气出现，阴天降低透明度。

清晨时，用户点击空白窗景会在点击位置附近随机出现一只代码鸟影，并在 `2s` 内淡出；最多同时显示 6 只。该互动不落库、不计次数、不改变天气、时段、画像或任何业务状态；点击返回按钮和陪伴气泡不触发鸟影。失败、重试、返回、离页和组件销毁时必须清理鸟影、计时器与动画帧。

弱动效模式停止持续光束、浮尘、环境鸟影、位移与闪电；点击生成的鸟只保留 `2s` 透明度淡出。当前版本不添加鸟鸣、环境声、背景音乐或其他音频，不申请音频权限。

#### 1.1.2.3 旅行期间主页用文字讲，旅途画面回家后放进明信片

**破壳后的旅行期间，三屏生活空间不出景区画面，用文字告诉用户 ta 去哪儿了。** ta 回家后，独立的旅行明信片可以展示预制目的地插画；明信片图不作为三屏背景，也不替代魔法窗外。

理由不只是省素材，而是这样更对：

**ta 出门了，家里就是空的。** 用户滑过三屏，垫子上没有 ta，床上也没有 ta，只有一句从远方来的话——

> 「大理的风比我想的大，我把帽子按住了一路。」

**一张空桌子比任何一张风景图都更能说明 ta 去了远方。** 画了大理的全屏图，用户是在看风景；留一张空桌子，用户是在想 ta 什么时候回来。后者才是陪伴产品要的东西。

这一条同时把三件事咬在一起：

| 事 | 形态 | 为什么 |
|---|---|---|
| 魔法窗外 | **图** | 隔着窗看远方，看的就是画面 |
| 旅行 | **文字** + 家里空着 | ta 不在，没有可看的画面 |
| 纪念物 | **图** | ta 回来了，东西是实的，落在桌上 |
| 旅行明信片 | **图** + 原生文字 | ta 回家后，把途中看见的画面寄给用户 |

**图的投入落在「远方的想象」「回来后留下的旅途画面」和「带回来的实物」上，中间那段路用文字走。** 旅行明信片的详细执行以《蛋宝宝旅行明信片内容与美术规格 v1.0》为准。

> 与交互形态天然咬合：ta 在远方 → 空房只读，无沟通入口（§4.2）。


#### 1.1.3 破壳解锁的两屏

**左 · 起居区（方向已定）**

床、台灯。ta 躺着睡觉、开灯关灯，ta 的作息起居在这里发生。

孵化期的蛋是被**放在**那里的：放在桌上的垫子上。它没有自己的位置。破壳后左边多出一张床——**有床意味着 ta 住在这里，而不是被摆在这里。** 用户手指第一次能往左滑的那一刻，感知到的是这个，不需要任何文案解释。

**右 · 布置区（方向已定：蛋壳创作的空间版）**

完整链路：

```
用户在画板上画一件自己喜欢的小家具 / 装饰
        ↓
AI 绘画把它转译成视觉风格统一的设计
        ↓
落到右侧布置区，用户可自由移动、安放
```

**AI 转译层是这个方案的关键，它的作用不是「画得更好」，而是「让用户的东西属于这个世界」。**

UGC 装饰最大的风险从来不是用户画得丑，而是**画风失控毁掉整体氛围**——一个精心做了几个月的暖调空间，被一件像素风的沙发彻底破功。AI 转译解决的正是这件事：用户保留创作的主权（是我画的、是我想要的那个东西），系统保留风格的主权（它看起来仍然属于这里）。**用户得到「这是我的」，产品得到「它还是它」。**

这也是它和「收集家具」路线的根本差别：那条路给的是**拥有感**，这条路给的是**创造感**。后者不需要稀缺性来支撑，因此不需要经济系统，因此不触碰 C-04。

**合规口径（需写进 PRD，供提审与法务留档）**

C-04 禁的是「商店、背包、购买、库存、装配、**摆放**、投喂**道具**」。本方案的关键在于：**被摆放的不是道具。**

| 判据 | 本方案 |
|---|---|
| 如何获得 | 用户自己画的，不存在获取行为 |
| 是否有拥有状态 | 无。不存在「已拥有 / 未拥有」两态 |
| 是否有稀缺性 | 无。不设总数、稀有度、限定 |
| 是否可交易 / 赠送 | 否 |
| 是否解锁其他内容或权益 | 否 |
| 是否影响实体结果 | 否 |

结论：这是 §8「免费蛋壳创作」的同一套逻辑，从蛋壳表面扩展到一块区域。

> ⚠️ **但「摆放」二字会撞门禁。** §22.3 是全局文案扫描，§21 验收清单也会逐条查 C-04。因此 PRD 里必须写一条**显式豁免**：用户自绘内容的自由放置不构成 C-04 意义上的道具摆放，理由为上表六条。这条豁免要由产品与法务共同签字留档，不能靠开发自行判断——体例参照 §7.13.6 连续登录压缩的处理方式。

**必须同时解决的三件事**

| # | 事项 | 说明 |
|---|---|---|
| 1 | **内容安全** | 用户手绘 → AI 转译 → 落库展示，**输入与输出都要过检测**。手绘的风险低于照片上传（无真人、无第三方版权），但仍可能画出违规图形。转译后的成品也需检测后再落库 |
| 2 | **模型成本与限流** | 每创作一件家具就是一次图像模型调用。需设频率限制，并对结果做持久化缓存——生成一次、永久保存，不重复生成 |
| 3 | **不能长成背包** | 若允许保存多件家具，事实上就形成了一个「库」。**建议允许保存多件，但呈现上不得做成背包**：无格子、无数量角标、无「已创作 X 件」、无分类标签页、无空位。视觉上更接近「散落在旁边的几张画」，而非「一个物品栏」 |

**入口已定：破壳后的 AI 绘画工具，不设破壳后许愿池**

装饰创作的入口是一个**破壳后开放的 AI 绘画工具**。用户想布置了就打开它，画一件东西，AI 转译成统一风格，放进右屏。

| | 结论 |
|---|---|
| 破壳后许愿池 | **不做。** 该模块取消，PRD 无需新增规格 |
| 孵化期许愿池（§7.5） | 保持现状，每日选择题 + 预置回应，不受影响 |
| 装饰入口 | 破壳后开放的 AI 绘画工具，随用随开 |

> ✅ 与 §5.4 无冲突：整条链路在破壳后，AI 调用发生在破壳后，也不构成「孵化期行为 → 破壳后权益」。

**用量规则（已定版）：每天 3 次许愿**

- 工具的使用单位叫**许愿**，每个自然日 3 次；
- 用完后可以直接说「今天的许愿次数用完了」；
- 次数**不累积**、**不可购买**、**不可通过看广告获得**；
- 破壳后许愿池模块取消，PRD 无需新增该模块的规格。

**关于「显示剩余次数」的合规判断：可以做，但要写清楚为什么可以**

此前本文判断「展示剩余次数会撞 §6」，这个判断**过严了**。§6 管的是**任务感**，而用量上限不是任务：

| | 任务 / 打卡（§6 禁止） | 生成额度（本方案） |
|---|---|---|
| 用户需要完成它吗 | 是，是待办事项 | 否，是能力上限 |
| 完成后有奖励吗 | 有 | 无 |
| 是否构成解锁条件 | 是 | 否 |
| 不做会怎样 | 进度停滞、错过 | 什么都不会发生 |

AI 生成类功能展示每日额度是行业通行做法，与游戏化任务系统在性质上是两件事。

> ⚠️ **但必须在 PRD 里写一条显式说明**，否则 §22.3 的全局文案扫描会把「次数」「用完」判为违规，开发或测试会去「修正」它。需要写明：**生成类功能的用量上限提示不属于 §6 任务感表达**，判据为上表四条。与 §7.13.6、C-04 豁免同一体例。

**措辞边界：陈述额度可以，催回访不可以**

| ✅ 可以 | ❌ 不可以 | 原因 |
|---|---|---|
| 「今天的许愿次数用完了」 | 「明天再来许愿吧」 | 后者是回访提示，属催促 |
| 进入工具时显示剩余次数 | 首页 / Tab 上挂「剩余 1 次」角标 | 常驻角标制造稀缺压力与打开动机 |
| 用完后按钮置灰 | 「你今天还没许愿哦」 | 未使用额度被表述成未完成事项，直接构成任务感 |
| — | 「看视频再得 1 次」 | 🟥 撞 C-09 激励广告换资源 |
| — | 「解锁更多许愿次数」 | 🟥 撞虚拟支付与 C-04 |

**🟥 真正的红线不是次数本身，是次数可获得。**

3 次/天固定额度没有问题。一旦次数可以**买**、可以**看广告换**、可以**做任务赚**，性质立刻变化：
- 看广告换次数 → C-09（激励广告换资源），永久停用项；
- 付费买次数 → 触发虚拟支付，直接推翻「IAA 变现、无虚拟支付、免游戏版号」这条已定版的合规路径；
- 做任务赚次数 → 建立任务系统，推翻 §6。

**因此「3 次/天、固定、不可获取」这三个词要一起写进 PRD，不能只写「3 次/天」。**

> ⚖️ **成本待估**：3 次/天 × DAU 的图像生成调用量在规模化后不小。建议排期前先按预估 DAU 算一遍月度成本，再确认 3 这个数字。另外，生成结果需持久化（用户的家具是长期存在的），生成一次永久保存，不重复生成。

**一个零成本的表现层建议：把生成过程说成 ta 在帮你画**

机制上是工具，表现上不必是。生成的等待时间可以呈现为 ta 在施法，而不是一个进度条。理由是它能和窗户那一层共用同一个设定：

| 场景 | 表现 |
|---|---|
| 窗户（全周期） | ta 释放魔法，带你看见远方的大理、北京、西双版纳 |
| 布置区（破壳后） | ta 释放魔法，把你画的东西变成一件真的家具 |

**魔法是 ta 的能力，不是产品的功能。** 两处共用一套视觉语言（施法表现、光效、等待节奏），用户学一次就够；生成结果的偏差也更容易被接受——那是 ta 的理解，不是 bug。

这一条只涉及文案与动效，不改任何机制，不新增模块，可在开发阶段决定。

#### 1.1.4 此刻状态与空间的绑定

**破壳后**，横向全景让「小场景」从一个列表升级成**一个位置**：

| 此刻状态 | 所在屏 |
|---|---|
| 睡觉 / 赖床 / 开着小灯 | 左 · 起居区 |
| 发呆 / 涂涂画画 / 喝东西 | 中 · 桌面 |
| （视右屏方案而定） | 右 · 扩展区 |

进入小程序时**自动定位到 ta 此刻所在的那一屏**，用户可自由滑动到其他屏。会产生一个很好的瞬间——你打开发现桌面是空的，滑到左边，ta 在床上睡着了。**「ta 不在你以为的地方」比「ta 在等你」更像一个活的东西。**

**破壳前**没有屏可切，但同一个效果可以在**单屏内**做到：桌面图里窗台是可见的，蛋可以在**垫子上**或**窗台上**两个位置之间变化。打开发现垫子空着，蛋趴在窗台上看外面——不需要任何手势，悬念一样成立。

### 2.2 Story Engine（剧情引擎）

## 4 · 宠物此刻状态

### 4.1 刷新规则

**此刻的状态每 5 小时更新一次。**

状态序列示例（一天内的连续时段）：

| 时段序 | 状态（大场景 + 小场景） | 对应动作 | 产出纪念物 |
|---|---|---|---|
| 1 | 在家（小憩） | 对话 | 糖画勺 |
| 2 | 旅行（大理） | — | — |
| 3 | 上学（学 AI） | — | — |
| 4 | 打工（餐厅） | — | — |
| 5 | 上学（学英语） | — | — |
| … | 持续生成 | — | — |

### 4.1.1 设计初衷：为什么是 5 小时

**5 小时是刻意选的「除不尽」的数。** 24 ÷ 5 = 4.8，不是整数。这意味着场景切换的时刻**不会每天落在同一个钟点上**。

具体的漂移规律（以全局统一起算为例）：

| 天 | 当天的切换时刻 |
|---|---|
| 第 1 天 | 00:00 / 05:00 / 10:00 / 15:00 / 20:00 |
| 第 2 天 | 01:00 / 06:00 / 11:00 / 16:00 / 21:00 |
| 第 3 天 | 02:00 / 07:00 / 12:00 / 17:00 / 22:00 |
| 第 4 天 | 03:00 / 08:00 / 13:00 / 18:00 / 23:00 |
| 第 5 天 | 04:00 / 09:00 / 14:00 / 19:00 |
| 第 6 天 | 回到第 1 天的时刻，循环 |

即：**切换时刻每天推迟 1 小时，5 天走完一个完整循环，每天落在 4–5 个时段里。**

这个「除不尽」带来三件事：

1. **同一个用户在同一个时间进来，每天看到的 ta 都不一样。**
   如果用 4 小时、6 小时、8 小时、12 小时或 24 小时，都能被 24 整除，习惯晚上 8 点打开的用户会发现「每天这个点 ta 都在做饭」，两周之后这个模块就死了。5 小时让同一个进入时刻在 5 天里扫过 5 个不同的时段。

2. **ta 的作息不围着用户转。**
   这是整个模块的情感底层：ta 在过自己的日子，用户是**碰巧撞见**其中一段，而不是打开一个为自己准备好的表演。固定钟点等于「ta 在等你」，漂移的钟点等于「ta 有自己的时间表」。前者是玩具，后者是活的。

3. **绝大多数时段用户永远不会看到。**
   一天 4–5 个时段，用户可能只进来一两次。看不到的那些照常推进、照常记录——这正是「ta 不在的时候也在生活」的证据。用户偶尔连着进两次撞见两个不同场景时，这个感觉才会真正成立。

> **与「每日心情」的分工再强调一次**：今日心情按自然日走，一天一次，稳定；此刻状态按 5 小时走，跨日漂移，不稳定。**稳定的那层负责「ta 是谁」，漂移的那层负责「ta 在过日子」。** 两层节奏必须不同步，同步了就退化成同一个东西。

### 4.1.2 由「除不尽」引出的三条规则（已定版）

漂移是设计目标，但它带出三条必须先定的规则，均已写入 PRD §12.3.1、§12.3.3、§13.4.1：

1. **夜间场景过滤**：任何小场景都可能落在凌晨 3 点，ta 半夜在「打工（洗车）」会出戏。按时段的实际钟点过滤可用小场景——深夜只允许「家」下的睡觉、看窗外（夜景），「打工」「上学」限制在合理时段。
2. **未访问时段不留物**：用户看不到的时段照常推进剧情，但不产出纪念物。否则隔几天回来会被灌一堆东西。
3. **起算点按蛋计算，基准取破壳时刻**：理由以容量成本为主——全局统一起算要按峰值采购服务器，按蛋起算调用曲线平滑，且对用户体验无差别。顺带每只蛋有自己的作息相位，两个用户同时打开看到的不是同一个场景。

### 4.1.3 「按蛋起算」是什么意思，服务端要做什么

#### 先说人话：每只蛋有自己的作息表

两种做法的区别，用两个用户举例。

**如果全局统一起算**（所有蛋一个时钟）：

> 小 A 和小 B 的蛋，同时在下午 3 点整换场景。全国所有用户的蛋，都在同一秒集体换。

**如果按蛋起算**（每只蛋自己的时钟）：

> 小 A 的蛋是周一早上 8:20 破的壳，所以它的换场景时刻是 8:20、13:20、18:20…
> 小 B 的蛋是周二下午 3:47 破的壳，所以它是 15:47、20:47、次日 1:47…
> 两个人同时打开小程序，看到的不是同一个场景。

**已定版：按蛋起算，从破壳那一刻开始数。**

叙事上讲得通——**ta 的一天从睁眼那一刻开始算**，而不是从某个全国统一的钟点开始算。

#### 为什么这么选：省服务器钱

这才是真正的理由，跟叙事无关。

**全局统一起算的问题**：所有蛋在同一秒换场景，意味着所有 AI 生成请求在同一秒涌进来。平时服务器闲着，一到整点瞬间挤爆。**你得按那个尖峰去买服务器容量，剩下 99% 的时间都在浪费。**

**按蛋起算之后**：破壳时刻本来就是随机分布的（用户什么时候破壳都有），所以换场景的时刻天然均匀散布在 5 小时里。**任何时刻的请求量都差不多，曲线是平的，按平均值买容量就够。**

用户越多，这个差距越明显。而且**对用户体验完全没有影响**——用户根本不知道别人的蛋几点换场景。纯赚。

> 此前担心「按蛋起算会让缓存不能共用、成本更高」，这个判断是错的。此刻状态的内容本来就是每只蛋独有的（由各自的角色人设生成），本来就没法共用缓存。相位只改变「什么时候切」，不改变「内容按谁生成」。真正占大头的场景图、纪念物图这些**素材**是全局共用的，走 CDN，跟相位完全无关。

---

#### 服务端要做的九件事

以下已同步进 PRD v3.6 §12.3.4，并转成验收项（§21 第 34–36 条）。

**1 · 时段号当场算出来，不存数据库**

```
slot_index = floor((现在 − 破壳时刻) / 5小时)
slot_start = 破壳时刻 + slot_index × 5小时
slot_end   = slot_start + 5小时
```

破壳时刻数据库里本来就有，所以**不用新增任何字段**。

好处是：服务器重启、扩容、数据迁移之后，同一只蛋算出来的时段号永远一样，不会错乱。

万一破壳时刻缺失，依次退到绑定时刻、再退到用蛋的 ID 算一个固定偏移。

**2 · 每段内容只生成一次，之后不再重算**

用 `(蛋ID, 时段号)` 做主键。同一只蛋的同一个时段，内容生成一次就固定下来，重试也返回同一条。

> **这里有个坑**：落库时**要把 `slot_start` / `slot_end` 这两个绝对时间也存下来，不能只存时段号**。
>

> 因为如果将来把 5 小时改成 4 小时或 6 小时，「第 100 个时段」对应的实际时间就全变了，历史记录会整体错位——用户翻回去看会发现「ta 上个月的那天在大理」变成了别的日子。存了绝对时间就不受影响。

**3 · 提前备好两段，用户来的时候不用等**

要求任意时刻每只蛋都已经生成到「当前时段 + 后面两段」。

**触发方式是用户访问时顺手检查，不够就在后台补**，而不是搞一个全局定时任务去扫所有蛋——那样又会制造新的请求尖峰，跟第一条的初衷矛盾。

这样用户恰好卡在切换那一秒进来，下一段内容已经躺在那儿了，不用等 AI 现生成。

**4 · 缓存怎么分**

| 存什么 | 能不能全局共用 |
|---|---|
| 状态内容（这只蛋这个时段的文案和场景组合） | 不能，本来就是每只蛋独有的 |
| 场景图、纪念物图、明信片图等**素材** | **能**，走 CDN，所有用户共用同一份 |

素材才是流量大头，它不受影响。

**5 · 夜里不能出现「洗车」**

因为时刻是漂移的，任何场景都可能落在凌晨三点。ta 半夜在洗车会直接出戏。

所以生成的时候就要按这一段的实际钟点筛掉不合理的场景——深夜只留睡觉、看夜景这类。

> **筛选结果要落库，读取时不再重新判断。** 否则同一个时段，用户 8 点看是一个场景、8 点半看又变了，破坏「同一时段内多次进入看到同一状态」这条规则。

**6 · 时间一律以服务器为准**

用服务端北京时间，不信任手机上的时间——用户手机时间调快调慢很常见。

接口返回时段号和起止时间，**前端不自己推算什么时候该换**，只在到点后重新请求一次。

**7 · 🟥 红线：`slot_end` 不许做成倒计时**

这个字段是给前端判断「什么时候该重新拉数据」用的技术字段。

**绝对不能拿它给用户显示「距离 ta 换个地方还有 23 分钟」。**

那就变成催回访了，跟 §4.2「不出现倒计时、冷却」直接冲突。**字段可以下发，展示必须禁止**——这句话要写进接口文档，否则前端很容易顺手做出来，还觉得自己在做体验优化。

**8 · 运营看板按时段看，不按天看**

一天有 4–5 个时段，按自然日聚合会把它们混成一团，看不出问题。

**9 · 留一个能自查的指标**

记录「场景 × 该时段的实际钟点」的分布。

**如果看板上出现了凌晨 3 点的「洗车」，说明第 5 条的夜间过滤漏了。** 这是唯一能自动发现该问题的方式，靠人工抽查基本发现不了。

### 4.2 状态交互与沟通

**八个居家状态恒可对话且各有一个固定动作；外出状态只读。** 外出不提供对话、写信、留言或回信入口。

每段状态有两个属性：

| 属性 | 说明 | 是否必有 |
|---|---|---|
| **对应动作** | 居家时用户在这个场景可做的固定动作（清单见 §10A.4） | 仅居家 |
| **沟通方式** | 居家从左下角入口进入完整对话页；外出不显示沟通入口 | 仅居家 |

**对应动作是主体，说话是附加。** 大部分时候用户做的是关灯、盖被子、翻书页这类事，不是打字。

#### 4.2.1 对话与外出只读

判据只有所在大场景：**在家即可对话，外出则只读。** 睡觉、赖床、打游戏等居家状态也保留完整对话页入口，回应可按情境缩短，但不得关闭输入。

八个居家场景全部可以对话；旅行、打工、上学统一无沟通入口。

完整对照表见 §10A.4（含对应动作与即时反馈）。

#### 4.2.2 硬规则

1. **居家对话使用完整对话页。** 点击左下角角色按钮直接跳转；不先定位角色，不显示三点提示，不弹出场景内输入框。
2. **外出无沟通入口。** 旅行、打工、上学不开放对话、写信、留言或回信。
3. **外出无用户动作。** 空房和第一人称去向文字只读，不派生回信或纪念物。
4. **映射不可随机改写。** `home = action + talk`，`travel / work / school = read_only`。

> **与空间模型的关系（见 §1.1）**：「家」这条大场景线不是一个抽象分类，而是**破壳后横向全景的三屏**——起居区 / 桌面 / 窗户区。下面树里「家」的小场景需要各自落到某一屏上。目前「做饭」没有对应的屏，见 §1.1.4 P3。


```

│   ├─ 生产方式：原创绘制或 AI 原创生成，生成记录进入提审归档
```

## 6 · 纪念物（ta 带回来的东西）

### 6.1 它是什么

**一件 ta 从某段日子里带回来的小东西，附一则故事。**

它的价值不在物件本身，在于**它证明那段时间真的发生过，而且你在场**。

| 项 | 说明 |
|---|---|
| 何时出现 | 只在破壳后。破壳前蛋哪儿也没去，没有东西可带回来 |
| 由什么触发 | 用户完成该场景的对应动作（动作清单见 §10A.4） |
| 与场景的关系 | 强绑定。ta 在哪个小场景待过，就带回对应的那件 |
| ta 不在家时 | 空房只读，无对应用户动作，不因用户输入产生纪念物 |

### 6.1.1 选物的两条线

原先列的糖画勺、拨浪鼓、单词红宝书太「日用」了——是生活道具，不是有分量的东西。年轻人愿意截图发出去的，是**能替自己说句话**的物件。

现在分两条线出物：

| 线 | 来源 | 作用 |
|---|---|---|
| **A · 通用祈愿物** | 民俗物料库 | 所有角色都可能带回，承担「好兆头」的分量 |
| **B · 角色定制物** | **从该角色的动作图里长出来** | 只有这个角色会带回，承担专属感 |

**B 线的生成规则：ta 做过的那件事，留下了什么。**

角色动作图（玉兔的毛绒动作组、锦鲤的水彩动作组）已经把「ta 在干什么」画完了。**每张动作图天然对应一件残留物**——泡过澡就有那只小黄鸭，骑过车就有车铃铛，踢过毽子毽子就还在。

这比凭空挑物件强在：物和事**本来就是一件事**，故事不用硬编，而且它正好落在 §6.1 那句话上——**它证明那段时间真的发生过**。

选物判据仍是三条：带祈愿或纪念属性、与 IP 根系对得上、单件平面一张图可成立。

#### 6.1.5 出图风格（已定版：统一 3D）

**全部纪念物统一使用 3D 渲染风格，不跟随角色的原画风格。**

参考图里玉兔是毛绒 3D、锦鲤是水彩，但纪念物是同一面墙上的东西——各随各的画风，用户翻看「ta 带回来的东西」时会看到一半 3D 一半水彩，整面墙是碎的。

**给 Codex 的完整前缀**，拼在每条短提示词之前：

```
温暖治愈的 3D 渲染风格，柔和自然光，低饱和奶油色调，
单件物品居中，微俯视角度，
纯透明背景，物体边缘干净，不带任何底色与投影，
不出现人物、文字与商标。
```

四条一致性要求，出图时全批统一，不单张微调：

1. **视角一致**——全部微俯视，不能有的正面有的侧面；
2. **相对尺寸一致**——铜钱和折纸船在画面里占比接近，不按真实大小缩放；
3. **材质表现一致**——同一套光照与粗糙度，金属就是同一种金属；
4. **透明底干净**——无投影、无底色，投影由前端代码统一加。

> 💡 **锦鲤那套水彩不要浪费**：横构图、留白边框、场景感，正好是**明信片**（§7）要的样子。建议把水彩定为明信片的视觉语言，与 3D 的纪念物形成两种质感，各司其职。

### 6.2 每件的两个要素

1. 一张平面 2D 图；
2. 一则预制的治愈系故事（道具故事）。

### 6.3 写作范式

1. 一件具体的旧物 + 一个具体的关系；
2. 一次给予，或一次失去；
3. 结尾落在**一个至今仍在做的小动作**上；
4. 不说教、不煽情、不解释道理；
5. 2–3 句，一屏读完；
6. 允许跨角色互相出现，构建 IP 宇宙的连带感；
7. 不出现死亡的直接描写、不出现可诊断的心理状态、不出现真实品牌。

#### 6.3.1 让故事有梗的四种结构

范式管的是形状，梗管的是**最后一句是否让人「噢」一下**。四种结构，够覆盖绝大多数物件：

| 结构 | 做法 | 例 |
|---|---|---|
| **① 重新定义失败** | 承认自己做得不好，然后把标准换掉 | 毽子：踢不过十个，「重点不是踢多少，是毽子落下来的时候你还在原地」 |
| **② 明知故犯** | 知道问题出在哪，但选择不改 | 浮漂：做成鱼的样子所以钓不到鱼，「它知道，但没换」 |
| **③ 位置的反讽** | 拥有得最多的那个，恰恰缺那一样 | 月相卡：住在月亮上，反而看不见月亮长什么样 |
| **④ 数量的错位** | 用一个不成比例的数字制造反差 | 玉杵：捣到杵头都磨圆了；铜钱：捣了三年也没捣碎 |

**写的时候只用一种，不叠加。** 两个梗放一起会互相抵消，读起来像在使劲。

**判据**：把最后一句单独拎出来，如果它只是在总结前面，就是还没写好；它应该让前面的话**换一个意思**。

### 6.5 硬规则

**纪念物是纯内容，不是资产。**

- 不可交易、不可赠送、不可合成、不可兑换；
- 不影响实体结果与收藏卡字段；
- 不构成收集系列：不设总数、不设图鉴、不设空位、不显示进度；
- 不解锁任何其他内容或权益；
- 用户侧文案禁用 `解锁` / `获得` / `集齐` / `收集进度` / `已收集 X/Y` / `还差几件`（PRD §22.3）。

> ✅「ta 从大理带回来一样东西，想给你看看。」
> ❌「恭喜解锁第 3 件纪念品！」「收集进度 3/12」

## 7 · 明信片

### 7.1 单向送达机制

| 方向 | 规则 |
|---|---|
| 用户收信 | 到条件后由服务端主动发给用户，**忽略登录状态、可累积接收** |
| 用户回信 | 不提供；前端与服务层均不保留写信能力 |

> 收信不依赖登录，意味着用户隔了很久回来会一次性收到一批 —— 这是**回流钩子**的核心设计点。同时需注意：累积的信件内容不得出现催促、责备、被抛弃类表达（PRD §13.5.2）。

### 7.2 新消息入口状态（后续版本储备，V3.6 / V3.7 停用）

V3.6 / V3.7 不在生活空间、对话入口或“我的 / 设置”显示明信片红点，也不提供明信片列表入口。送达与已读字段可保留在数据层，正式 UI 不消费；后续版本恢复前重新确认提示位置与已读语义。

### 7.3 素材构成

1. 预制一批明信片正面插画；最终交付为静态 2D 图片，画面可使用统一的 2.5D 渲染风格；
2. 居家、打工、上学可复用已批准的场景母题；旅行使用独立目的地插画库；
3. 旅行期间主页保持空房与文字，目的地插画仅在回家后送达的明信片列表与详情中出现；
4. 正式旅行目的地为大理、北京、西双版纳、东京；详细规则见《蛋宝宝旅行明信片内容与美术规格 v1.0》。

## 8 · 收藏卡 · 今日推荐

收藏卡本身由 PRD §11 定义——一枚实体蛋一张，破壳时生成，留在账号里。本节只管**每天把它拿出来给用户看一次**。

### 8.1 机制

**AI 今日推荐**：每天挑一张用户账号里的收藏卡 + 一句 AI 生成的推荐语。

- 每个自然日更新一次，与今日心情同一节奏；
- 可保存到本地，口径参照 PRD §11.7。

### 8.2 可选范围

从**账号内已有的收藏卡**里挑，没有的不展示、不虚化、不留空位、不提示「绑定后可见」。

**解绑不影响。** 收藏卡一经生成就留在账号里，解绑实体蛋不删卡。**这些是回忆，不是权益，没有收回的理由。**

### 8.3 推荐语（生成层）

一句短话，让用户看到时心头一乐。

> 这句话是**推送文案层**，承担打开率。**卡是内容，推荐语才是钩子。**

### 8.4 卡面变体（已定版）

一枚实体蛋只有一张收藏卡（PRD §11.2），只有一只蛋的用户账号里就一张卡。

**做法：给同一张卡出多个卡面变体（季节 / 昼夜 / 天气版），推荐时轮换。**

变体的切换条件与窗外景色复用同一组变量（天气、时段、节令），不新增判断逻辑。卡的本体、字段、编号都不变，变的只是卡面呈现。

## 9 · 用户图生图（永久不做）

原设想：让用户上传自己的照片，AI 加工成明信片风格。

**产品决策（已定版）：不做，以后也不做。** 该条不作为「未来可能开启」的选项保留，涉及此方向的需求直接驳回。

停用范围：用户上传照片、上传图片二次生成、以用户上传素材参与任何内容生成。

> 与右屏的 AI 绘画工具（§1.1.3）是两件事：那条是**用户自己画**，输入是笔迹，本产品自有；这条是**用户传照片**，输入是外部影像，牵涉真人肖像、第三方版权、未成年人保护，负担完全不同。

### 10A.4 破壳后 · 每段状态的对应动作

破壳后的核心交互：**每段状态配一个对应动作，用户做了那个动作，这一段的纪念物才出现（§6）。**

ta 在睡觉时你关掉灯——这个动作本身就是陪伴，纪念物只是它的回音。用户在做的事是「读懂 ta 现在需要什么」，而不是「触发一个按钮」。

| 屏 | 小场景 | 用户要做的事 | 即时反馈 | 能说话 |
|---|---|---|---|---|
| 起居区 | 睡觉 | 点台灯关掉 | 房间暗下来，ta 翻了个身 | ✓ |
| 起居区 | 赖床 | 拉被角替 ta 盖好 | 被子被拉上，ta 往里缩了缩 | ✓ |
| 桌面 | 发呆 | 点 ta | ta 慢半拍地回头看你 | ✓ |
| 桌面 | 涂涂画画 | 点画纸 | 画纸转向你，能看清 ta 画了什么 | ✓ |
| 桌面 | 看书 | 翻书页 | 书页翻过去，故事又向前走了一小格 | ✓ |
| 桌面 | 打游戏 | 点屏幕 | 画面里的角色动了一下，ta 没抬头 | ✓ |
| 桌面 | 听音乐 | 一起听 | 旋律又走了一小段，房间里像多了一点月光 | ✓ |
| 窗户区 | 看窗外 | 点窗户，陪 ta 一起看 | 进入日常窗外详情，展示真实天气、五时段动效与第一人称陪伴气泡；本版不显示 ta 的背影 | ✓ |
| — | 不在家（旅行 / 打工 / 上学） | 留言 | 留言送出，画面里仍是空着的家 | — |

**七条硬规则**：

1. **动作只用场景里本来就有的物件，不新增按钮。** 一旦出现「互动」按钮，就变回任务了。
2. **每段状态只有一个对应动作，不给选项。** 唯一解才有「读懂了」的感觉。
3. **不提示、不预告。** 不出现「试试关掉台灯」「再互动一次就有东西」。
4. **点错不惩罚、不纠正。** 安静地什么都不发生，比提示更接近真实。
5. **给极轻的视觉线索。** 对应物件带一点呼吸感或微光——看得出可以点，但看不出是任务。
6. **一次就够，不设次数。**
7. **用户没在场的时段不留物。**

> 判据：如果一个动作需要解释，说明这个动作设计错了，改动作，不加提示。

### 11.4 分层硬规则

1. 房间使用完整环境底图；蛋、窝垫、天气动态和 UI 保持独立。
2. 日常窗外详情本版不显示蛋 / 角色背影；魔法窗外若后续使用背影层，也必须保持独立。两个视图都不得把角色、UI 或代码光效烘焙进背景图。
3. 日常窗外进入和返回采用稳定的全屏淡入 / 淡出，不做几何位移，不使用默认左右滑动转场。
4. 弱动效模式显示静态代表帧并停止持续位移、浮尘、环境鸟影与闪电；点击鸟只保留 `2s` 透明度淡出。离页停止全部连续动效并清理计时器。
5. 两个独立视图都必须有加载、失败、重复进入与返回路径。
6. 日常窗外的业务内容随机只作用于陪伴文案，不随机天气或时段；清晨点击鸟的位置与外观允许做临时视觉随机，但不得影响窗景和业务状态。文案不得立即重复，不落库、不计次数、不改变业务状态。
7. 清晨点击鸟影属于纯临时视觉反馈，不落库、不计次数、不发送业务结果；最多同时 6 只，返回、失败、重试和销毁时必须清理。
8. 日常窗外当前不添加任何音频，不播放鸟鸣、环境声或背景音乐，也不申请音频权限。
