## 1 · 审查目标

破壳后，「我的 / 设置」应让用户清楚地管理账号、通知、隐私与注销，不制造无效提醒，也不把服务端应负责的授权、留存、删除或身份判断放到 App。

本审查回答四件事：

1. 当前设置页是否有对破壳后用户无意义、不可用或会误导的项目；
2. 哪些问题 App 可以先修复；
3. 哪些必须由 CTO、法务或运营确认；
4. 设置状态如何与正式服务、聊天记录和账号注销保持一致。

## 2 · 范围与非范围

### 2.1 本次范围

- 「我的」入口与导航；
- 个人信息（头像、昵称）；
- 系统设置（订阅消息与通知偏好）；
- 账号（退出登录、开发验收清除、本账号注销）；
- 隐私协议、帮助和邮件支持（`hello@eggbabe.com`）中的设置相关承诺；
- 破壳后用户的聊天记录与账号删除关系。

### 2.2 明确不在本次范围

- 破壳前孵化提醒的内容策略；
- 收藏卡、明信片、旅途回放及其通知；这些功能在 V3.6 / V3.7 正式版均不得触达；
- 广告、算法推荐、画像、关系成长、任务与经济系统；
- 在 App 本地判断聊天安全、危机或敏感信息。

## 4 · 破壳后设置的目标信息架构

### 4.1 「我的」

保留现有入口：个人信息、我的激活码、系统设置、账号、隐私协议、帮助中心。不得在此加入“好感度”“连续陪伴”“成长数据”或任何促使用户反复打开的通知开关。

### 4.2 系统设置

破壳后系统设置只保留仍然真实可用的项目：

| 分组 | 项目 | 破壳后规则 |
| --- | --- | --- |
| 消息通知 | 陪伴服务提醒 | 只有已上线、已配置微信模板、经用户主动授权且服务端实际会发送的类型才展示 |
| 消息通知 | 破壳提醒 | 用户已破壳后隐藏，不保存为有效偏好，不再请求模板 |
| 消息通知 | 节令上新 | V3.6 / V3.7 正式版先隐藏；未来真实上线后，另行确认内容、模板、频率与退订方式 |
| 隐私与数据 | 隐私协议 | 可查看当前版本、生效日期和联系/删除方式 |
| 账户 | 退出登录、注销账号 | 保持独立入口与明确后果说明，不与通知设置混在一起 |

没有真实可发送的破壳后提醒时，系统设置应显示简短说明“当前没有可管理的提醒”，而不是展示无法生效的开关。

## 5 · 责任边界

### 5.1 App 可以先完成

1. 根据蛋的权威生命周期展示或隐藏“破壳提醒”；已破壳用户不显示该开关。
2. 下线或禁用当前不可用的“节令上新”开关，修复不存在方法的调用，避免点击报错。
3. 将通知开关改为明确状态展示：`未开启`、`已开启`、`未授权`、`暂不可用`；授权请求失败或被拒绝后回滚页面状态。
4. App 回到前台时重新读取正式设置结果；不把本地缓存当作 live 最终事实。
5. 退出登录时清除本机用户、会话缓存、通知偏好缓存和未上传的非必要队列；不删除服务端数据。
6. 在注销确认页清楚说明：聊天记录和账号数据会按隐私政策处理，冷静期内可以取消，处理完成后不可恢复。
7. 补齐设置页的可点击面积、按压态、加载态、失败重试、弱动效和真机测试。

### 5.2 CTO 必须完成

1. 以当前登录用户为唯一主体读取和写入通知偏好，不能信任 App 自带的用户或蛋 ID。
2. 提供通知偏好读取/更新接口，保存模板级授权状态、偏好状态、更新时间和必要审计信息。
3. 仅当模板已配置、用户对该模板有效授权、内容仍在发布范围内时发送订阅消息；服务端控制频率、退订和发送审计。
4. 个人资料、头像 URL、昵称、登出会话、注销状态和删除执行均由服务端确认。
5. 注销到期后删除或匿名化聊天记录、账号资料、创作与绑定数据；任何法定/售后例外留存须最小化、可审计并与隐私协议一致。
6. 记录隐私协议版本及用户必要同意/更新记录，不将聊天正文或通知偏好用于画像、推荐或广告定向。

### 5.3 法务与产品必须确认

- 正式版是否存在任何破壳后的订阅消息；若有，逐项确认目的、模板 ID、触发条件、最高频率、关闭方式和文案；
- 注销后聊天记录、危机安全审计和售后必要记录的保存期限；
- 隐私协议版本、生效日期、第三方处理者、存储地域与用户权利路径；
- “节令上新”是否属于未来版本范围；未确认前不得在正式设置页展示。

## 6 · 通知偏好状态机

通知设置不使用简单的布尔值作为正式事实。每个通知类型独立维护以下状态：

| 状态 | App 展示 | 允许操作 | 服务端语义 |
| --- | --- | --- | --- |
| `unavailable` | 暂不可用 | 不请求授权 | 模板/功能未上线或不在发布范围 |
| `not_enabled` | 未开启 | 用户点击后发起微信订阅请求 | 未获得有效授权或用户未选择接收 |
| `enabled` | 已开启 | 可关闭；按平台规则再次确认 | 有效授权与服务端偏好均存在 |
| `declined` | 未授权 | 用户再次主动点击后才可重新请求 | 上次请求未获授权；不影响其他模板 |
| `loading` | 正在更新 | 禁止重复点击 | 正在等待微信或服务端确认 |
| `error` | 更新失败，点击重试 | 重试同一操作 | 本次状态未确认，保留服务端旧值 |

规则：

- App 不得在用户点开关的一瞬间永久写成“已开启”；必须在微信订阅结果与服务端偏好确认后再展示成功。
- 每类模板独立处理拒绝与授权；“破壳提醒被拒绝”不能阻止未来其他通知类型。
- 一次用户拒绝不应在后台反复弹授权；只有用户再次主动进入并点击同一项时，才可重试。
- 功能下线、模板失效或用户破壳后，服务端返回 `unavailable`，App 清理对应展示状态。

## 7 · 推荐接口契约

### 7.1 读取设置 `getSettings`

```json
{
  "mode": "live",
  "request_id": "request-id",
  "client_version": "3.7.0-ordinary"
}
```

服务端按会话识别用户，返回：

```json
{
  "success": true,
  "data": {
    "mode": "live",
    "notification_preferences": [
      {
        "type": "companion_reminder",
        "availability": "unavailable",
        "status": "unavailable",
        "template_id": "",
        "updated_at": "2026-08-10T12:00:00+08:00"
      }
    ],
    "privacy_policy": {
      "version": "2026-08-10",
      "effective_at": "2026-08-10T00:00:00+08:00"
    }
  }
}
```

### 7.2 更新偏好 `updateNotificationPreference`

```json
{
  "type": "companion_reminder",
  "requested_enabled": true,
  "platform_authorization": "accept",
  "request_id": "idempotency-key",
  "mode": "live"
}
```

服务端必须再次校验模板是否可用、用户授权是否有效、请求用户身份与当前发布范围。响应返回最终状态；App 不自行推断成功。

### 7.3 账户与注销

- `logout`：服务端撤销当前会话或令牌；App 仅在成功或本地会话已无效时清除本机缓存。
- `manageDeletion(query/request/cancel)`：沿用现有操作，但服务端响应必须含当前状态、冷静期截止时间、隐私政策版本及可向用户披露的例外说明。
- 删除执行由服务端异步完成并留审计证明；App 不能通过“清除本地数据”冒充正式注销。

## 8 · 数据与隐私要求

1. 通知偏好只用于用户明确请求的提醒，不用于推断兴趣、关系、活跃度或营销画像。
2. 聊天正文、危机标签、安全评分、模型提示词和历史上下文不得进入设置埋点或通知偏好接口。
3. App 不在本地长期保存聊天正文、失败消息或通知授权的敏感原始结果；未完全退出前的未送达聊天消息仅存在页面内存。
4. 通知与资料的本地缓存必须按账号命名空间隔离；退出登录、注销完成或账号切换后清理。
5. 隐私协议的页面文案、后台保存期限与注销页承诺必须一致；发生冲突时，以法务确认的正式版本为准。

## 9 · 错误处理

| 场景 | App 行为 | 服务端要求 |
| --- | --- | --- |
| 模板未配置/功能未发布 | 显示“暂不可用”，不弹授权 | 返回 `unavailable` |
| 用户拒绝订阅授权 | 保持未开启/未授权，不显示成功 | 不写已开启偏好，不影响其他模板 |
| 网络失败 | 恢复服务端已知旧状态，显示重试 | 不产生不确定写入；写操作幂等 |
| 多设备同时修改设置 | 重新读取最终状态 | `updated_at`、版本或条件写入防止覆盖 |
| 登录失效 | 引导重新登录，不继续写偏好 | 返回 `AUTH_REQUIRED` |
| 注销冷静期 | 显示当前状态与取消入口 | 拒绝重复提交，返回权威截止时间 |
| 注销已执行 | 返回欢迎/登录页，不保留本机账号数据 | 拒绝所有旧会话和旧数据访问 |

## 10 · 分阶段执行顺序

| 顺序 | 工作项 | 负责人 | 开始条件 | 完成条件 |
| --- | --- | --- | --- | --- |
| 1 | 修复节令开关调用错误；破壳后隐藏破壳提醒 | App | 产品确认本 PRD | 页面无无效开关、无运行时错误 |
| 2 | 重构 App 通知状态展示与失败回滚 | App | 第 1 项完成 | 不会把拒绝/失败显示成已开启 |
| 3 | 确认正式破壳后通知清单；未确认则正式页不展示通知开关 | 产品 + 法务 | 第 2 项方案确认 | 形成模板、频率与文案清单 |
| 4 | 实现通知偏好、会话退出、隐私版本和注销执行接口 | CTO | 第 3 项确认 | 接口、鉴权、审计和删除测试通过 |
| 5 | 接入 live 设置并做双端真机联调 | App + CTO + QA | 第 4 项可用 | 授权、拒绝、跨设备、注销全链路通过 |

未经第 3 项确认，App 不得把“节令上新”或其他未来内容伪装成可生效的正式通知。

## 11 · 验收清单

### 11.1 App 自动化与页面验收

- [ ] 破壳后不显示破壳提醒；
- [ ] 正式版不显示未上线内容的通知开关；
- [ ] 点击所有可见设置项不报错；
- [ ] 用户拒绝授权、网络失败、重复点击后，页面均不误显示“已开启”；
- [ ] 每个通知类型互不影响；
- [ ] 退出登录清除本机设置缓存，但不显示“已删除服务端数据”；
- [ ] 注销页与隐私协议均明确聊天记录处理与冷静期；
- [ ] 小屏、深色系统、弱动效、iOS/Android 下可读、可点、无安全区遮挡。

### 11.2 CTO / 法务验收

- [ ] 未登录、跨账号、伪造请求和失效模板均不能修改他人偏好；
- [ ] 通知只发送给有效授权、有效偏好和发布范围内用户；
- [ ] 偏好跨设备一致，最近写入规则可审计；
- [ ] 不把通知偏好、聊天记录或注销数据用于画像或广告定向；
- [ ] 注销 request / cancel / 到期执行、聊天记录删除与例外留存均可审计；
- [ ] 隐私协议版本、同意记录和实际数据流程一致。

## 12 · 本轮待产品确认的决策

1. V3.6 / V3.7 是否存在任何真正的破壳后订阅消息？若否，系统设置中的通知分组应整体隐藏或显示“当前没有可管理的提醒”。
2. 若未来启用提醒，第一种提醒是什么、谁会收到、最多多久一次、使用哪一个微信模板？
3. 注销后聊天正文、危机安全审计和售后必要记录的保存期限分别是什么？
4. 隐私协议是否改为服务端版本化下发/备案域名页面，及其上线生效流程？

在以上决策未确认前，本 PRD 的默认执行原则是：**隐藏无效通知开关、不给用户虚假的“已开启”状态、聊天和删除规则以服务端与法务为准。**
